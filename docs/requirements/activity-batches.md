# 활동 배치 수락과 비동기 처리

## 목적과 사용자

활동을 수집하는 macOS 클라이언트는 여러 활동 레코드를 배치로 보내고, 서버의
DB 처리 완료를 기다리지 않고 전달 수락 여부를 확인한다. 사용자는 열린 화면에서
DB에 반영된 관찰 타임라인을 주기적으로 조회한다.

## 현재 구현 범위

이번 서버 범위는 애플리케이션과 독립된 Kafka 전달 경로, 활동 배치 수락 API, 별도 Handler의
원본 저장·타임라인 갱신, 제한된 실패 보관과 재처리 경로다. 기존 단건 활동 POST를
배치 API로 대체하고, 타임라인 GET과 라벨·집중 세션·계정 API 계약은 유지한다.
클라이언트 연동 범위는 배치 생성·재전송·수락 확인과 타임라인 polling이다.

## 기능 요구사항

### 서버 수락

- FR-1: `POST /api/v1/activities/batches`는 Bearer 인증 계정과 `deviceId`의
  귀속을 확인한다. 계정은 인증 결과에서 결정하며 요청 body에서 받지 않는다.
- FR-2: 요청은 UUID `batchId`, UUID `deviceId`, 1~200건의 `records`로 구성한다.
  개별 레코드의 `deviceId` 반복을 제거하고 `eventId`, `sequence`, `recordType`,
  `observedAt`, `timezoneId`, `utcOffsetMinutes`, 선택적 `focusSessionId`와 종류별
  문맥 또는 수집 상태·사유의 기존 의미와 검증을 유지한다.
- FR-3: 비압축 JSON 본문은 512 KiB 이하다. 입력 검증에 실패한 요청은 일부도
  전달하지 않으며, Kafka에는 배치 전체를 하나의 메시지로 발행한다.
- FR-4: 수락 성공 시 `202 {"batchId": "...", "status": "accepted"}`를 반환한다.
  Kafka 발행 ACK를 확인한 뒤 응답하며 Handler의 DB 처리 완료를 기다리지 않는다.
  최초 저장 시각·원본별 처리 건수·DB
  완료 시각을 반환하지 않는다.
- FR-5: 스키마·빈 배열·건수·필드 오류는 422, 크기 초과는 413, 인증 실패는 401,
  Device 미등록·귀속 불일치는 404, 발행 실패·ACK 제한 시간 초과·과부하는 503으로 응답한다.
  기존 공통 오류 형식을 유지한다.

### 원본 처리와 타임라인

- FR-6: 이미 저장된 `eventId`와 Device별 `sequence`의 중복·충돌은 Handler에서
  판정한다. 기존 처리 결과를 덮어쓰지 않고 계정·Device 경계를 보호한다.
- FR-7: 같은 Device sequence의 서로 다른 원본은 먼저 온 기록을 유지하고 후발
  기록만 거절한다. 배치 내부 중복도 한 번만 반영하고 충돌 승자를 결정적으로 선택한다.
- FR-8: sequence의 연속성을 요구하지 않는다. 미사용 낮은 sequence와 역순 도착도
  수용하고 영향받는 타임라인을 재구성한다. 같은 Device에서 sequence 증가에 따라
  관찰 시각이 감소하면 배치 전체를 롤백하고 실패 원본을 보관한다.
- FR-9: 중복·충돌 원본을 제외하고,
  채택 원본과 구간 변경을 하나의 DB 트랜잭션으로 반영한다. DB 처리 장애 시 채택 집합의 변경을 전부 롤백한다.
- FR-10: 동일 Device 내 관찰 순서는 sequence를 기준으로 하며 관찰 시각은
  구간 경계의 근거로 보존한다. 서로 다른 Device의 sequence를 계정 전역 순번으로
  비교하지 않는다. 서로 다른 Device의 관찰 시각이 같으면
  `deviceId → sequence → eventId` 오름차순으로 정렬한다.
- FR-11: 뒤에 이어지는 입력은 마지막 상태에서 증분 갱신하고, 과거 변경은 배치
  단위로 묶어 영향받는 지점부터 재구성한다. 기존 상태·경계와 일치하는 안전한
  경계에서 재계산을 멈춘다.
- FR-12: 문맥 전체 동등성, 불투명 활동, 명시적 수집 중단·재개 공백, 60초 병합,
  길이 없는 구간, 날짜를 넘는 구간, 내용 버전과 라벨 적용성은 보존한다.
- FR-13: 선택적 집중 세션 연결의 소유권·시간·수집 상태 규칙을 보존한다.
  Handler에서 소유권·시간 검증에 실패하면 배치 전체를 롤백하고 실패 원본을
  보관한다. 오류 원본만 제외하거나 연결만 제거해 저장하지 않는다.

### 전달 장애와 복구

- FR-14: 동시 발행·처리와 실패·보류 보관량을 제한하고 애플리케이션 시작·종료에 맞춰
  관리한다. 처리 메시지는 종료된 HTTP 요청의 DB 세션을 재사용하지 않는다.
- FR-15: Handler의 일시 장애는 최초 시도를 포함해 총 5회 처리하며, 재시도 대기
  상한은 1/2/4/8초와 jitter를 적용한다. 정상 중복·sequence 충돌은 장애 재시도 대상이 아니다.
- FR-16: 실패·보류 원본은 제한된 개발용 진단 경로에 보관한다. 같은
  계정·Device의 후속 배치는 수락 순서대로 보류하고 다른 Device·계정은 계속
  처리한다. 실패한 선두 배치의 재처리 성공 후 보류를 원래 순서대로 해제한다.

### 클라이언트 연동

- FR-17: 전송 가능한 상태에서 대기 10초, 최대 200건, 비압축 본문 512 KiB 중
  먼저 도달한 조건으로 전송한다. Device별 전송 중인 배치는 하나이며, 수락 응답 후
  해당 로컬 배치를 제거하고 적체가 있으면 다음 배치를 즉시 전송한다.
- FR-18: 응답이 확인되지 않으면 로컬 원본을 보존하고 같은 batchId와 내용으로
  재시도한다. full jitter를 적용한 backoff 상한은 1/2/4/8/16/32/60초이며
  `Retry-After`를 존중한다.
- FR-19: 전달 수락 전에 명확하게 받은 413에는 원본 ID·sequence·내용을 유지해
  재분할하고 새 batchId를 사용할 수 있다. 단건 원본이 크기를 초과해도 절삭하지 않는다.
- FR-20: 화면을 열거나 재활성화하면 즉시 조회하고 열린 화면은 초기 5초 간격으로
  polling한다. 숨김 상태에서는 중단하며 겹치는 요청·오래된 응답 반영을 방지한다.
  조회 오류 시 기존 화면을 유지하고 backoff한다.

## 정책과 불변식

- `accepted`는 Kafka 브로커의 발행 ACK를 확인했다는 뜻이다. DB commit,
  consumer offset commit, 원본별 처리 성공을 뜻하지 않는다. 보존과 장애 내성의
  범위는 연결한 Kafka의 복제·저장·retention 설정에 따른다.
- 같은 batchId의 재시도는 같은 계정·Device와 같은 원본 내용으로 한다. 다른 내용은
  내부 거절·진단 대상이며 동기 DB 조회를 통한 즉시 HTTP 409는 보장하지 않는다.
- HTTP 입력 검증 실패 시 전체 미전달과, Handler의 원본별 거절 후 채택 집합
  원자적 반영은 서로 다른 경계다. 중복·sequence 충돌은 원본별로 처리하며
  집중 세션 연결 오류·DB 장애·관찰 시각 역행은 배치 전체를 롤백한다.
- 재전송·재시작·동시 처리에도 원본의 중복 안전성과 계정 격리를 유지한다.
- 시간 역행을 음수 간격의 정상 병합으로 처리하거나 원본 시각을 자동 보정하거나
  거짓 구간 경계를 만들지 않는다. 관찰 시각 역행 시 배치 전체를 롤백하고 보관한다.
- Kafka 발행 ACK를 확인하지 못하면 성공을 반환하지 않는다. 다만 브로커에
  기록됐을 가능성은 있으므로 동일 batchId·내용으로 재시도한다.

## 예외와 경계 조건

- 빈 배치·건수 초과·잘못된 종류별 필드·미등록 및 다른 계정 Device를 거절한다.
- 동일 eventId 재전송, Device별 sequence 충돌, 배치 내부 중복, 순번 누락,
  낮은 sequence의 지연 도착을 구분한다.
- 같은 계정·Device의 동시 처리와 프로세스 재시작 후 중복 처리에서도 기존
  UNIQUE/FK 및 필요한 DB 동시성 보호를 유지한다.
- 미시작·종료 중·전달 용량 부족 상태에서 새 배치를 수락 성공으로 응답하지 않는다.
- 자정 경계, 길이 없는 구간, 불투명 활동, 명시적 수집 공백과 라벨 확정 이력의
  적용성을 배치 도입 후에도 보존한다.

## 비기능 요구사항

- 개인정보 보호와 기존 입력 검증·공통 오류 계약을 유지한다. 요청 세션·인증 토큰 등
  HTTP 요청 자원을 비동기 메시지에 의존시켜 처리하지 않는다.
- 무제한 task·backlog를 만들지 않으며, 종료 시 Worker·메시지 세션·트랜잭션을
  정리하고 미관찰 task 예외를 남기지 않는다.
- 정상 경로에서 매 배치마다 계정 원본 전체 조회 또는 구간 전체 삭제·재삽입을 하지 않는다.
  전체 재생과 증분·부분 재생 결과의 관찰 의미가 같은지 비교해 정확성을 검증한다.
- 처리 속도·응답 지연의 수치 목표는 미정이다. 측정하지 않은 성능 개선을 주장하거나
  정상 계산에 근거 없이 짧은 hard timeout을 정하지 않는다.
- FastStream과 faststream_fastapi를 사용한다.
  실제 등록 Handler 실행, HTTP 응답 선반환, 독립 세션, lifespan, 수락 실패를
  실제 라이브러리 조합으로 검증해야 한다.

## 확장 방향

Kafka 연결 정보는 환경별로 구성하며 개발·운영 환경에 같은 발행 수락 계약을
적용한다. 개발 환경의 로컬 Docker 실행 방식으로 운영 배포 방식을 제한하지 않는다.
운영 환경의 복제·retention·장애 대응 정책은 별도로 정의한다.

기존 이력의 최초 정렬 전환은 부분 재구성으로 최적화할 필요가 있다. 변경 지점
식별과 안전한 재구성 범위의 조건은 [활동 배치 PRD](../prd/activity-batches.md)의
확장 방향을 따른다.

## 제외 범위

- 원본별 부분 실패를 클라이언트에 알리는 응답·조회·복구 계약.
- 운영 Kafka 배포·다중 브로커 장애 내성·운영 retention·복제 정책, Outbox·CDC.
- Spark·분석·AI 신규 기능, 전체 모듈 이동, Account–Device 리팩토링 재도입.
- 단조 시계 도입, 단일 활성 Device 강제, 원본 시각 자동 보정.
- 다른 macOS 기능·UI 전체 재설계·인증 정책 변경.
- 운영용 원본·receipt 보존 정책과 처리 지연의 수치 목표 확정.

## 인수 조건

- AC-6001: 인증 계정 소유 Device의 유효한 1~200건 배치를 발행하고 브로커 ACK를 확인하면,
  Handler의 DB 처리가 대기 중이어도 batchId와 accepted만 담은 202가 먼저 반환된다.
  ACK를 확인하기 전에는 202를 반환하지 않는다.
- AC-6002: 잘못된 스키마·빈 배열·건수 초과는 422, 512 KiB 초과는 413,
  인증 실패는 401, Device 미등록·귀속 불일치는 404이며 일부 원본도 전달하지 않는다.
- AC-6003: 발행 실패·ACK 제한 시간 초과·미시작·종료 중·용량 부족에는 503으로 응답하고
  수락 성공을 반환하지 않는다.
- AC-6004: 동일 계정·Device·batchId와 같은 내용의 재시도는 결과를 중복 반영하지
  않으며, 다른 내용은 기존 결과를 덮어쓰지 않고 내부 거절·진단 대상으로 처리한다.
- AC-6005: 저장된 eventId의 재전송은 다시 반영하지 않고, Device별 sequence 충돌은
  먼저 온 기록을 보존하며 충돌하지 않은 원본은 반영한다. 계정·Device 경계도 보호한다.
- AC-6006: 배치 내부 중복은 한 번만 반영하고 충돌 승자는 결정적이다.
- AC-6007: sequence가 누락되거나 미사용 낮은 sequence가 늦게 도착해도 연속성을
  기다리지 않고 저장하며, 관찰 시각 역행이 없는 입력의 타임라인을 재구성한다.
- AC-6008: DB 처리 장애 시 해당 채택 집합의 원본과 구간 변경을 모두 롤백한다.
- AC-6009: 동일 Device의 순서는 sequence로 정하고 다른 Device의 sequence를
  전역 순번으로 비교하지 않는다. 서로 다른 Device의 관찰 시각이 같으면
  deviceId·sequence·eventId 오름차순으로 정렬해 전송 순서와 무관한 결과를 얻는다.
- AC-6010: append·과거 삽입·배치 내 여러 과거 변경의 결과가 전체 재생과 같은
  관찰 의미를 가지며, 정상 경로는 증분 또는 영향 범위 재구성을 사용한다.
- AC-6011: 배치 처리 후에도 문맥 동등성·불투명 활동·명시적 공백·60초 병합·길이 없는
  구간·날짜 경계·내용 버전·라벨 적용성이 기존 계약대로 유지된다.
- AC-6012: 유효한 집중 세션 연결은 기존 소유권·시간·수집 상태 규칙대로 반영한다.
  Handler의 집중 세션 소유권·시간 검증에 실패하면 배치 전체의 원본·타임라인
  변경을 롤백하고 실패 원본을 보관한다.
- AC-6013: 일시 Handler 장애는 최초 포함 최대 5회와 1/2/4/8초 jitter 상한으로
  재시도하고 정상 중복·sequence 충돌에는 장애 재시도를 하지 않는다.
- AC-6014: Handler는 HTTP 요청과 독립된 메시지별 세션·트랜잭션을 사용하며,
  앱 시작·종료 시 Worker와 세션을 정리하고 미관찰 task 예외를 남기지 않는다.
- AC-6015: 클라이언트는 전송 가능한 상태에서 10초·200건·512 KiB 중 먼저 도달한
  조건으로 전송하며 Device별 한 배치만 전송 중으로 둔다. 수락 후 로컬 배치를
  제거하고 적체가 있으면 즉시 다음 배치를 전송한다.
- AC-6016: 응답 미확인 시 로컬 원본과 batchId·내용을 보존해 지정 backoff와
  Retry-After에 따라 재시도한다. 수락 전 명확한 413에는 원본을 보존한 재분할과
  새 batchId를 허용하며 단건 초과 원본을 절삭하지 않는다.
- AC-6017: 화면 열기·재활성화 즉시 조회하고 열린 화면은 초기 5초 간격으로 갱신한다.
  숨김 시 중단하며 겹치는 요청·오래된 응답을 방지하고 오류 시 기존 화면을 유지한다.
- AC-6018: 수락 경로의 API 설명과 실행 설정에서 accepted가 Kafka 발행 ACK를
  뜻하며 DB 처리 완료와 구분됨을 확인할 수 있다. 원본 보존·장애 내성의 범위는
  해당 환경의 Kafka 설정을 기준으로 설명한다.

- AC-6019: 같은 Device에서 sequence가 증가하는데 관찰 시각이 감소하면 배치
  전체의 원본·타임라인 변경을 롤백하고 실패 원본을 보관한다.

- AC-6020: 배치 처리 실패 후 같은 계정·Device의 후속 배치는 보류하고 다른
  Device·계정의 배치는 처리한다. 실패한 선두 배치의 재처리 성공 후 보류 배치를
  수락 순서대로 처리하며 실패·보류 원본의 보관량도 제한한다.

## 확인된 사실·가정·미결정

### 확인된 사실

수락 응답은 Kafka 발행 ACK 이후이며 DB 처리 완료는 기다리지 않는다.
동일 Device 내 관찰 순서는 sequence를 기준으로 하고 관찰 시각은 구간 경계에 사용한다.

### 미결정

Kafka의 실패·보류 저장과 복구, offset commit 경계는
[Kafka 전달 ADR](../adr/0006-deliver-activity-batches-through-kafka.md)에서 결정한다.

단건 원본 자체의 크기 초과 시 사용자 진단·복구 방법은 미정이다.
원본은 보존하며 내용을 절삭하지 않는다. 처리 속도·응답 지연의 수치 목표도 미정이다.
