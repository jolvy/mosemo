# 관찰부터 라벨 확정까지 이벤트스토밍

현재 탐색 범위에서 합의한 도메인 기록이다. 아래 사건은 비즈니스 흐름을 이해하기 위한 이름이며,
애플리케이션이 별도의 이벤트 메시지를 발행하거나 변경 이력을 저장한다는 뜻은 아니다.

## 범위

Device의 활동 관찰부터 사용자의 라벨 또는 미분류 확정까지 살펴본다. 제안 실패,
확정 라벨 정정, 늦게 도착한 관찰 기록으로 인한 구간 재구성도 포함한다.
라벨 목록 관리, 로그인, Device 등록, 라벨별 시간 집계는 이 흐름과 연결되는 지점에서
확장한다.

## 사건과 정책

| 계기 | 사건 | 정책 또는 결과 |
| --- | --- | --- |
| Device가 활동 레코드를 제출한다 | 활동 레코드가 처음 저장됨 | 관찰 시각을 기준으로 관찰 구간을 다시 계산한다. 같은 레코드의 재전송은 새 사건이 아니다. |
| 후속 관찰 또는 수집 상태를 반영한다 | 관찰 구간이 닫힘 *(도출)* | 닫힌 상세 관찰 구간만 라벨 제안과 확정의 대상이다. |
| 시스템이 대상 구간을 분석한다 | 라벨이 제안됨 / 제안에 실패함 | 제안이 없어도 사용자는 구간을 검토하고 직접 확정할 수 있다. 개별 시도와 임대는 이 보드에서 다루지 않는다. |
| 사용자가 라벨 또는 미분류를 확정한다 | 라벨이 확정됨 | 해당 관찰 구간 버전의 사용자 선택이 공식 값이다. |
| 사용자가 기존 확정값을 바꾼다 | 확정 라벨이 정정됨 | 최신 확정값이 현재 구간에 적용된다. |

## 늦은 관찰의 갈래

1. 과거에 관찰한 활동 레코드가 뒤늦게 처음 저장된다. 관찰 시각과 최초 저장 시각은
   별개의 시점이다.
2. 관찰 구간이 재구성된다 *(도출)*. 현재 구간의 내용 버전이 이전과 같은지 대조한다.
3. 버전이 바뀌면 **기존 라벨 제안이 현재 구간에 적용되지 않게 됨**을 기록한다.
   새로운 제안이 만들어지는 일은 별도 사건이다.
4. 이전 버전의 확정이 있으면 **관찰 구간 변경으로 재검토가 필요해짐**을 기록한다.
   기존 사용자 선택을 삭제하거나 새 구간에 조용히 이전한다는 의미는 아니다.

## 사건의 책임

현재 이 보드의 관찰·사용자 해석·제안·라벨 목록은 하나의 바운디드 컨텍스트
안에서 일관된 언어로 설명할 수 있다는 가설을 채택한다. 인증과 Device까지
같은 컨텍스트인지의 판단은 별도로 남긴다. 아래 구분은 현재 범위 안의 모듈
책임이며, 컨텍스트 분리를 뜻하지 않는다.

- 관찰 모듈은 Device가 보고한 원본 사실과 그로부터 도출한 현재 관찰 구간을 소유한다.
- 사용자 해석 모듈은 라벨 또는 미분류의 확정·정정과, 현재 관찰 구간에 기존 확정을
  적용할 수 있는지의 판단을 소유한다. 관찰 사실과 사용자 판단은 별개 모델이다.
- 제안 처리는 자체 실패·재시도·대체 상태를 가진 독립 모듈로 둔다. 제안은 사용자
  확정을 바꾸지 않는 보조 흐름이며, 현재는 별도 바운디드 컨텍스트로 정하지 않는다.
- 라벨 목록 모듈은 새 계정의 기본 라벨 종류와 중복 없이 준비하는 규칙을 소유한다.
  인증 흐름은 새 계정 생성에 맞춰 이를 호출하고 같은 트랜잭션으로 묶는다.
- 이 구분은 하나의 컨텍스트 안의 모듈 책임이다. 별도 서버, DB, 이벤트 전송 방식은
  도입하지 않는다.

## 패키지 구조에 적용할 결정

- 관찰 사실은 `activities/`에 두고, 라벨 관련 모듈은 `activity_labels/` 아래에 모은다.
- `activity_labels/catalog/`는 라벨 목록, `confirmations/`는 사용자 확정·정정,
  `proposals/`는 제안 생성과 처리 상태를 소유한다.
- `activity_labels/queries/`는 여러 모듈의 정보를 결합하는 사용자용 조회를 소유한다.
  구간 라벨 상태는 관찰 구간·유효한 확정·제안을 조합하고, 날짜별 라벨 타임라인은
  관찰 구간·유효한 확정·현재 라벨 이름을 조합한다. 현재 타임라인은 제안을 읽지 않는다.
- 라벨 목록처럼 한 모듈 안에서 끝나는 조회는 해당 모듈에 둔다. 확정 모듈이 응답
  조합을 위해 제안 모듈에 의존하지 않도록 한다.
- 공개 `/activities/...`와 `/labels` 경로 및 operation ID는 유지한다.
- 패키지 재배치는 바운디드 컨텍스트 분리를 뜻하지 않는다.
- 상위 `activity_labels/service.py`는 확정 요청의 트랜잭션과 계정별 잠금을 관리한다.
  `confirmations/`의 검증·저장과 `queries/`의 응답 조합을 같은 세션·트랜잭션 안에서
  호출한다. 하위 모듈은 그 요청 안에서 별도 트랜잭션을 시작하거나 커밋하지 않는다.
- 배치 확정은 전체 항목을 검증한 뒤 저장하는 순서를 유지한다. 한 항목의 실패는
  전체 요청을 롤백한다. 동일 요청의 재시도와 단일 구간 정정의 기존 의미도 유지한다.
- 제안 작업자는 선점과 결과 반영에 각각 짧은 트랜잭션을 사용하고, AI 호출은
  트랜잭션과 계정 잠금 밖에서 수행하는 현재 흐름을 유지한다.

## 파일 재배치 계획

아래는 합의한 책임을 코드에 적용하기 위한 계획이며 아직 구현한 구조가 아니다.
`__init__.py`는 필요한 패키지에 두되 아래 목록에서는 생략한다.

```text
src/mosemo/
  activities/
    versioning.py
    ...                       # 기존 관찰 코드
  activity_labels/
    router.py                 # /activities 라벨 API
    schemas.py                # 기존 공개 요청·응답 계약
    service.py                # 요청별 트랜잭션과 모듈 호출
    catalog/
      models.py
      repository.py
      router.py               # /labels API
    confirmations/
      models.py
      repository.py
      service.py              # 확정 적격성·버전·선택·배치 검증과 저장
    proposals/
      models.py
      repository.py
      service.py              # 스캔·선점·결과 반영
      examples.py             # 제안 입력에 맞는 확정 사례 검색
      suggestions.py          # 기존 제안기 계약과 AI 구현
      worker.py
    queries/
      repository.py           # 확정과 현재 라벨 이름 등 조회 결합
      service.py              # 구간 상태와 날짜별 타임라인 응답 조합
```

| 현재 파일·책임 | 이동할 위치 |
| --- | --- |
| `labels/router.py` | `activity_labels/router.py` |
| `labels/catalog_router.py` | `activity_labels/catalog/router.py` |
| `labels/schemas.py` | `activity_labels/schemas.py`; 기존 스키마 이름과 JSON 필드를 유지한다. |
| `labels/models.py`의 Label과 기본 라벨 목록 | `catalog/models.py` |
| `labels/models.py`의 확정 모델 | `confirmations/models.py`; 기존 도메인 동작을 유지한다. |
| `labels/models.py`의 제안 모델·상태·시도 결과 | `proposals/models.py` |
| `labels/repository.py` | 목록·확정·제안의 저장 책임과 사용자용 결합 조회를 각 패키지로 분리한다. |
| `labels/service.py`의 확정 검증과 저장 | `confirmations/service.py`; 제안 상태를 읽어 응답을 만드는 책임은 제외한다. |
| `labels/service.py`의 트랜잭션과 요청 순서 | 상위 `activity_labels/service.py` |
| `labels/service.py`의 상태·타임라인·확정 응답 조합 | `queries/service.py` |
| `labels/service.py`의 `segment_version` | `activities/versioning.py`; 계산 알고리즘과 결과를 유지한다. |
| `labels/proposals.py`의 스캐너·처리기 | `proposals/service.py` |
| `labels/proposals.py`의 확정 사례 검색 | `proposals/examples.py`; 제안 입력을 구성하는 내부 검색으로 둔다. |
| `labels/suggestions.py`, `labels/worker.py` | `proposals/suggestions.py`, `proposals/worker.py` |

### 의존 방향

- API 라우터는 상위 애플리케이션 서비스를 호출한다. 목록 라우터의 조회는 목록
  모듈 안에서 처리한다.
- 상위 서비스는 확정과 사용자용 조회를 조율한다. 하위 모듈은 상위 서비스를
  import하지 않는다.
- 확정은 관찰 구간과 라벨 목록에 의존한다. 제안·사용자용 조회에는 의존하지 않는다.
- 제안은 관찰 구간, 라벨 목록, 확정 이력을 읽는다. 사용자용 조회에는 의존하지 않는다.
- 사용자용 조회는 관찰·목록·확정·제안을 결합한다. 다른 하위 모듈이 사용자용 조회에
  역으로 의존하지 않는다.
- 관찰 패키지는 라벨 관련 패키지를 import하지 않는다. 구간 내용 버전은 관찰 쪽에
  두어 확정·제안·조회가 같은 계산을 사용하게 한다.

### 적용 순서와 검증

1. 모델과 저장소의 소유권을 분리하고 모든 모델을 Alembic에 등록한다. 테이블·컬럼·
   제약 조건·기존 마이그레이션은 유지한다.
2. 확정·제안·사용자용 조회의 코드를 분리하고 요청별 트랜잭션을 상위 서비스로 모은다.
3. API와 의존성 주입, 인증의 기본 라벨 호출, 작업자 실행 경로, 테스트 import를 갱신한다.
   `poe label-worker` 명령은 유지한다.
4. 현재 HTTP와 PostgreSQL 통합 테스트로 직접 확정, 제안과 다른 선택, 배치 전체 롤백,
   재전송, 늦은 관찰 및 제안 처리 중 확정·구간 변경을 확인한다. 빠진 시나리오가 있으면
   해당 경계의 테스트를 추가한다.
5. OpenAPI를 내보내 기존 스냅샷과 동일한지 확인한다. 경로·operation ID·JSON·오류·태그·
   공개 스키마는 유지한다.
6. Ruff 검사와 포맷 확인, ty, 빌드, 전체 테스트, diff 검사를 실행하고 실제 결과를 보고한다.

## 라벨 목록에서 연결되는 사건

라벨은 현재 관찰 활동의 의미를 분류하는 계정별 목록이다. 아래의 구현 상태는
이벤트스토밍 사건의 중요도와 별개다.

| 사건 | 현재 상태 | 제안·확정에 미치는 영향 |
| --- | --- | --- |
| 기본 라벨이 생성됨 | 계정 최초 로그인 시 구현됨 | 새 계정에 선택 가능한 라벨이 생긴다. |
| 사용자 라벨이 생성됨 | PRD에 정의됨, 공개 쓰기 API는 아직 없음 | 이후 제안과 확정의 후보가 된다. |
| 라벨 이름이 변경됨 | PRD에 정의됨, 공개 쓰기 API는 아직 없음 | 과거 확정의 표시 이름에도 현재 이름이 반영된다. |
| 라벨이 보관됨 | PRD에 정의됨, 공개 쓰기 API는 아직 없음 | 과거 확정은 남지만 새 제안·확정의 후보에서 제외된다. 기존 미확정 제안은 기록상 보일 수 있으나 그대로 확정할 수 없다. |
| 라벨이 복원됨 | [이슈 #34](https://github.com/jolvy/mosemo/issues/34)에 정의됨, 공개 쓰기 API는 아직 없음 | 보관된 라벨과 같은 이름으로 생성을 요청하면 기존 라벨의 정체성을 유지한 채 다시 사용 가능한 후보가 된다. |

## 현재 범위 밖에서 검토할 경계

- 인증과 Device의 모델이 현재 범위와 별도 컨텍스트를 필요로 하는지.
