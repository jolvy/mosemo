# 활동 분석 골든 데이터셋 (외부 정답)

[지표 명세](activity-analytics-metrics.md)의 C1~C7 값이 실제 하루와 맞는지 사람이 만든 정답으로
확인한다. 사용자가 하루를 기록하면 그날의 기대 결과를 골든 파일로 고정하고, 비교 도구가 덤프에서
계산한 값과 값마다 비교한다. 허용 오차는 측정 전인 2026-11-11에 고정했다.

## 정답의 세 부류

사람은 초 단위 전환을 일지로 셀 수 없다. 실제 6일 기록의 관찰 간격 중앙값은 5.5초이고 C2 1,527회 중
55%가 5초 미만 왕복이다(지표 명세 Q7·M3). 그래서 정답을 세 부류로 나누고 섞지 않는다.

| 부류 | 범위 | 기대값을 만드는 방법 | 잡는 오류 | 잡지 못하는 오류 |
| --- | --- | --- | --- | --- |
| **일지 정답** | 통제 구간 S1·S2 | 사용자가 정해진 시나리오대로 행동하고 시각을 일지에 적는다. 기대값은 시나리오에서 사람이 손으로 계산해 측정 전에 고정한 값(아래 기대값 표)이며 도구가 계산하지 않는다. | 수집·projection·정의·참조 계산 어디서든 생긴, 실제 행동과 다른 결과 | 시나리오에 없는 상황 |
| **기계 정답** | 기록일 하루 전체(로거 실행 구간) | Mosemo와 따로 실행하는 OS 앱 활성화 로거의 기록. 사람도 Mosemo도 값을 만들지 않는다(「기계 정답」 절). | 하루 전체의 앱 단위 수집 누락·지연·잘못된 전환, projection 규칙과 지표 정의가 만든 차이(층별로 나눔) | 사이트·창·라벨·세션 값, 로거와 Mosemo가 같이 받는 OS 알림 자체의 누락 |
| **원본 사실 정답** | 기록일 하루 전체 | 덤프에서 계산한 값을 사람이 검수한 뒤 고정한다(`golden.py freeze`). 사람은 값을 만들지 않고, 일지의 사용 시작·끝과 수집을 끈 시각이 덤프의 구간·수집 공백과 맞는지 검수만 한다. | 고정 이후의 회귀(참조 계산 변경, 4단계 구현과 참조 계산의 차이) | 참조 계산 자체의 정의 오류(일지 정답과 명세 경계 사례가 잡는다) |

라벨의 정답은 사용자의 확정 자체다. 일지 정답에서는 시나리오가 정한 확정 행동(S2 확정 표)이 정답이고,
원본 사실 정답에서는 덤프의 확정 레코드가 입력이다.

창 제목·URL(C6 진입 문맥), 라벨과 집중 세션(C3~C7)을 줄 수 없다. 앱 미확인·불투명·전체 관찰 시간은 Mosemo
수집 상태와 개인정보 필터가 정하는 값이라 OS 기록에 대응값이 없다. C2의 기계 정답은 사용 대상을 앱으로 접어
같은 C2 정의(맞닿음·공백·침묵·0초 구간·앱 미확인 제외)를 적용한 앱 단위 전환이며, `Chrome youtube.com →
Chrome github.com`처럼 앱 안의 사이트 전환은 덮지 않는다.

C3~C6과 세션별 C7은 원본 사실 정답을 두지 않는다. 기록일에는 S2 외의 집중 세션을 만들지 않으므로
하루 전체의 세션 값이 S2 값과 같다.

### 허용 오차 근거

고정 정책: `version` 2026-11-11, `journal_resolution_s` 60, `capture_lag_s` 30. 골든 파일의 정책이
이 값과 다르면 비교 도구가 실패한다(`PRE/policy`). 측정 결과를 본 뒤 허용 오차를 바꾸지 않는다.
바꿔야 하면 다음 기록일 전에 새 version과 근거를 이 절에 먼저 쓴다.

| ID | 허용 오차 | 근거 |
| --- | --- | --- |
| G0 | 0 | 횟수·순서·식별자·참거짓은 시나리오가 정하며 시각 해상도와 무관하다. 시나리오의 단계는 2분 이상 떨어져 있고 세션·일시중지 경계에서 1분 이상 떨어져 있어 1분 미만의 시각 오차가 작업 구간 안팎을 바꾸지 못한다. 0초여야 하는 시간(불투명·앱 미확인·미관찰)은 시나리오 앱이 상세 문맥이고 30초 하트비트가 60초 침묵 규칙보다 짧기 때문이다. 원본 사실 정답은 같은 덤프에서 결정적으로 계산하므로 0이다. |
| G1 | 연속 구간 수 × 90초 | 일지는 행동 순간에 시계에 보이는 분(HH:MM)을 적으므로 실제 시각은 기록 시각부터 60초 안에 있고, 두 기록 시각의 차인 구간 길이는 60초 미만으로 어긋난다. 관찰 경계는 전환 즉시 스냅샷을 만들고 놓쳐도 30초 하트비트로 잡으므로(활동 관찰 PRD) 0~30초 늦고, 구간 양 끝의 지연 차이는 30초 이내다. 구간마다 오차가 독립이므로 값을 이루는 연속 구간 수만큼 더한다. |
| G2 | 90초 | 한 시각(전환 시각, 이탈 시작·끝)은 기록 시각보다 0~60초 늦은 행동과 0~30초의 관찰 지연이 더해져 기록 시각부터 90초 안에 관찰된다. 세션 시작·종료는 클라이언트가 보낸 시각이고 일시중지는 일지 시각을 그대로 입력으로 쓰므로 이 오차에 더하지 않는다. |

측정 전 가정: 관찰 지연 상한 30초는 PRD 계약이다. 실제 6일 기록의 관찰 간격 99백분위는 45.8초이고
45~75초 간격이 42쌍 있어(지표 명세 Q7) 하트비트가 늦은 순간이 있다. 기록일 잔차가 90초를 넘으면 허용
오차를 넓히지 않고 수집 지연 문제로 보고한다.

## 통제 구간 시나리오

역할: `W` 작업 앱(편집기), `M` 메신저, `T` 터미널, `F` 파일 관리자, `Chrome`, `Firefox`. 라벨 `L1`은 세션
라벨(예: 코딩), `L2`는 다른 라벨(예: 여가). 시각은 시작 시각부터의 분이며 시계의 분이 바뀌는 순간에
행동한다. 각 통제 구간은 화면 잠자기에서 깨우며 시작하고 화면 잠자기로 끝나므로 앞뒤에 수집 공백이 생긴다.

**S1 사용 대상 구간(C1·C2, 15분)**: 0 깨우고 `W` → 5 Chrome `youtube.com` → 7 같은 탭에서 다른
`youtube.com` 페이지 → 9 Chrome `github.com` → 11 Firefox `github.com` → 13 `W` → 15 화면 잠자기.
같은 사이트 안 페이지 이동(7분)과 다른 브라우저의 같은 사이트(11분)는 전환이 아니다.

**S2 집중 세션(C3~C7, 35분)**: 0 깨우고 `W`, 세션 시작(라벨 `L1`) → 8 Chrome `youtube.com` → 11 `M` →
13 Chrome `youtube.com` → 15 `W` → 20 일시중지 → 21 `M` → 23 `W` → 26 재개 → 28 `T` → 30 `F` → 32 `W` →
35 세션 종료, 화면 잠자기. 세션 분석 시간은 29분이다.

S2 확정(세션 종료 후, 구간 시작 분 기준): 0·15·23·32분 `W` → `L1`, 8·13분 Chrome과 11분 `M` → `L2`,
30분 `F` → 미분류, 21분 `M`과 28분 `T`는 확정하지 않는다(판정 대기).

## 기계 정답(OS 로거)

### 원천과 독립성

산출물 폴더의 `logger/activation_logger.swift`는 `NSWorkspace.didActivateApplicationNotification`과 화면·
시스템 잠자기/깨우기·세션 전환 알림을 JSON Lines(벽시계 시각, 가동 시간, 사건, bundleId, pid)로 남긴다.
창 제목·URL을 읽지 않아 접근성·자동화 권한이 필요 없고, 이 Mac에 있는 Swift 6.0.3(`swiftc`)으로 추가 설치
없이 빌드된다.

독립성의 범위: 로거는 Mosemo 클라이언트의 코드·큐·개인정보 필터·전송·서버·projection과 독립이다. 그러나
Mosemo 클라이언트(`mosemo-macos` `cd4f109`, `WorkspaceObserver.swift`)도 같은 OS 알림을 받고 0.5초 주기
폴링(`CollectorViewModel.swift`의 `pollTimer`)을 함께 쓴다. 그래서 OS 알림 자체가 빠지는 경우는 둘이 같이
놓친다. 이 공통 원인은 기계 정답이 잡지 못한다.

### 오차 예산과 판정 기준

사전 등록 SHA-256: `590c087ecc23d98f0fea59c4dc698f3622fc72f6a76608f18f33dad691437545`

판정 방법과 기준은 산출물 폴더의 `prereg.json`에 기록일 전, 데이터를 보기 전에 고정했다. 일지 정답의 허용

오차 예산(L = 1.05초):

- 시계 차이 0: 로거와 클라이언트가 같은 Mac의 벽시계(`Date()`)를 쓴다(클라이언트 코드 확인). 시계가
  보정되어도 둘이 같이 움직인다.
- 로거 지연 0.05초 이하: 최소 재현에서 로거는 `lsappinfo` 폴링보다 31~44ms 먼저 기록했다(4회, 측정).
- 클라이언트 관찰 지연 1.0초 이하: 같은 OS 알림을 즉시 받고, 놓쳐도 0.5초 폴링이 잡는다(코드 확인). 처리
  지연 0.5초는 측정 전 가정이다.
- 매칭 창 [−0.5초, +1.05초]: 위쪽은 클라이언트 지연과 로거 지연의 합이다. 아래쪽 −0.5초는 두 프로세스가 같은
  알림을 처리하는 순서의 흔들림으로, 측정 전 가정이다.
- 60초 침묵: 클라이언트가 30초마다 관찰을 만들면 깨어 있는 동안에는 생기지 않아야 한다. 생기면 L2 차이로
  드러난다(10월 기록에는 45~75초 간격이 42쌍 있었다).

| ID | 방법 | 기준 | 근거 |
| --- | --- | --- | --- |
| M1 | C1 앱 시간 Bland–Altman. 단위는 (bundleId, 계정 시간대 1시간 칸)이고 차이는 Mosemo C1 − OS 시간(초) | 평균 편차의 절댓값 ≤ L. 95% 일치 한계(평균 ± 1.96 SD) ⊂ ±L × P95(칸별 OS 경계 수). 모든 칸에서 차이의 절댓값 ≤ L × 그 칸의 OS 경계 수(최소 1) | 칸 안 한 앱의 차이는 나간 경계 지연의 합 − 들어온 경계 지연의 합이다. 경계마다 지연은 L 이하이므로 칸 차이는 L × 경계 수 이하이다. 들어온 경계와 나간 경계의 수는 칸마다 1 이하로 차이 나므로 지연이 같은 분포면 칸 차이의 기댓값은 L 이하이다. |

### 층별 비교 도구

산출물 폴더의 `machine.py`. 작업 트리에서 `uv run --locked python <산출물>/machine.py <logger.jsonl> <덤프>
<기록일> <시간대>`로 실행한다.

| 층 | 비교 | 차이의 뜻 |
| --- | --- | --- |
| L1 | 로거 전환 ↔ `activity_records`의 관찰 사이 앱 변화(매칭 창), 로거 앱 시간 ↔ 관찰부터 다음 레코드까지의 시간 | 수집 누락(31초 안에도 없음), 지연 초과(1.05초 초과 31초 이하), 잘못된 전환(OS에 없음) |
| L2 | 관찰 사이 앱 변화 ↔ 맞닿은 구간 사이 앱 변화(같은 시각), 관찰 시간 ↔ 구간 시간 | projection 규칙(60초 침묵, 수집 공백) |
| L3 | 구간 사이 앱 변화 ↔ C2 앱 단위 전환, 구간 시간 ↔ C1 앱 시간 | 지표 정의(앱 미확인·불투명 제외, 날짜 경계) |

종단 기준(M1·M2)에서 실패한 전환과 칸마다 차이가 처음 생긴 층을 함께 보고한다.

모의 검증(`check_step3.py`): 일지 정답 모의와 같은 합성 하루를 「실제 행동」으로 두고 OS 로거 기록을 만든 뒤,
Mosemo 쪽만 바꿔 비교한다.

- 양성: 지연 0, 지연 0~1.0초. 둘 다 불투명·앱 미확인 구간을 제외 규칙으로 넘기며 통과한다.
- 음성: 12초 머문 앱을 놓침(M2 recall, L1 수집 누락), 전환을 5초 늦게 관찰(L1 지연 초과·잘못된 전환),
  OS에 없는 2초 전환(M2 precision, M1 칸, L1), 하트비트 100초 누락(M1 칸, L2), 5초 미만 체류 전환을 빼는
  C2 구현(M2 recall, L3), 칸 앞 30분을 더하는 C1 구현(M1 칸, L3). 모두 기대한 층의 이유로 실패한다.

M1 칸 기준은 전환이 많은 칸에서 느슨하다(경계 수에 비례). 12초 누락이나 5초 지연은 M1 칸 기준을 넘지 않을
수 있으며 M2가 잡는다.


- 사전 검사: 형식, 사전 등록 SHA-256(`PRE/prereg`), 고정 정책, PSL(`PRE/psl`), 사이트 미정(`PRE/site`), 모든 값의 정답 존재(`PRE/coverage`), 작성자·작성 시각, 원본 사실 검수
  기록, 통제 구간마다 그 날짜에 관찰이 있는지(`PRE/date`), 일지와 맞는 완료 세션이 1개이고 라벨이
  같은지(`PRE/session`, 세션 시작이 일지 분 안).
- 값마다 기대값·실제값·차이·허용 오차와 통과/실패를 내고 하나라도 실패하면 종료 코드 1이다.
- 일시중지 구간은 서버가 아직 저장하지 않으므로(FR-25 미구현) 일지 시각을 입력으로 쓴다.
- 사이트는 `psl.py`가 공개 접미사 목록(PSL) 알고리즘(예외 규칙 우선, 가장 긴 규칙, 없으면 `*`, ICANN과
  PRIVATE 절 모두)으로 계산한다. 국제화 도메인은 라벨마다 IDNA(표준 라이브러리, IDNA 2003)로 바꾼다. 골든
  파일의 `psl`에 PSL 파일 경로와 SHA-256을 적고 다르면 `PRE/psl`로 실패한다. 이전의 「마지막 두 라벨」 근사는
  `example.co.kr`을 `co.kr`로, `user.github.io`를 `github.io`로 만들어 폐기했다.
- eTLD+1이 없는 URL은 FR-2(2026-11-12 결정, 지표 명세 D7)대로 `http`·`https`면 호스트 그대로(포트 제외),
  그 밖의 URL과 호스트 없는 URL은 브라우저 앱이다. PSL 없이 계산하면 근사하지 않고 `?no_psl`을 사용 대상으로
  두며 `PRE/site`가 실패한다.
- `INFO/work_seconds`: S2의 (종료 − 시작 − `workSeconds`)와 일지의 일시중지 합의 차이를 판정 없이 보고한다.

PSL 최소 재현: 시험용 목록(`psl_fixture.dat`, 규칙 11개)과 이 Mac에 있던 전체 목록 사본(Arc 브라우저 확장의
`effective_tld_names.dat`, VERSION 2025-10-13) 두 가지로 같은 결과를 얻었다.

| --- | --- |
| `https://m.youtube.com/watch` | `youtube.com` |
| `https://www.example.co.kr/` | `example.co.kr` |
| `https://user.github.io/x` | `user.github.io` |

실패하는지 확인한다.

## 기록일 준비

서버·DB:

1. 로컬 DB를 백업 없이 현재 마이그레이션까지 올린다(결정 1). 지금은 2026-10-07에 멈춰 있다. 분석 도구는
   DB가 아니라 `~/mosemo-dump/*.csv`를 읽으므로 10월 기록은 덤프로 남는다.
2. 작업 트리의 서버를 실행하고 클라이언트가 그 서버로 보내는지 확인한다.
3. 라벨 `L1`·`L2`가 있는지 확인한다.

클라이언트·Mac:

4. Chrome 관찰이 `web.kind = browser`와 URL `captured`로 오는지 확인한다(Chrome 자동화 권한). 현재
   클라이언트는 Safari를 브라우저로 판정하지 않으므로 S1의 다른 브라우저 단계는 Firefox로 한다(결정 2).
   Firefox URL은 접근성 권한으로 주소창 값을 읽어 수집한다(`mosemo-macos` `cd4f109`,
   `ApplicationWindowContextClient.swift`).
5. 접근성 권한을 허용해 창 제목과 Firefox 주소창 URL을 수집한다(결정 3).
6. 리허설: 기록일 전에 S1을 5분으로 줄여 한 번 해 보고, 화면을 깨울 때와 잠금 해제 때 무엇이
   관찰되는지(잠금 화면이 앱으로 관찰되는지) 덤프로 확인한다. 2026-11-13 리허설 결과:
   - Firefox URL은 `github.com/explore`처럼 scheme 없이 왔다. 지표 명세 D9(scheme 없는 URL은 비웹
     scheme이 아니면 `https://`를 붙여 해석)로 해결해 S1의 사이트 검사에 그대로 쓴다.
   - 화면 잠자기·잠금 화면이 어떻게 관찰되는지는 확인하지 못했다. 기록일 전에 이 부분만 다시
     리허설한다.
   - 로거와 Mosemo를 같이 켜고 비교했을 때 약 3초 머문 Chrome 활성화 1건이 Mosemo 관찰에 없었고,
     1건은 Mosemo가 약 2초 늦게 관찰했다. 기계 정답 판정 기준 M2(recall = 1, 매칭 창 +1.05초)로는
     두 건 모두 실패에 해당한다. 원인 층은 기록일의 층별 비교(L1)로 확인한다.
7. 로거를 빌드한다: `cd <산출물>/logger && swiftc -O activation_logger.swift -o activation_logger`.
   공식 PSL(`https://publicsuffix.org/list/public_suffix_list.dat`)을 한 번 내려받아(결정 6)
   `~/mosemo-golden/<기록일>/`에 두고 골든 파일의 `psl`에 경로·SHA-256을 적는다.
8. 방해 금지 모드를 켜고, Chrome에 `youtube.com`, Firefox에 `github.com` 탭을 미리 연다. `W`·`M`·`T`·`F`로
   쓸 앱을 정해 골든 파일의 `roles`에 적는다(`M`은 불투명으로 수집되지 않는 앱).

기록일:

9. 하루 첫 사용 전에 로거를 켠다: `<산출물>/logger/activation_logger ~/mosemo-golden/<기록일>/logger.jsonl`
   (터미널 한 탭을 그대로 둔다). 다음 날 0시가 지나고 마지막 사용을 끝낸 뒤 Ctrl+C로 끈다. 로거가 그날
   Mosemo 관찰을 모두 덮지 못하면 `PRE/logger_coverage`가 실패한다. 로거를 켜고 끄는 터미널 조작 자체도
   앱 전환이며 두 기록에 똑같이 남는다.
10. 일지의 하루 칸을 채운다. S1·S2를 시나리오대로 하고 화면 잠자기로 끝낸다.
11. S2 일시중지와 재개 때 Mosemo 타이머에 보이는 작업 시간(분:초)과 시계의 분을 함께 적는다. 다음 날
    `INFO/work_seconds`가 서버의 (종료 − 시작 − `workSeconds`)를 일지의 일시중지 합과 비교한다. 일지 분
    단위라 일시중지 하나에 60초 미만, `workSeconds` 내림에 1초 미만의 분해능이 있다. 타이머 표시값은
    일시중지 시작 시각(세션 시작 + 표시값)을 초 단위로 다시 구하는 데 쓴다(일시중지가 하나일 때).
12. S2 종료 후 1분 이상 지나 화면을 깨우고 Mosemo에서 S2 확정 표대로 라벨을 확정한다. 확정 후 S2
   구간이 다시 구성되면 확정이 무효가 되므로 덤프 전에 확정이 남아 있는지 다시 본다.
13. 그날 S2 외 집중 세션을 만들지 않는다.

다음 날:

14. 클라이언트 전송이 끝났는지 확인한다. 10월 기록은 수신 지연 중앙값이 41.6시간이었다(지표 명세 Q6).
15. `dump_activity.sh dump <계정> <기록일>T00:00:00+09:00 <다음 날>T00:00:00+09:00 ~/mosemo-golden/<기록일>/dump`
16. 일지로 골든 파일을 만든다(`scenario.build_golden`에 시작 시각·역할). 일지의 다른 점과 사고는
    작성자가 기대값을 손으로 고치고 그 이유를 `checks[].note`에 적는다.
17. `compare`로 일지 정답을 비교하고, 검수 후 `freeze`로 원본 사실 정답을 고정한 뒤 다시 `compare`한다.
18. `machine.py`로 기계 정답을 비교한다.

## 측정 전 가정과 확인하지 못한 것

- 관찰 지연 30초 상한(G1·G2)은 PRD 계약이며 실제 클라이언트에서 측정하지 않았다.
- 화면 잠자기는 실제 10월 기록에서 `screen_sleep` suspended·active로 남았다(23건). 화면 잠금은 그런 사유가
  없어 통제 구간 경계로 쓰지 않는다. 깨운 직후 잠금 화면이 어떻게 관찰되는지는 2026-11-13 리허설에서도
  확인하지 못했다(준비 6, 다시 리허설 필요).
- 클라이언트의 일시중지 동작과, 일시중지 중 관찰에 `focusSessionId`를 붙이지 않는지는 실제 기록으로
  확인하지 못했다. 확인되면 일지의 일시중지 시각을 원본으로 교차 확인할 수 있다.
- 클라이언트 관찰 처리 지연 0.5초와 매칭 창 아래쪽 −0.5초는 측정 전 가정이다(기계 정답 절). 로거 지연은
  4회만 측정했다. 2026-11-13 리허설에서 약 2초 늦은 관찰 1건과 약 3초 활성화 누락 1건을 보았다(준비 6).
  이 가정을 넘는 사례이므로 기록일 결과에서 같은 일이 반복되는지 본다.
- 로거의 화면·시스템 잠자기/깨우기 알림은 2026-11-13 리허설에서도 확인하지 못했다(다시 리허설 필요).
- 로거가 하루 종일 켜져 있을 때의 안정성(앱 낮잠 App Nap, 터미널 종료)은 확인하지 못했다.
- 일지 정답의 G1·G2는 관찰 지연 30초(PRD)를 쓴다. 클라이언트 코드는 0.5초 폴링이라 이 값은 보수적이다.
  고정한 정책이므로 바꾸지 않는다.
- PSL 결과는 IDNA 2003 기준이다. IDNA 2008과 다른 문자(예: `ß`)가 있는 호스트는 확인하지 않았다.
- Firefox 주소창 값은 scheme 없이 온다(2026-11-13 리허설, 준비 6). 클라이언트는 주소창 값을 그대로 URL로
  보내며 분석이 D9로 해석한다.

## 결정 (2026-11-12)

기록일 준비 질문 7개를 다음과 같이 정했다.

1. 로컬 DB: 기존 `mosemo` DB를 백업 없이 현재 마이그레이션까지 올린다. 10월 기록은 덤프로 보존되어 있다.
2. S1의 다른 브라우저 단계는 Safari 대신 Firefox로 한다. 현재 클라이언트는 Safari를 브라우저로 판정하지
   않는다.
3. 기록일에 접근성 권한을 허용한다.
4. 일지 시각은 분 단위로 적는다(현재 허용 오차의 근거).
5. eTLD+1이 없는 URL: `http`·`https`면 호스트 그대로(포트 제외)가 사이트, 그 밖의 URL과 호스트 없는 URL은
   브라우저 앱이다(FR-2, 지표 명세 D7).
6. 공식 PSL을 기록일 준비 때 한 번 내려받아 경로와 SHA-256을 골든 파일에 고정한다.
7. Safari 방문 기록은 쓰지 않으며 터미널에 전체 디스크 접근 권한을 주지 않는다.
