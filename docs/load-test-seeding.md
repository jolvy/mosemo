# 부하 테스트 시드 적재

`scripts/seed_load.py`는 부하 테스트용 대용량 데이터를 결정적으로 생성해 `DB_*` 설정의 PostgreSQL에 적재한다. 마이그레이션 head가 적용된 DB가 대상이다. 데이터 삭제 기능은 없으며, 시드 데이터를 지우려면 DB를 다시 만든다.

## 사용법

```sh
uv run --locked --env-file "$ENV_FILE" python scripts/seed_load.py \
  --users N --confirm-host "$DB_HOST" --end-date 2026-11-07 [--account-id UUID] [--seed 1] [--days 365]
```

| 인자 | 필수 | 의미 |
| --- | --- | --- |
| `--users` | 예 | 목표 유저 수(1 이상). `--account-id`가 있으면 본인 계정 1명과 더미 N-1명, 없으면 더미 N명이다. |
| `--confirm-host` | 예 | env 파일의 `DB_HOST`와 정확히 같아야 실행한다. |
| `--end-date` | 예 | 생성 기간의 마지막 날(ISO 날짜). 기본값이 없다. 실행일보다 이전 날짜를 쓴다. |
| `--account-id` | 아니요 | 데이터를 붙일 본인 계정 ID. |
| `--seed` | 아니요 | 생성 난수 seed. 기본 1. |
| `--days` | 아니요 | 생성 기간 일수(마지막 날 포함). 기본 365. |

- 생성 기간은 `--end-date`로 끝나는 `--days`일이다. 단계별 재실행에서 같은 `--end-date`·`--seed`·`--days`를 쓰면 같은 데이터(ID 포함)가 나온다.
- 건너뛰기 판정은 seed와 유저만 보고 기간은 보지 않는다. 같은 seed로 `--end-date`나 `--days`를 바꿔 재실행하면 기존 유저는 건너뛰고 새 유저만 다른 기간으로 적재되므로, 한 DB에서는 기간을 바꾸지 않는다.
- 더미 유저 i의 계정은 `provider = KAKAO`, `provider_subject = load-seed-{seed}-{i:06d}`(6자리)이다. seed가 다르면 별도 더미 계정이 된다.
- 유저는 순서대로 하나씩, 유저마다 한 트랜잭션으로 적재한다. 이 seed의 유저 기기가 이미 있으면 그 유저는 건너뛴다. 그래서 `--users`만 늘려 다시 실행하면 새 유저만 추가된다.
- 한 유저 적재가 실패하면 그 유저를 롤백하고 즉시 멈춘다(종료 코드 1). 앞서 커밋된 유저는 남으며, 같은 인자로 다시 실행하면 실패한 유저부터 이어서 적재한다.
- 같은 대상에 두 프로세스를 동시에 실행하지 않는다.
- 끝나면 적재 대상 테이블에 `ANALYZE`를 실행하고, 적재·건너뛴 유저 수, 테이블별 `pg_total_relation_size`, `pg_database_size`(`(database)` 행)를 바이트 단위 표로 출력한다(종료 코드 0).
- `native_auth_codes`와 토큰은 만들지 않는다. 부하 테스트 토큰은 직접 로그인해 얻는다.

## 안전 가드

- `--confirm-host`가 `DB_HOST`와 다르면 DB에 연결하지 않고 종료 코드 2로 끝난다. 다른 DB(운영 등)에 실수로 적재하지 않도록 매번 대상 호스트를 직접 적는다.
- 인자 오류(`--users` 0 이하, 필수 인자 누락, 날짜 형식 오류)도 DB에 연결하지 않고 종료 코드 2로 끝난다.
- `MOSEMO_ENV`는 검사하지 않는다.

## 본인 계정 준비

`--account-id`에는 Kakao 로그인으로 만든 본인 계정을 쓴다. 로그인은 해도 되지만, 활동 수집 레코드가 없는 계정이어야 한다. 시드는 계정과 라벨을 만들지 않고, 계정의 보관되지 않은 라벨을 쓰며, 시드 전용 기기를 하나 추가해 데이터를 붙인다.

쓰기 전에 다음 순서로 검사하고, 종료 코드 2면 아무것도 쓰지 않는다.

1. 계정이 없으면 종료 코드 2.
2. 이 seed의 본인 계정 기기가 이미 있으면 그 유저는 건너뛴다.
3. 계정 기기의 활동 레코드나 타임라인 구간이 하나라도 있거나, 보관되지 않은 라벨이 없으면 종료 코드 2. 레코드 없는 기존 기기는 허용한다.

한 seed로 적재한 본인 계정은 다른 `--seed`로 다시 적재할 수 없다(이미 레코드가 있어 종료 코드 2). 단계별 재실행에서는 같은 seed를 쓴다.

서비스는 계정의 모든 기기 레코드를 합쳐 타임라인을 투영하므로 기존 활동 데이터와 섞으면 타임라인과 라벨 버전이 어긋난다. 그래서 기존 데이터가 있는 계정은 거부한다.

## 분포 가정

모든 유저는 1년치 헤비 유저이며, 아래 수치는 부하 데이터용 고정 가정이다(Asia/Seoul 기준, 매일 같은 규칙). 바꿀 필요가 생기면 스크립트 상수를 고친다.

- 수집 상태: 09:00 active → 12:00 suspended(`screen_locked`) → 13:00 active → 21:00 suspended(`system_sleep`). 기간 마지막 날은 21:00 suspended 없이 21:00 관찰로 끝나 `ended_at`이 없는 활동 구간이 하나 남는다.
- 관찰 간격: 문맥이 같으면 30초, 문맥이 바뀌는 관찰은 직전 관찰 후 5~30초 균등 난수. 관찰마다 문맥이 바뀔 확률 0.2.
- 문맥: 80% detailed, 20% opaque. detailed는 고정 앱 20개 중 선택하고, 브라우저 앱이면 탭 제목·URL을 고정 풀에서 고른다. detailed 관찰의 5%는 창 `absent`, 창 `unavailable`, 탭 제목 `redacted`(브라우저), URL `redacted`(브라우저), 창·탭 제목 `truncated` 변형을 고르게 섞는다.
- 배치: 같은 기기의 레코드를 10초 창 단위로 묶어(최대 200건) 배치 하나와 배치 영수증 한 행(`results`는 모두 `stored`)을 만든다.
- 집중 세션: 하루 3회. 10:00·14:00 시작은 목표·작업 3000초, 16:00 시작은 목표 없는 세션(목표 0초, 작업 2400초)이며 모두 3000초 뒤 끝난다. 완료 세션 라벨은 활성 라벨 중 하나다. 기간 마지막 날 16:00 세션은 진행 중(`ended_at`·`work_seconds`·`label_id` NULL)으로 둔다.
- 라벨: 더미는 기본 라벨 5개(활성)와 `보관된 라벨` 1개(`archived_at` = 기간 첫날 00:00 UTC)를 만든다. 보관된 라벨에는 세션·확정·제안을 연결하지 않는다.
- 라벨 제안: 닫힌 detailed 활동 구간마다 구간 종료 30초 뒤 현재 버전 제안 1건(98% `ready`, 2%는 생성 2분 뒤 lease가 만료된 `processing`). `ready`의 `suggested_label_id`는 10%가 NULL(미분류)이고, 지연 800~3000ms, 입력 토큰 1500~3000, 출력 토큰 20~60, 참조 확정은 그 시점 이전 확정 최대 5개다. 별도로 닫힌 detailed 구간의 5%에 종료 시각을 30초 앞당긴 이전 버전의 `superseded` 제안 1건을 더한다. `failed`는 만들지 않는다.
- 라벨 확정: 닫힌 detailed 활동 구간의 60%(그중 10%는 미분류), 구간 종료 10분 뒤.

## 유저 수 ↔ 용량 측정 절차

유저 수와 용량의 환산값은 코드에 두지 않고 대상 환경에서 실측한다.

1. 빈 DB(마이그레이션 head만 적용)에서 `--users 1`을 실행하기 전 DB 크기를 확인한다. 예: `SELECT pg_database_size(current_database());`
2. 단계에서 쓸 `--end-date`·`--seed`·`--days`로 `--users 1`을 적재하고, 출력된 `(database)` 크기를 기록한다.
3. 유저 1명당 크기 = 적재 후 DB 크기 − 적재 전 DB 크기.
4. 목표 용량 T(1·10·100·1000GB)의 유저 수 = ⌈(T − 적재 전 DB 크기) ÷ 유저 1명당 크기⌉.
5. 그 유저 수로 `--users`를 올려 다시 실행한다(이미 적재한 유저는 건너뛴다). 출력된 `(database)` 크기로 목표에 도달했는지 확인하고, 모자라면 유저 수를 다시 계산해 늘린다.

인덱스·TOAST 크기는 행 수에 정비례하지 않을 수 있으므로 단계마다 출력된 크기로 다시 확인한다.
