# 활동 원본은 단건으로 저장하고 타임라인은 조회 시 계산한다

초기 활동 수집은 구현 속도와 물리 모델의 단순성을 우선한다. 클라이언트는
개인정보 필터를 통과한 관찰 또는 수집 상태 변경을 한 요청에 하나씩 보내고,
서버는 `activity_records`를 유일한 원본으로 저장한다. 활동 구간과 수집 공백은
별도 projection에 저장하지 않고 조회 시 원본에서 계산한다.

## 결정

- 계정은 여러 앱 설치의 Device를 가질 수 있다.
- `sequence`는 `device_id` 안에서 증가한다. 앱 재설치로 등록과 순번 상태를 잃으면
  새 `device_id`를 발급한다.
- 활동 요청은 레코드 하나만 포함한다. `batch_id`, `collection_stream_id`, batch
  watermark와 batch 결과 테이블은 만들지 않는다.
- `activity_records`는 `event_id`, Device, 순서, 종류, 관찰 시각, 시간대 문맥,
  수신 시각을 일반 컬럼에 저장하고 종류별 본문을 JSONB `payload`에 저장한다.
- `event_id`는 단건 재시도의 멱등성 키다. 같은 내용의 재전송은 기존 결과를
  반환하고 다른 내용의 재사용은 충돌로 거절한다. 별도 event hash는 저장하지
  않는다.
- 타임라인 조회는 계정에 속한 원본 레코드를 읽어 `ActivitySpan`과 `CaptureGap`을
  계산한다. 계산 결과를 영구 저장하지 않는다.
- 초기 제품은 한 시점에 하나의 기기만 계정에 접속해 기록한다고 가정한다. 이를
  인증에서 강제하는 작업은 별도 TODO이며 이번 저장 모델이나 `accounts` 변경에
  포함하지 않는다.

## 고려한 대안

- batch 수신, collection stream, watermark를 두는 방식은 오프라인 대기열과 대량
  전송에는 유리하지만 초기 온라인 단건 수집에 필요한 것보다 많은 상태와 충돌
  처리를 요구하므로 선택하지 않았다.
- `activity_timeline_segments`를 쓰기 트랜잭션에서 갱신하는 방식은 반복 조회를
  단순화하지만 원본 저장과 함께 projection 일관성·재생성 로직을 구현해야 하므로
  초기 범위에서 제외했다.
- 레코드별 hash를 저장하는 방식은 충돌 비교를 빠르게 만들 수 있지만 초기에는
  저장한 컬럼과 JSONB를 직접 비교할 수 있으므로 추가하지 않았다.
- 서로 다른 기기의 동시 활동을 대표 기기나 우선순위로 병합하는 방식은 초기
  제품의 단일 활성 기기 전제에 필요하지 않으므로 선택하지 않았다.

## 결과

- 초기 쓰기 경로와 스키마는 작아지지만 레코드마다 HTTP 요청과 DB 트랜잭션이
  발생한다.
- 타임라인 조회는 기간 경계의 이전 레코드까지 읽고 활동 경계를 다시 계산해야
  한다. 실제 병목이 확인되면 원본을 바꾸지 않고 projection을 추가할 수 있다.
- batch와 오프라인 대기열을 제외했으므로 네트워크가 없는 동안의 관찰 보존을
  보장하지 않는다.
- 인증 TODO가 구현되기 전까지 단일 활성 기기는 제품 가정일 뿐 서버가 강제하는
  불변조건이 아니다.
