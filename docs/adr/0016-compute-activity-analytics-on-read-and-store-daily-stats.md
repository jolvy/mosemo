# 활동 분석은 조회 때 계산하고 지난 날짜의 일간 통계만 변경 표시와 배치로 저장한다

## 맥락

[활동 분석 요구사항](../requirements/activity-analytics.md)은 날짜별 사용 시간·사용 대상
전환·라벨 전환(C1·C2·C7)과 집중 세션별 전환·시간 구성·방해 앱·이탈 근거·라벨 전환(C3~C7)을
요구한다. 이 ADR의 앞선 초안(2026-11-02~11-11)은 모든 결과를 15분 UTC 칸과 세션 단위로 저장하고
재계산 표시와 5분 배치로 갱신하는 구조였다. 2026-11-11 설계 목표를 하루 활성 사용자 1천 명으로
정하고 재설계를 허용하면서 그 구조를 다시 검토했다.

분석 결과의 원천은 세 곳에서 서로 다른 트랜잭션으로 바뀐다
([ADR 0012](0012-notify-cross-context-changes-with-in-process-domain-events.md)).

| 원천 변경 | 발생 BC·경로 |
| --- | --- |
| 관찰 구간 재구성(늦은 관찰 포함) | observation, 활동 기록·Kafka 배치 |
| 라벨 확정·정정 | labeling, HTTP API |
| 집중 세션 완료(일시중지 구간 포함) | observation, HTTP API |

측정한 사실(2026-11-10~12, [지표 명세](../activity-analytics-metrics.md)):

- 실제 기록의 가장 바쁜 하루(구간 497개, 전환 438회)에 세션 2개를 붙여 C1~C7 전체를 하루치
  계산하면 Python 프로토타입으로 중앙값 20ms, 최대 69ms다. DB 읽기 시간은 포함하지 않았다.
- 1천 명에서 분석 계산 수요는 초당 1건 미만이다(활동 1시간당 구간 50개 실측, 하루 활동 8시간·피크
  동시 25%는 측정 전 가정).
- 15분 칸 구조는 칸 경계 읽기 조건 결함(0초 구간 유실)과 칸 밖 연속 체류 읽기를 낳았고, 칸 합 =
  하루 계산, 재계산 표시 수렴, version·lease 동시성, 과거 재처리를 모두 따로 증명해야 했다.
- 사용자는 일간 통계를 나중에 LLM 답변과 주간·월간·연간 통계의 바탕으로 쓸 계획이다(이번 범위
  밖). 연간 통계를 매번 조회 때 계산하면 계산만 365일 × 20~70ms = 약 7~25초다.

선택 기준:

- 결과가 언제나 정정·늦은 관찰을 반영하는가
- 옳음을 증명해야 할 부품이 얼마나 적은가
- 여러 날을 한꺼번에 읽는 소비자(주간·월간·연간, LLM)가 빠르게 읽을 수 있는가
- 배치 실패·지연이 결과의 정확성을 깨뜨리는가
- 정의 변경 후 과거 결과를 어떻게 바꾸는가

## 결정

### 조회 때 계산

- 세션 분석(C3~C6, 세션별 C7)은 저장하지 않고 조회 때 원천에서 계산한다.
- 오늘(계정 시간대 날짜가 끝나지 않은 날)의 일간 통계(C1·C2·C7)도 조회 때 계산한다.

### 지난 날짜의 일간 통계 저장

- 저장 단위는 **(계정, 계정 시간대 날짜)**다. 15분 칸은 쓰지 않는다.
- 행에는 그날의 C1(앱·사용 대상별 시간, 앱 미확인·불투명·전체 관찰 시간), C2(횟수와 전환 목록),
  C7(횟수와 전환 목록), `source_version`, `definition_version`, 계산에 쓴 계정 시간대 `timezone`,
  `computed_at`을 둔다. 시간과 횟수는 여러 날을 더해 기간 통계를 만들 수 있는 값으로 둔다.
- 하루 계산은 `started_at`이 날짜 끝보다 이르고 `COALESCE(ended_at, last_observed_at) >= 날짜 시작`인 구간을
  읽고, 첫 구간에서 같은 사용 대상으로 맞닿은 앞 구간들을 날짜 밖까지 거슬러 읽는다(연속 체류).
  `>`로 읽으면 자정의 0초 구간을 놓치고, 거슬러 읽지 않으면 자정을 넘는 체류가 잘린다(무작위
  타임라인 20,000개 비교: C2 불일치 1,813개, 56개 → 둘 다 적용 시 0개).

### 변경 표시

- observation·labeling은 이벤트만 기록하고, analytics BC의 BEFORE_COMMIT handler가 같은 트랜잭션에서
  (계정, 날짜) 표시를 UPSERT한다. 표시의 version은 전역 DB 시퀀스로 발급한다.

  | 이벤트 | 표시할 날짜 |
  | --- | --- |
  | `TimelineChanged` | 교체 전후 구간의 시간 범위와 겹치는 날짜, 그 범위의 끝 시각이 속한 날짜 |
  | `LabelConfirmed` | 확정 구간의 시작 시각 날짜와 끝 시각 날짜 |
  | `FocusSessionCompleted` | 표시하지 않는다(일간 통계는 세션에 의존하지 않음) |

- 계정 시간대를 바꾸면 지난 날짜도 새 시간대로 다시 계산한다. 시간대를 바꾸는 트랜잭션은 계정
  advisory 잠금 안에서 `accounts.timezone`을 바꾼 뒤, 그 계정의 저장 행이 있는 날짜와 표시가 있는
  날짜, 그리고 각각의 앞뒤 하루에 표시를 추가하고 커밋한다(정의 변경 재처리와 같은 길). 지원 시간대
  사이의 UTC 오프셋 차이는 하루보다 작아(최대 14시간) 한 시각의 날짜가 최대 하루만 움직이므로 앞뒤
  하루면 새 시간대에서 활동이 생기는 날짜를 모두 덮는다. 오프셋 차이가 24시간 이상인 시간대를 지원하게
  되면 이 범위를 넓혀야 한다.
- 표시할 날짜를 정하는 계정 시간대는 원천 handler가 계정 advisory 잠금을 잡은 뒤에 읽는다. 잠금 전에
  읽은 시간대(예: UseCase가 앞에서 읽어 넘긴 값)로 날짜를 정하면, 시간대 변경과 겹칠 때 정정이 옛
  시간대 날짜에만 표시되어 사라진다.
- 오늘의 표시는 날짜가 끝날 때까지 남아 있다가 배치가 처리한다. 그래서 활동이 있었던 날은 모두
  처음 저장될 때도 이 표시를 통해 계산된다.

### 정확성은 조회가 보장한다

- 지난 날짜를 조회할 때, 표시가 남아 있거나 `definition_version`이 현재 정의와 다르거나 `timezone`이
  계정의 현재 시간대와 다른 날짜는 저장 행을 쓰지 않고 조회 때 계산한다. 그 밖의 날짜는 저장 행을 쓴다.
- 그래서 배치가 실패하거나 늦어도 화면·기간 통계·LLM은 언제나 원천의 현재 상태를 반영한 값을 받는다.
  배치가 늦으면 조회가 느려질 뿐이다. 조회 응답에 "갱신 대기" 상태를 두지 않는다.

### 배치

- [ADR 0010](0010-run-batch-jobs-in-apscheduler-process.md)의 job으로 등록한다. 끝난 날짜의 표시와
  옛 `definition_version` 행을 처리해 저장 행을 교체한다. 실행 주기는 정확성과 무관하며, 아래
  「실패·재처리」의 기본값(5분)으로 시작해 측정 뒤 조정한다.
- 저장과 표시 삭제는 같은 트랜잭션에서 한다. 저장은 `source_version`이 기존보다 클 때만 교체하고,
  표시는 선점 때 읽은 version과 같을 때만 삭제한다. 계산 중 새 변경이 오면 표시가 남아 다음 실행이
  다시 계산한다.
- 일간 통계는 원천에서만 계산하고 다른 저장 결과를 읽지 않는다.
- 정의를 바꾸면 `definition_version`을 올린다. 옛 행은 조회 때 계산으로 대체되고, 배치가 차례로 새
  정의로 다시 저장한다. 재처리 도중에도 결과가 섞이지 않는다. 재처리 방식은 아래 「일간 통계
  프로토콜」을 따른다.
- 계산 실패의 재시도·backoff·격리, 실행 주기, 선점, 정의 변경 재처리 절차는 아래 「실패·재처리」를
  따른다. 선점은 「일간 통계 프로토콜」대로 잠금을 계산 동안 쥐지 않는다.

### 일간 통계 프로토콜 (2026-11-13)

4단계 상태 모델 전수 검사(원천 변경 2회·배치 2개·날짜 1개·조회 1개, 정의 변경 0회·1회)에서 아래 조합이
불변식 위반 없이 탐색을 끝냈다(상태 621,510개, 실행 순서 37,265,556,568개). 불변식은 조회 결과 = 조회가
걸친 어느 순간의 원천 계산값, 변경이 멈추면 표시 0개와 저장 행 = 현재 원천·현재 정의의 계산값, 원천
변경이 배치의 잠금을 기다리지 않음, 저장 행의 정의 version이 줄지 않음이다. 각 항목을 빼거나 바꾼 변형은
반례가 있다(괄호 안).

계정 시간대 변경 1회를 더한 검사(날짜 3개·시간대 2개, 원천 변경 0~2회·배치 2개·조회 1개, 정의 변경 0회·1회)에서도
아래 조합이 위반 없이 탐색을 끝냈다(지원 시차 범위, 상태 1,040,566개, 실행 순서 5,354,277,558개). 이때 조회
결과는 조회가 걸친 어느 한 순간의 (계정 시간대, 원천)으로 계산한 값이어야 한다. 또 변경이 멈추면 새 시간대로
활동이 있는 날짜마다 저장 행이 생겨야 하고, 저장 행의 시간대가 옛 시간대로 되돌아가지 않아야 한다.

- **정의 변경 재처리(mark)**: 정의 행을 올린 뒤 옛 정의로 저장된 날짜마다 표시를 추가한다. 새 표시
  version이 커서 위의 guard(`source_version`이 클 때만 교체)를 그대로 써도 교체된다. 배치가 옛 정의 행을
  직접 찾는 방식은 guard를 (정의, `source_version`) 순서 비교로 바꿔야 하므로 쓰지 않는다(ADR guard 그대로면
  옛 정의 행이 영원히 남음).
- **저장 트랜잭션**: 한 트랜잭션에서 차례로
  1. 정의 행과 계정 행을 `FOR SHARE`로 읽고, 배치 코드의 정의나 배치가 계산에 쓴 계정 시간대와 다르면
     롤백한다(배포 중 옛 코드 배치가 옛 정의로 저장하거나 새 정의 행을 되돌리는 것, 시간대 변경과 겹친
     배치가 옛 시간대 값을 표시 없이 남기는 것을 막음).
  2. 일간 통계를 UPSERT한다(`source_version`이 클 때만 교체, `source_version` = 선점 때 읽은 표시 version v).
  3. `DELETE 표시 WHERE version = v`.
- **분석 조회**: `REPEATABLE READ READ ONLY` 트랜잭션 하나로 계정 시간대·표시·저장 행·원천을 읽는다. 표시와
  저장 행을 다른 스냅샷으로 읽으면 낡은 값을 "표시 없음"으로 읽고, 원천을 문장마다 다른 스냅샷으로 읽으면
  존재한 적 없는 원천 조합을 계산한다. 계정 시간대를 다른 스냅샷에서 읽으면 시간대 변경과 겹칠 때 옛
  시간대와 새 원천을 섞어 계산한다. 지금의 `read_snapshot()`은 READ COMMITTED이므로 분석 조회만 이 격리
  수준으로 열고, 계정 시간대도 그 트랜잭션 안에서 읽는다.
- **표시와 배치**: 표시 version은 전역 시퀀스에서 뽑는다. 표시 쓰기(원천 handler, 정의 재처리, 시간대 변경
  모두)는 계정 advisory 잠금 안에서 한다(잠금 밖에서 미리 뽑은 version을 쓰면 version이 뒤로 감). 배치는
  잠금 없이 표시를 읽어 version을 기억하고, 선점 잠금(`FOR UPDATE SKIP LOCKED`)을 쓰더라도 계산 동안 쥐지
  않는다(쥐면 원천 쓰기가 `lock_timeout`으로 실패). 원천은 선점 뒤에 읽는다.
- **시간대 변경**: 한 트랜잭션에서 차례로 계정 advisory 잠금, `accounts.timezone` UPDATE, 대상 날짜 읽기,
  대상 날짜마다 표시 UPSERT를 하고 커밋한다. 대상은 저장 행이 있는 날짜와 표시가 있는 날짜, 그리고 각각의
  앞뒤 하루다. 잠금 없이 시간대를 바꾸면 그와 겹친 원천 변경의 표시가 옛 시간대 날짜로 가서 정정이
  사라진다. 표시를 시간대보다 먼저 커밋하거나 대상을 UPDATE 전에 읽으면 옛 시간대로 저장된 행이 표시 없이
  남는다. 저장 날짜만 표시하면 새 시간대에서 처음 활동이 생기는 날짜가 저장되지 않는다. 앞뒤 하루를 빼면
  표시만 있고 저장 행이 없는 날짜의 이웃이 빠진다.
- 표시는 DB에만 있고 화면 상태는 없다. 조회 응답에 "갱신 대기"를 두지 않는다.
- 설계 원칙 "저장과 표시 삭제는 같은 트랜잭션"과 "일간 통계는 원천에서만 계산하고 다른 저장 결과를 읽지
  않는다"는 이 검사로 뒷받침된다. 같은 트랜잭션은 충분조건이다(삭제를 먼저 따로 커밋하면 반례가 있다).
- 측정 전: 정의 변경 때 표시 쓰기량(계정 수 × 날짜 수, 1천 명 × 365일 = 약 36.5만 행)과 계정 잠금 경합,
  운영 PostgreSQL 버전에서의 같은 동작은 5단계에서 확인한다.

### 실패·재처리 (2026-11-13)

일간 통계 배치의 실행·실패·재처리 방식이다. 위 프로토콜의 version 발급, guard, 조건부 삭제, 정의 확인은
바꾸지 않는다. 표시 행에 version 밖의 열(`attempts`, `next_attempt_at`, `kind`, `marked_at`,
`last_error`, `last_failed_at`)을 더하고 그 열을 다루는 규칙을 정한다. 수치는 측정 전 기본값이며 규모
측정 뒤 조정한다.

- **실행**: ADR 0010의 상시 프로세스에 job `analytics-daily-stats`를 5분 interval(시작 즉시 1회)로
  등록한다. 실행 한 번의 시간 예산은 120초이며 날짜 사이에서만 확인한다. 정의 재처리 표시는 스케줄
  없는 job `analytics-definition-mark`로 수동 실행한다.
- **지난 날짜**: DB `now()`에서 유예 1시간을 뺀 시각을 계정 시간대로 바꾼 날짜보다 이른 날짜를 배치가
  처리한다. 유예는 자정 직후 늦은 관찰로 같은 날짜를 두 번 계산하지 않기 위한 값이다. 조회는 유예 없이
  자정부터 지난 날짜로 보며, 그 사이에는 표시가 남아 조회 때 계산한다.
- **선점(lease)**: 짧은 트랜잭션 하나에서 처리할 표시를 최대 50개 `FOR UPDATE SKIP LOCKED`로 고르고,
  `attempts`를 1 올리고 `next_attempt_at`을 10분 뒤로 미룬 뒤 바로 커밋한다. 이때 돌려받은 version이
  "선점 때 읽은 version"이다. 다른 작업자는 잠금이 아니라 `next_attempt_at`으로 그 표시를 건너뛴다.
  계산 동안 쥐는 잠금은 없다. 원천 표시(`kind = 'source'`)를 정의 재처리 표시보다 먼저, 각각은 version
  순으로 처리한다.
- **재시도와 격리**: 시도는 선점 때 센다(프로세스 강제 종료도 시도 1회). 실패하면 같은 version일 때만
  `next_attempt_at`을 5분·30분·2시간·12시간·24시간 뒤로 미루고 실패 분류(예외 타입 이름만)를 남긴다.
  `attempts`가 6에 이르면 선점 대상에서 빠진다(격리). 원천 handler, 정의 재처리, 시간대 변경이 표시
  version을 새로 쓸 때 `attempts`와 `next_attempt_at`을 되돌린다. 격리 해제는 운영 SQL로 `attempts`를
  0으로 한다.
- **실패 분류**: 계산 예외와 날짜 단위 DB 오류(`lock_timeout`, `statement_timeout`)는 기록하고 다음
  날짜로 넘어간다. 한 날짜의 반복 실패가 다른 날짜를 막지 않는다. 연결 오류와 정의 불일치는 그 실행을
  끝낸다. 선점한 날짜는 lease가 끝난 뒤 다시 처리한다. 일시 오류로 쓴 시도는 되돌리지 않는다.
- **격리된 날짜의 조회**: 표시가 남으므로 조회는 그 날짜를 원천에서 계산한다. 계산 자체가 예외를 내면
  그 날짜를 포함한 조회는 요청 전체를 공통 오류로 실패시킨다. 저장된 옛 행으로 응답하지 않고, 그
  날짜만 뺀 부분 응답도 하지 않는다. 잘못된 값 대신 오류를 돌려 정확성을 지킨다.
- **정의 변경 절차**: 정의 상수를 바꾸는 커밋에 정의 행을 올리는 Alembic 마이그레이션을 함께 넣는다.
  배포를 확인한 직후 `analytics-definition-mark`를 실행한다. mark는 반드시 정의 행을 올린 뒤에 한다.
  먼저 하면 옛 코드 배치가 그 표시를 옛 정의로 처리해 지운다. mark는 계정 advisory 잠금 안에서 계정
  하나씩 표시를 UPSERT하며, 다시 실행해도 안전하다. 재처리 속도는 환경 변수
  `ANALYTICS_REPROCESS_PER_RUN`(실행 한 번의 정의 재처리 표시 상한, 0이면 멈춤)으로 조절하고, 바꾸면
  배치 프로세스를 재시작한다. 정의 행은 줄이지 않는다. 되돌리기는 옛 로직을 새 정의 version으로
  배포하는 것이다. downgrade 마이그레이션은 새 정의로 저장된 행이 하나라도 있으면 실패해야 한다.
- **완료 확인과 운영 지표**: "표시 없는 옛 정의 저장 행 수"가 0이고 남은 정의 재처리 표시가 0이면 끝이다.
  배치는 실행마다 저장·대체됨(계산 중 원천 변경)·guard 무시·실패(분류별)·새 격리·정의 불일치 수를
  로그로 남긴다. 운영 지표는 가장 오래된 원천 표시의 나이, 격리 수, 마지막 성공 실행 시각, 조회 중 원천
  계산 비율, 원천 쓰기의 `lock_timeout` 수다.
- 근거: 위 상태 모델에 재시도·lease·격리 열을 더한 전수 검사(실패 1회·강제 종료 1회 추가, 상태 2,958,806개)에서
  불변식 위반과 교착이 없었다. lease나 실패 기록의 version 조건을 빼도 불변식은 깨지지 않으므로 둘은 정확성
  장치가 아니라 중복 계산과 정정 반영 지연을 줄이는 비용 장치다. 장애 주입 시나리오(실제 PostgreSQL 두 연결·
  프로세스 kill)와 FMEA는 4B 산출물에 있다.

| 대안 | 장점 | 단점·비용 |
| --- | --- | --- |
| 모든 결과를 15분 칸·세션 단위로 저장하고 재계산 표시와 5분 배치로 갱신(이 ADR의 앞선 초안) | 조회가 언제나 저장 행 읽기다. | 칸 경계·칸 밖 체류·칸 합 일치·표시 수렴·lease 동시성·과거 재처리를 모두 증명해야 한다. 1천 명에서는 계산이 수십 ms라 얻는 것이 적다. 결과가 최대 5~10분 늦고 "갱신 대기"를 보여야 한다. |

| 최근 N일만 매일 다시 계산 | 단순하다. | N일보다 늦은 변경을 놓친다. 실제 기록에 5일 늦은 일괄 업로드가 있었다. |

| Kafka 이벤트와 분석 Consumer | 반영 지연이 짧다. | HTTP 경로에 outbox와 중계기가 필요하다. 1천 명에서 얻는 것이 없다. |

## 결과와 트레이드오프

- 결과는 언제나 원천의 현재 상태를 반영한다. 배치는 지난 날짜를 미리 채우는 캐시이며 정확성을
  책임지지 않는다.
- 세션 분석과 오늘 통계에는 저장 테이블·표시·배치가 없다. 증명할 대상이 "조회 때 계산 = 참조
  구현"과 "저장된 일간 행 = 그날의 조회 때 계산"으로 줄어든다.
- 조회 지연은 계정-하루 구간을 읽는 DB 시간에 달려 있다. 예산은 분석 화면 하나 조회의 서버 응답 p95
  300ms·p99 500ms(원천 계산 포함)이며 5단계에서 측정한다. 조회가 몰리거나 긴 기간 조회가 생기면 그때
  저장 범위를 넓힌다. 계산 함수는 그대로 쓴다.
- 이벤트 handler와 표시 테이블, 일간 결과 테이블, version 시퀀스, job 하나가 생긴다. handler의 실패는
  원천 요청을 롤백한다(ADR 0012).
- 계산이 결정적으로 실패하는 날짜는 배치에서 격리되고, 그 날짜를 포함한 조회도 오류로 실패한다.
  정확성을 지키는 대가로 그 날짜는 코드를 고칠 때까지 볼 수 없다. 격리 수는 운영 경보로 본다.
- 정의를 바꾸면 계정 수 × 저장 날짜 수만큼 표시를 쓰고(1천 명 × 365일 = 약 36.5만 행, 측정 전),
  재처리가 끝날 때까지 옛 정의 날짜의 조회는 원천에서 계산한다.
- 계정 시간대를 바꾸면 그 계정의 저장 날짜 수와 비슷한 수의 표시를 계정 잠금을 쥔 채 쓴다(1년 사용자 약
  370행, 측정 전). 그동안 그 계정의 원천 쓰기는 기다리고, 재처리가 끝날 때까지 그 계정의 지난 날짜 조회는
  원천에서 계산한다.
- 원본 보관은 90일이다(요구사항 「비기능 요구사항」). 90일이 지나면 원본 활동 레코드는 삭제되고 구간·라벨
  확정·집중 세션은 S3로 옮겨지므로, 그보다 지난 날짜의 조회는 원천에서 계산하지 못하고 저장 행만 쓴다.
  정의 변경 때 그 날짜를 다시 계산하려면 S3에서 원천을 읽는 경로가 필요하며 7단계에서 설계한다.
- 주간·월간·연간 통계와 LLM 답변은 이번 범위가 아니다. 일간 행은 그 바탕이 되도록 더할 수 있는
  값으로 둔다. LLM에 넘길 때의 개인정보(창 제목·URL)는 그 기능을 다룰 때 검토한다.
