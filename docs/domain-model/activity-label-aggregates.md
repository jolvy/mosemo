# 활동 라벨 Aggregate 설계

탐색 중인 설계 기록이다. 합의한 Root의 단위와 현재 구현에서 확인한 사실을 구분한다.
합의한 규칙 소유권, 배치 원자성, 동시성 보호와 값 객체 매핑을 기록한다.
메서드의 구체적인 인터페이스는 구현 시 이 결정에 맞춰 정한다.

## 합의한 출발점

- 현재 탐색 범위인 관찰·라벨 목록·사용자 확정·제안은 하나의 바운디드 컨텍스트로 둔다.
- 라벨, 사용자 확정, 제안을 독립된 Aggregate로 설계한다.
- 각 후보의 수명주기와 불변식, 객체 사이의 규칙을 확인한 뒤 최종 경계를 결정한다.
- 패키지 구분이나 계정별 잠금 범위만으로 Aggregate를 정하지 않는다.
- 이번 탐색은 기존 패키지 재배치 명세와 별도의 모델 설계다.

## 합의한 Root와 정체성

### 개별 라벨

라벨 하나를 Root로 둔다. 이름 변경·보관·복원에도 라벨의 식별자는 유지한다.
이 동작의 수명주기는 개별 라벨이 소유한다. 계정의 모든 라벨을 한 Aggregate로
불러와 변경하는 구조로 확장하지 않는다.

계정별 이름 중복은 목록을 조회하는 협력과 DB 유일성 제약으로 보호하는 방향을
채택한다. 보관 라벨과 같은 이름으로 생성 요청을 했을 때의 복원 계약도 유지한다.
구체적인 조회·변경 순서와 경쟁 조건 보호 방식은 아래 Q14 합의에 따른다.

기존 라벨 목록 쓰기 계약은 제거 시 영속 참조가 없으면 물리 삭제하고, 참조가
있으면 보관하는 방식이다. 복원은 별도 API가 아니라 보관 라벨과 같은 이름의
생성 요청으로 수행한다. 활성 라벨과 같은 이름의 생성은 충돌이다. 이 기존 계약을
유지한다.

### 라벨 쓰기의 동시성 — Q14 합의

라벨 생성·복원·이름 변경·제거는 라벨 쓰기 트랜잭션에서 처리하며 계정 타임라인
잠금에는 참여하지 않는다. 기존 라벨을 변경할 때는 계정과 식별자로 대상 행을
조회해 행 잠금을 획득한 뒤, 라벨 Root의 이름 변경·보관·복원 규칙을 적용한다.

생성 요청은 이름을 정규화한 뒤 같은 계정·이름의 라벨을 조회한다. 보관된 행이면
잠금 후 복원하고, 활성 행이면 이름 충돌로 처리한다. 행이 없으면 새 라벨을 삽입한다.
존재하지 않는 행은 잠글 수 없으므로 동시 생성·이름 변경과의 최종 경쟁은
`UNIQUE(account_id, display_name)`으로 판정한다. 유일성 충돌 시 해당 DB 오류를
그대로 노출하지 않고 트랜잭션의 실패한 구문을 정리한 뒤 재조회해 복원 가능 여부
또는 이름 충돌을 판단한다.

이름 변경은 대상 행을 잠그고 정규화한 이름으로 변경한다. 다른 활성·보관 라벨과
겹치면 유일성 충돌을 공개 이름 충돌 오류로 변환한다. 제거는 대상 행을 잠그고
확정과 제안의 영속 참조를 검사한다. 참조가 있으면 보관하고, 없으면 물리 삭제한다.
라벨을 참조하는 두 FK의 `NO ACTION` 제약은 검사와 새 참조 생성의 경쟁에 대한
DB 안전망으로 유지한다.

새 확정·제안 참조가 먼저 저장되면 제거는 참조를 보고 보관한다. 물리 삭제가 먼저
완료됐다면, 앞서 활성 조회를 통과했더라도 뒤늦은 참조 저장은 FK 위반으로 실패한다.
확정 경로에서는 이를 라벨 사용 불가 오류로 변환하고, 배치 확정은 전체
트랜잭션을 롤백한다. 제안 작업에서는 최신 라벨 상태를 다시 확인해 해당 시도의
실패로 처리한다. 보관이 활성 확인 뒤에 일어난 경우에는 기존 합의대로 새
확정 저장을 허용한다. 이 경쟁 처리는 계정 전체가 아닌 해당 라벨 행과 DB 제약을
사용한다.

### 반복 요청 — Q15 합의

정규화 후 현재 이름과 같은 이름으로 변경하면 성공으로 응답하되 `updatedAt`을
바꾸지 않는다. 이미 보관된 라벨을 다시 제거하면 `archived` 결과를 반환하며
`archivedAt`과 `updatedAt`을 바꾸지 않는다. 이 반복 제거는 현재 참조가 없어도
보관된 라벨을 물리 삭제하는 명령으로 해석하지 않는다. 이미 물리 삭제된 라벨의
제거 재시도는 라벨 없음 오류를 반환한다. 실제 상태가 바뀐 경우에만 변경 시각을
갱신한다.

### 시작 원본 관찰별 최신 확정

같은 계정과 같은 시작 원본 관찰을 근거로 하는 최신 확정 하나를 Root로 둔다.
확정에는 어떤 구간 내용 버전에 대한 선택인지 남긴다. 현재 버전과 다르면 기존
선택을 적용하지 않고 사용자의 재검토를 기다린다.

사용자가 새 버전을 명시적으로 다시 확정하면 같은 확정 객체의 최신값을 갱신한다.
내용 버전이 바뀌었다는 사실만으로 사용자 선택을 갱신하지 않는다. 정정·재확정마다
새로운 확정 객체나 이력 행을 만드는 모델은 현재 설계에 포함하지 않는다.
구간 재구성으로 시작 원본 관찰 자체가 달라지면 기존 확정을 새 식별 단위로
자동 이전하지 않는다.

### 구간 내용 버전별 제안

같은 계정·시작 원본 관찰·구간 내용 버전에 대한 제안 하나를 Root로 둔다.
한 버전의 선점·실패·재시도·완료는 같은 객체의 상태 전이다. 새 내용 버전에
대해서는 별도의 제안 객체를 둘 수 있다.

처리 시도 자체를 별도 Root로 만들지 않는다. 제안 Root가 시도 횟수·임대·처리
토큰과 전이 조건을 관리해 이전 시도가 최신 시도를 덮어쓰지 못하게 한다.

## 객체 사이의 규칙 소유권

제안 결과를 반영할 때 제안 Root는 자신의 임대·처리 토큰과 상태 전이를 판단한다.
확정 Root는 자신의 선택이 현재 구간 버전에 적용되는지 판단하고, 라벨 Root는
새 제안·선택에 사용할 수 있는지 판단한다. 현재 관찰 구간의 버전·적격성과 함께
여러 객체의 판단을 결합해야 하는 도메인 규칙은 별도의 협력 객체가 맡는다.

확정 판단과 제안 완료 판단은 각각 별도의 협력 객체로 둔다. 확정 판단은 구간의
적격성·최신 버전, 라벨 사용 가능 여부, 기존 확정과 요청 선택의 관계를 결합한다.
제안 완료 판단은 현재 구간과 사용자 확정, 선택 라벨의 유효성 등 결과 반영 조건을
결합한다. 임대 토큰 소유권과 상태 전이는 제안 Root가 판단한다. 여러 작업을 모두
처리하는 범용 협력 객체로 합치지 않는다.

애플리케이션 서비스는 잠금 획득, 최신 객체 조회, 판단 호출, 저장과 외부 호출의
순서를 조율한다. 구간 버전, 확정 상태, 제안 임대와 같은 조건은 변경 경쟁으로부터
보호한다. 라벨 활성 여부는 검증 시점의 판단이며 저장 순간까지 활성 상태를
유지해야 한다는 조건은 두지 않는다.

협력 객체에는 서비스가 조회한 구간·라벨·확정·제안 객체와 요청 값을 직접 전달한다.
같은 상태를 담는 별도의 도메인 모델로 복제하지 않는다. 각 객체의 판단을 결합하며
세션과 저장소를 전달받거나 조회·저장을 수행하지 않는다. 판단에 필요한 데이터는
서비스가 미리 조회한다. 통과 시 변경 대상을 반환하고, 실패 시 도메인 오류를 낸다.
상태 전이는 해당 Root가 수행하고 저장·커밋은 서비스가 조율한다. 메서드의 구체적인
입출력 타입과 이름은 구현 시 이 책임 구분에 맞춰 정한다.

## 배치 확정의 원자성

단건과 배치 모두 시작 원본 관찰별 최신 확정 Aggregate를 사용한다. 배치 요청은
여러 확정 Aggregate를 하나의 DB 트랜잭션에서 검증하고 저장한다. 항목 하나가
실패하면 전체 요청을 롤백한다. 이는 여러 Aggregate에 걸친 트랜잭션을 허용하는
명시적 예외다. 계정 전체 확정을 하나의 Root로 확대하지 않는다.

VS Code 구간의 '개발' 확정과 문서 읽기 구간의 '학습' 확정은 각자 수정할 수 있다.
각 확정의 선택이 상대 구간의 선택에 의존하는 불변식은 현재 확인되지 않았다.
함께 성공하거나 실패해야 한다는 조건은 이번 배치 요청의 원자성 계약이다.
여러 구간의 확정이 항상 함께 변경되어야 지켜지는 도메인 규칙이 발견되면
Aggregate 경계를 재검토한다.

배치 API는 제안 식별자를 승인하는 명령이 아니라 구간별 라벨 또는 미분류 선택을
확정하는 명령이다. 사용자는 제안을 채택하거나 다른 선택을 직접 확정할 수 있다.
현재 라벨 타임라인은 저장된 관찰 구간과 최신 확정을 조회해 상태와 묶음을 계산한다.
이번 결정에 확정 직후 별도의 라벨 타임라인 projection을 저장하는 단계는 포함하지
않는다. 별도 읽기 테이블이나 비동기 이벤트 처리의 도입은 후속 판단이다.

## 값 객체

`SegmentVersion`과 `LabelSelection`을 값 객체로 도입한다. `SegmentVersion`은 버전의
유효한 형식을 보장하고, 최신 관찰 구간과의 일치는 해당 구간을 조회한 뒤 판단한다.
`LabelSelection`은 라벨 선택과 명시적 미분류를 구분한다. 아직 확정하지 않은 상태는
확정 객체의 부재로 표현하며 미분류 확정과 혼동하지 않는다.

계정 ID, 라벨 ID, 임대 토큰은 우선 UUID를 유지한다. 별도 규칙이 없는 식별자까지
일괄적으로 값 객체로 감싸지 않는다.

### API와 ORM 사이의 매핑 — Q13 합의

값 객체 자동 변환과 기존 Declarative Mapping을 함께 사용한다. 도메인 동작에
진입할 때 서비스가 API 요청 값을 `SegmentVersion`과 `LabelSelection`으로 변환한다.
ORM 속성에서도 값 객체를 사용하며, 저장과 조회 시 `TypeDecorator`가 값 객체와
기존 DB 값을 변환한다. 도메인 메서드에서는 값 객체를 직접 비교하고 반영한다.
Imperative Mapping으로 변경하거나 별도의 도메인 모델을 복제하지 않는다.

DB의 구간 버전 문자열, 라벨 UUID와 NULL, 공개 API의 버전 문자열과 선택 형태는
유지한다. 확정의 라벨 NULL은 명시적 미분류이며 확정 객체 부재와 구분한다. 제안의
미완료 상태 등 다른 필드의 NULL 의미까지 일괄적으로 미분류로 해석하지 않는다.
API 응답 변환과 저장소·scanner의 비교 및 조회도 값 객체 사용에 맞춰 조정한다.
기존 `TimezoneStorage`처럼 변환기 자체의 규칙은 별도 저장 타입이 맡는다.

## 저장소와 조회 책임

확정과 제안의 저장소 책임을 분리하고, 기존 라벨 목록 저장소는 유지한다.
확정 저장소는 시작 원본 관찰별 최신 확정을, 제안 저장소는 구간 내용 버전별 제안을
조회하고 저장한다. 여러 모델을 조인해 타임라인 결과를 만드는 조회는 별도의 조회
객체가 맡는다. 트랜잭션의 시작과 커밋은 애플리케이션 서비스가 조율하므로 저장소가
개별 커밋을 수행해 배치 원자성을 깨뜨리지 않는다.

## 이벤트 도입 시점

현재는 실제 소비자가 필요한 후속 작업이 없으므로 확정 이벤트를 발행하지 않는다.
이벤트스토밍의 사건 이름을 곧바로 발행 메시지나 저장 이력으로 취급하지 않는다.
개인화 학습 데이터, 통계 또는 별도 읽기 모델처럼 구체적인 후속 작업을 도입할 때
이벤트 계약과 소비자 처리, 허용 가능한 반영 지연, 전달 보장 및 실패 복구를 함께
설계한다. Outbox의 필요성도 이때 판단한다. Outbox를 사용하는 비동기 전달에서는
확정 상태와 이벤트를 같은 DB 트랜잭션에 저장하고, 발행기와 소비자의 재시도 및
중복 처리 규칙을 함께 정의해야 한다. 이벤트 도입 자체가 Outbox 도입을 강제하지는
않는다.

## 동시성 보호 — Q11 합의

관찰 원본과 관찰 타임라인 projection은 현재처럼 동기적으로 같은 트랜잭션에서
갱신한다. 관찰 저장·구간 재구성, 확정, 제안 선점·최종 반영의 계정 타임라인 잠금은
유지한다. AI 호출은 잠금을 해제한 뒤 수행하고 최종 반영에서 다시 잠가 검증한다.

라벨 보관·복원·이름 변경은 이 계정 타임라인 잠금에 참여시키지 않는다. 라벨 활성
여부를 확인한 후 보관이 이루어져도 이미 검증을 통과한 확정은 저장할 수 있다.
활성 확인에서 이미 보관된 라벨은 기존 신규 선택 검증대로 거절하되, 보관 자체가
진행 중인 확정을 취소하거나 기존 확정을 제거하지 않는다. 같은 버전·같은 선택의
배치 재시도에 대한 기존 멱등성 예외도 유지한다.

라벨 자체의 경쟁 갱신과 계정별 이름 유일성은 라벨 쓰기 트랜잭션과 DB 제약으로
별도 보호한다. 계정 타임라인 잠금에 참여하지 않는다는 결정은 DB의 행 잠금이나
유일성 제약을 제거한다는 뜻이 아니다. 구체적인 경쟁 처리 방식은 Q14 합의를 따른다.

### 유지 결정의 검토 근거

현재 계정 타임라인 잠금은 관찰 저장·구간 재구성, 확정, 제안 선점·최종 반영을
조율한다. 이를 대체 보호 없이 제거하면, 동시 관찰이 각자의 원본 조회로 별도
구간을 생성하거나 기존 projection을 서로의 오래된 조회 결과로 재구성할 수 있다.
이전 버전의 확정을 두 배치가 현재 버전의 서로 다른 선택으로 동시에 갱신하면
둘 다 성공할 수 있다. 순차 처리에서는 두 번째 요청이 배치 충돌이어야 한다.
제안 토큰 검사는 현재 메모리 객체에 대한 검사이며 SQL 조건부 갱신이 아니므로,
잠금 없이는 새 임대 선점과 오래된 결과 반영이 서로 덮어쓸 수 있다.

이 검토는 코드의 교차 실행 분석이며 실제 경쟁 실행 테스트 결과가 아니다.
애플리케이션은 DB 격리 수준을 명시하지 않아 실행 DB의 설정을 따른다. 위 분석은
일반적인 READ COMMITTED 실행을 전제로 한다. 유일성 제약은 중복 식별 행을 막지만
이들 조회·판단·갱신 순서까지 보장하지 않는다.

기존 확정·제안 행은 행 잠금이나 조건부 갱신으로 보호할 수 있지만, 최초 생성과
구간 재구성 및 객체 사이의 조건은 별도 조율이 필요하다. 현재는 이런 대체 방식을
도입하지 않고 기존 계정 잠금을 유지한다. 라벨 쓰기로 잠금 범위를 확대하면 서로
기다려야 하는 작업이 늘어난다. 라벨 활성 상태를 저장 순간까지 보장할 요구가
없으므로 이런 범위 확대는 채택하지 않는다. 경합에 따른 성능 영향은 측정 결과로
단정하지 않는다.

## 현재 구현에서 확인한 사실

| 모델 | 저장된 식별 단위 | 현재 소유한 동작 |
| --- | --- | --- |
| 라벨 | `label_id`; 계정과 표시 이름의 유일성 | 현재는 라벨 데이터와 DB 제약이 있으며 공개 목록 쓰기는 후속 기능이다. |
| 사용자 확정 | `confirmation_id`; 계정과 시작 원본 레코드의 조합은 유일하다. | 같은 선택의 재시도 판정, 선택·버전 변경과 확정·정정 시각 갱신 |
| 제안 | `proposal_id`; 계정·시작 원본 레코드·구간 내용 버전의 조합은 유일하다. | 선점, 임대·재시도 판정, 처리 토큰에 따른 실패·완료·대체 전이 |

- 확정과 제안 처리는 현재 관찰 구간, 확정, 제안, 라벨을 따로 조회한다.
- 확정 서비스는 현재 구간의 적격성·버전·라벨 소유권과 활성 상태를 함께 검증한다.
- 제안 처리기는 선점과 최종 반영에서 구간 버전과 사용자 확정 등을 다시 검증한다.
- 배치 확정은 여러 구간을 하나의 요청 트랜잭션에서 검증하고 저장한다.
- 계정별 타임라인 잠금은 여러 구간과 모델을 포괄한다. 단일 Root가 모든 모델을
  소유해 변경하는 구조는 현재 없다.
- 현재 확정은 최신값 하나를 유지한다. 새 내용 버전의 재확정도 기존 확정 행을
  갱신하며, 정정·재확정마다 별도의 이력 행을 추가하지 않는다.
- 현재 제안의 재시도는 같은 버전의 제안 행에서 횟수와 임대 등을 갱신한다.
  새 내용 버전은 별도의 제안 행을 가질 수 있으며, 시도별 이력 행은 없다.
- 공개 API는 라벨의 식별자를 노출하지만 확정·제안의 내부 식별자는 노출하지 않는다.
- [라벨 목록 쓰기 계약](https://github.com/jolvy/mosemo/issues/34)은 이름 변경·보관·복원에서
  라벨의 식별자 유지를 요구한다. 현재 계정별 이름 유일성 제약은 보관 라벨도 포함한다.

## 경계를 검증할 시나리오

### 제안 처리 중 사용자 확정

1. 제안 작업자가 관찰 구간 버전 V1을 선점한다.
2. AI 호출이 진행되는 동안 사용자가 V1의 라벨 또는 미분류를 확정한다.
3. 작업자가 결과를 반영하려 한다.
4. 사용자 확정은 공식 선택으로 유지되고 제안이 이를 변경하지 않는다.

이 조건을 어떤 객체가 판단하며 어떤 상태를 함께 변경해야 하는지 설계한다.

### 제안 처리 중 늦은 관찰

1. 제안 작업자가 관찰 구간 버전 V1을 선점한다.
2. 늦게 도착한 관찰을 반영해 현재 구간 내용이 V2로 바뀐다.
3. V1에 대해 생성한 제안은 V2의 현재 제안으로 적용되지 않는다.
4. V1의 사용자 확정도 V2에 조용히 이전하지 않는다.

원본 레코드의 정체성, 도출된 구간 식별자, 내용 버전과 사용자 판단의 정체성을
구분해 각 객체의 유효성을 설계한다.

## 구현 시 구체화할 내용

- 도메인 메서드와 협력 객체의 시그니처, 저장소 메서드 이름과 모듈 배치.
- 동시성 충돌을 공개 오류로 변환하는 트랜잭션 경계와 재조회 절차.

구현 과정의 근거와 정책은 기존 ADR 「관찰 사실과 개인 라벨 확정을 분리한다」 및
관찰부터 라벨 확정까지의 이벤트스토밍 기록을 함께 확인한다.
