# 활동 분석 검증 계획

[활동 분석 요구사항](requirements/activity-analytics.md)의 C1~C7과 일간 통계를 무엇으로, 어떤 정답에 대어
검증하는지 정한다. 테스트마다 대상·입력 생성·판정·계층·실행 위치와 대응하는 인수 조건(AC)·불변식·사례를
적는다. 대응 열은 검사기 `check_step4e.py`(산출물 폴더)가 읽어 AC-8001~8029와 아래 「불변식」 표의 모든
ID가 테스트 1개 이상에 대응하는지 확인한다.

작성: 2026-11-13(4단계 E). 기준 커밋: `feat/analysis` 0a2f014(참조 구현 A 갱신 #272 병합 뒤). 근거 산출물: 4단계 A~D 보고, 4B 확정과
후속 F-1 보고, `pg_scenarios.md`. 산출물 폴더는 저장소 밖이며, 아래에서 "산출물 도구"는 그 폴더의 Python
파일을 뜻한다.

## 목적과 범위

- 목적: C1~C7 계산(조회 때 계산)과 지난 날짜의 일간 통계 저장 프로토콜이 명세와 같다는 근거를 테스트 단위로
  고정한다. 사전 등록(4단계)의 증명 대상 P1~P4를 테스트로 옮긴다.
  - P1 조회 때 계산 결과 = 명세(AC-8001~8021, 지표 명세 사례 80개).
  - P2 저장된 일간 통계 = 그날을 조회 때 계산한 결과(AC-8022).
  - P3 변경 표시·배치·정의 version이 어떤 순서로 섞여도 조회는 현재 원천을 반영하고 표시는 0개로
    수렴한다(AC-8013·8015·8016·8023).
  - P4 서로 다른 정의 version의 결과가 섞이지 않는다(AC-8023).
- 범위: 계산(C1~C7), 날짜 읽기(거슬러 읽기 포함), 일간 통계 배치(표시·선점·저장·재시도·격리·정의 재처리),
  분석 조회 API, 실제 하루와의 일치(골든 데이터셋), 조회 지연 예산.
- 범위 밖: 제품 코드와 마이그레이션 작성(7단계 하위 Issue), 수집 클라이언트 자체의 검증(활동 관찰 PRD 범위),
  주간·월간 통계와 LLM 답변(요구사항 제외 범위).
- 4B에서 정한 FR-30과 AC-8024~8027(격리·재시도·강제 종료·정의 재처리), F-2에서 정한 AC-8028·8029(계정
  시간대 변경)도 대상이다.

## 불변식

대응 열에 쓰는 ID다. I는 일간 통계 프로토콜의 불변식(상태 모델이 검사), E는 요구사항 「정책과 불변식」과
FR-17이 정한 계산 불변식이다.

| ID | 내용 | 출처 | 상태 |
| --- | --- | --- | --- |
| I1 | 조회 결과 = 조회 코드의 정의로, 조회가 걸친 어느 한 순간의 원천을 처음부터 계산한 값. 어느 상태에서든 한 스냅샷 조회 = 그 상태 원천의 계산값 | 4단계 D 3.4 | 확정 |
| I2 | 변경이 멈춘 뒤 배치를 혼자 최대 2회 더 돌리면 표시 0개, 저장 행 = 현재 원천·현재 정의의 계산값(격리된 표시는 해제 뒤) | 4단계 D 3.4, F-1 3.4 | 확정 |
| I3 | 조회 결과의 정의 = 조회 코드의 정의. 저장 행 안에서 값과 정의 표기가 섞이지 않음 | 4단계 D 3.4 | 확정 |
| I4 | 원천 변경(과 정의 재처리 표시)의 커밋은 배치가 계산 동안 쥔 잠금을 기다리지 않음 | 4단계 D 3.4, F-1 3.4 | 확정 |

## 테스트 목록

열의 값:

- 계층: Unit·Integration·E2E는 [테스트 규칙](../tests/AGENTS.md)의 분류다. "설계 산출물"은 저장소 테스트가
  아닌 설계 근거(모델 탐색, 무작위 차등, 측정)다.
- 실행 위치: 저장소 테스트(지금 `feat/analysis`에 있음), 산출물 도구(산출물 폴더에서 실행), 7단계 이후 구현
  테스트(제품 코드와 함께 하위 Issue에서 작성).
- 상태: 있음(실행해 결과가 있음), 진행 중, 기록일 대기, 5단계 작성, 7단계 작성.
- 대응: AC, 불변식(위 표), 지표 명세 사례 ID, 4B 시나리오 ID. `~`는 범위다(`AC-8001~8011`).

7단계 테스트의 패키지 이름은 SUT 패키지가 정해지는 7단계에서 정한다. 아래 "분석 계산 모듈"은 C1~C7을
계산하는 제품 코드, "배치 job"은 `analytics-daily-stats`, "조회 API"는 분석 조회 HTTP 엔드포인트를 뜻한다.

### 장애 주입

4B 확정 4절 FI1~FI16을 옮긴다. 프로세스 kill이 필요한 것은 실제 배치 프로세스(`mosemo.entrypoints.batch`의
`run analytics-daily-stats`)를 띄우고 환경 변수로 켜는 대기 지점에서 신호를 보낸다. backoff·lease는 운영자
연결로 `next_attempt_at`을 당겨 기다리지 않는다. 끝에서 I1, 장애가 풀린 뒤 I2(격리는 해제 뒤)를 확인하고, kill

## 지금 있는 것과 7단계에 만들 것

| 구분 | 테스트 | 바로 실행하는 방법 |
| --- | --- | --- |
| 지금 저장소에 있음 | SC-1~SC-5(테스트 263개, 0a2f014에서 모두 통과) | `uv run pytest tests/unit/support/analytics_reference` |
| 지금 산출물 도구로 있음 | SC-6, DF-1~DF-4, MR-1~MR-6, MU-1·MU-2, SM-1~SM-4, GD-4, PF-3 | 산출물 폴더에서 `python3 cases.py`, `python3 compare_a.py cases`·`random -n 20000`·`targeted`·`real`·`mutants`, `python3 metamorphic.py -n 20000 --impl py:a_impl`, `python3 mutants.py -n 20000`, `python3 protocol_model.py`, `python3 protocol_model_4b.py F5`, `python3 protocol_model_tz.py`, `python3 protocol_model_tz3.py` |
| 기록일 뒤 | GD-1~GD-3 | [골든 데이터셋](activity-analytics-golden.md) 「비교 도구」 |
| 5단계 | PF-1, PF-2 | 5단계 사전 등록에서 정함 |
| 7단계 이후 구현 테스트 | SC-7·SC-8, DF-5, MR-7, MU-3, TX-1~TX-13, FI-1~FI-16, API-1~API-12, E2E-1 | 제품 코드와 함께 하위 Issue에서 작성 |

- 7단계로 옮길 때 산출물 도구 중 무작위 생성기(`gen.py`)와 관계 정의(`metamorphic.py`)는 저장소 테스트 지원
  코드로 옮겨 제품 구현에 그대로 쓴다. ref는 옮기지 않는다(독립 구현 A가 저장소에 있으므로 차등 상대는 A다).
- 상태 모델(SM-1~SM-3)은 구현이 바뀌어도 다시 돌릴 수 있도록 저장소 도구로 옮길지 7단계에서 정한다. 옮기지
  않으면 TX·FI 통합 테스트가 모델과 구현 사이의 대응을 지키는 유일한 근거다.
- 성능·장애 주입 테스트에서 테스트 전용 대기 지점은 환경 변수로만 켜고 운영 설정에서는 꺼진 것을 단위
  테스트로 확인한다.

## 데이터 품질과 개인정보

- 실제 기록(덤프, 기록일 일지, 로거 기록, 골든 파일)은 저장소와 산출물 보고서에 넣지 않는다. 저장 위치는
  저장소 밖(`~/mosemo-golden/` 권한 700, 작업 세션 scratchpad)이다. 보고서·Issue·PR에는 구간 수, 날짜 수,
  불일치 건수, 비율, 통계값만 쓴다. 앱 이름·URL·창 제목·라벨 이름 원문은 쓰지 않는다. 창 제목·URL의 일치는
  digest로만 비교하고 digest도 저장소에 넣지 않는다.
- 저장소 테스트의 입력은 손으로 만든 사례와 합성 생성기 출력뿐이다. 실제 기록을 픽스처로 쓰지 않는다.
- 생성기 분포는 결함 탐색용으로 경계 사례를 과대 생성한다(0초 구간 17.6%, 실측 4.5%). 무작위 차등의 결과를
  실제 분포의 오류율로 읽지 않는다. 실제 분포는 `scripts/seed_load.py`의 measured 프로필이 따른다(5단계).
- 실측 데이터 품질(지표 명세 「데이터 품질」 Q1~Q8)이 검증 범위를 줄인다. 실제 6일 기록은 확정 라벨·집중
  세션·브라우저 URL이 0건이라 DF-4는 C1·C2와 날짜 읽기만 확인한다. C3~C7과 사이트는 사례·무작위·골든
  일지 정답으로만 확인한다.
- 오차는 층별로 나눈다: 수집 누락·지연(GD-2 L1), 전송 손실(활동 관찰 범위), 구간화 규칙(GD-2 L2), 지표 정의
  (사례·차등·GD-2 L3). 한 층의 불일치를 다른 층의 허용 오차로 덮지 않는다.
- 측정 결과를 본 뒤 판정 기준(허용 오차, 성능 예산)을 바꾸지 않는다. 바꿔야 하면 새 사전 등록으로 먼저 적는다.

## 대응이 약한 곳

검사기는 "테스트 1개 이상"만 확인한다. 아래는 그 기준은 넘지만 근거가 약한 대응이다.

- AC-8012·AC-8014는 지금 존재하는 테스트가 없다(API-1~API-3, 7단계). 일시중지 저장(FR-25)이 아직 구현되지
  않았다.
- AC-8013·8015·8016·8023과 I1~I7은 지금 상태 모델(SM-1·SM-2)로만 확인한다. 모델은 원천 변경 2회·배치 2개·
  날짜 1개 범위이고, 실제 PG에서의 확인은 동작 전제(SM-4)뿐이다. TX·FI가 생기기 전까지 구현 대응은 없다.
- I8·I9와 AC-8028·8029는 지금 상태 모델(SM-3)과 PG 최소 재현(SM-4)으로만 확인한다. 모델은 시간대 변경 1회·날짜
  3개 범위이고, 시간대를 두 번 바꾸는 경우, 오늘 경계, 일광 절약 시간, F-1의 재시도·격리 열과의 결합은 모델링하지
  않았다. 시간대 변경 API가 없어 7단계에서도 테스트 전용 경로로 검증해야 한다. I8은 지원 시차 최대 14시간에
  기대며, 시차 24시간 이상인 시간대를 지원하면 표시 범위를 넓히고 다시 검사한다.
- E1·E4·E5는 지금 사례 단위로만 확인한다(무작위 입력에서 등식을 직접 검사하는 도구가 없다). SC-8이 생기기
  전까지 무작위 입력의 근거는 두 구현의 차등(DF-2)뿐이다.
- E7(원천 불변)은 참조 구현이 순수 함수라 구조로 성립할 뿐, 제품 경로의 테스트는 API-10뿐이다.
- AC-8024~8027은 장애 주입(FI)과 상태 모델(SM-2)이 대응하지만 FI는 7단계 작성이라 아직 실행한 테스트가 없다.
- C2-B11(자정 정각 전환)처럼 변이 하나를 잡는 사례가 하나뿐인 곳이 있다. MU-3은 제품 구현에서 같은 탐지력이
  유지되는지 다시 확인한다.

## 열린 결정

- E2E-1을 둘지: [테스트 규칙](../tests/AGENTS.md)은 E2E를 PRD 핵심 시나리오에 한정한다. 활동 분석이 핵심
  시나리오인지, 아니면 API-4·API-5 통합 테스트로 충분한지 정해야 한다.
- 속성 테스트 생성기: SC-8·DF-5·MR-7에 Hypothesis를 개발 의존성으로 더할지, 산출물 `gen.py`(표준 라이브러리,
  seed 고정)를 옮길지. Hypothesis는 실패 입력을 줄여 주지만 의존성이 하나 는다.
- 상태 모델을 저장소에 둘지(위 「지금 있는 것과 7단계에 만들 것」).
- TX·FI 통합 테스트의 실행 시간 예산과 CI 포함 여부(프로세스 kill·DB 재시작 시나리오는 느리다).
