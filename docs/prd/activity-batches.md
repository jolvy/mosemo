# 활동 배치 수락과 비동기 처리 PRD

## 문제와 배경

macOS 클라이언트는 수집한 활동 레코드를 함께 전송하고, 서버의 원본 저장과
타임라인 계산이 끝나기 전에 전달 수락 여부를 확인해야 한다. 응답 유실에 따른
재전송은 안전해야 하며, 개별 원본의 중복·순번 충돌과 배치 전체를
실패시키는 집중 세션 연결 오류를 구분해야 한다. 사용자는 DB에 반영된 결과를
열린 타임라인 화면에서 확인한다.

## 목표와 비목표

### 목표

- 한 Device의 활동 레코드를 배치로 수락하고 DB 처리를 별도로 수행한다.
- 전달 수락, 원본별 거절, 채택 집합의 DB 반영을 구분한다.
- 재전송·순번 누락·역순 도착에도 원본을 중복 반영하지 않는다.
- 계정·Device 격리와 원본·타임라인 변경의 원자성을 유지한다.
- 클라이언트 배치 전송·재시도와 열린 화면의 주기적 조회를 정의한다.

### 비목표

- 운영 Kafka 배포·다중 브로커 장애 내성·운영 retention·복제 정책, Outbox·CDC.
- 원본별 부분 실패를 클라이언트에 알리는 응답·조회·복구 계약.
- 단조 시계 도입, 원본 시각 자동 보정, 단일 활성 Device 강제.
- 다른 macOS 기능·UI 전체 재설계·인증 정책 변경, 분석·AI 신규 기능.

## 사용자와 사용자 시나리오

- 활동 수집 클라이언트는 한 Device의 원본들을 모아 보내고 전달 수락 후 다음
  배치를 전송한다. DB 처리 완료까지 업로드 요청을 유지하지 않는다.
- 클라이언트는 응답이 확인되지 않으면 같은 식별자와 내용으로 재전송한다.
- 서버는 원본별 중복·충돌과 집중 세션 연결을 검사해 채택할 원본을 결정한다.
- 사용자는 화면을 열거나 재활성화하면 최신 타임라인을 조회하고, 화면이 열려 있는
  동안 후속 반영 결과를 주기적으로 확인한다.
- 후속 범위에서 개발자는 처리 실패 원본과 보류 배치를 진단 경로에서 확인한다.

## 현재 구현 범위

애플리케이션과 독립된 Kafka를 통한 배치 수락과 별도 처리, 원본별 채택·거절, 타임라인 갱신,
정상 DB 처리와 중복 안전성을 이번 목표로 둔다. 장애 재시도·실패 보관·복구는 후속이다. 단건 활동 POST는 배치 API로
대체한다. 클라이언트 연동은 배치 생성·전송·수락 확인·재시도와 타임라인 polling이다.

날짜별 조회·구간 계산·라벨 적용성은 [관찰 타임라인 PRD](observation-timeline.md)를,
집중 세션 연결의 유효성은 [집중 세션 PRD](focus-sessions.md)를 따른다.

## 이번 Kafka 전환의 합의 범위

2026-10-18 승인한 정상 전달·처리 설계를 반영한 목표 문서다. 구현 완료 보고가 아니다.
[Plan Issue #61](https://github.com/jolvy/mosemo/issues/61)을 기준으로 서버를 변경하며
클라이언트 요구는 기존 범위로 유지한다.

- 실패·복구의 논의·설계·구현은 후속이다. 기존 FR-15·FR-16, AC-6013·AC-6020과
  FR-8·FR-13·AC-6012·AC-6019의 실패 원본 보관 부분은 이번 완료 조건에서 제외한다.
  배치 전체 rollback·소유권·시간·중복 검증은 이번에도 유지한다.
- BatchFailureHandler·BatchRecoveryService는 v1 객체 경계만 두고 로직은 비운다.
  Consumer 중단·partition 차단 등 대체 실패 정책도 이번에 확정하지 않는다.
- 아래 기존 실패 보관·보류·재처리 요구는 삭제하지 않고 후속 요구로 보존한다.

현재 서버의 공개 수락 경로는 Kafka Publisher만 실행하며 Consumer는 별도
프로세스로 실행한다. 직접 DB 처리용 `/activities/batches/legacy`는 별도 계약이다.
정상 전달 경로의 재현 명령과 TC-1~9 테스트 대응은
[README](../../README.md#real-broker-tests), 실행 결과와 검증한 revision·diff는
[검증 Issue #66](https://github.com/jolvy/mosemo/issues/66)에서 관리한다.
이는 위 후속 요구나 macOS 인수 조건의 완료를 뜻하지 않으며,
실패·복구가 미구현인 현재 서버를 운영 준비 완료로 보지 않는다.

## 기능 요구사항

### Kafka 메시지·실행·receipt 계약

- HTTP 요청은 기존 batchId·deviceId·records이며 accountId는 인증에서 결정한다.
  별도 Pydantic 내부 메시지의 value에는 accountId·batchId·deviceId·records를 담는다.
  인증 계정으로 value를 채운 뒤 같은 UUID의 UTF-8 문자열을 key로 생성한다.
  accountId header는 사용하지 않으며 Consumer가 key·value의 계정 일치를 검증한다.
- HTTP 원본 bytes 보존과 JSON 문자열의 이중 포장은 요구하지 않는다.
- 토픽 초기화 설정으로 partition 2개를 생성한다. 앱은 개수·번호를 직접 지정하지
  않고 기본 key partitioner를 사용한다. 계정 전용 partition은 아니다.
- partition 내부는 DB commit·해당 위치 offset commit 후 다음 배치를 시작한다.
  partition 간은 병렬로 최대 두 배치를 처리한다. 다른 partition의 미처리 offset을
  넘어 확정하지 않는다. 계정 순서는 Kafka 기록 순서이며 관찰 원본 정렬 규칙과 구분한다.
- API와 Consumer는 별도 진입점·프로세스로 실행하고 코드·업무 처리를 공유한다.
- 발행은 acks=all·producer idempotence를 사용한다. DB 중복 보호를 대신하지 않는다.
  유효한 committed offset은 이어서 읽고 없을 때에만 earliest로 현재 보관된 처음부터 읽는다.
- Consumer 정상 종료는 새 배치 실행을 멈추고 실행 중인 최대 두 배치의 DB·offset 확정을
  최대 30초 기다린 후 자원을 정리한다. 전체 대기 메시지를 처리하는 종료가 아니며
  FastAPI 서버의 종료 대기 설정과 구분한다.
- 2026-10-20 추가 승인: Kafka 시작 예외는 단일 API worker·Consumer 프로세스의
  비정상 종료로 전파하며 같은 프로세스 안에서 시작을 재시도하지 않는다. 시작 task의
  취소도 프로세스 경계로 전파한다. Consumer의 SIGINT·SIGTERM 종료 요청은 시작을
  취소하고 정상 종료할 수 있다. 재시작 책임은 외부 supervisor에 있으며 실제 배포·재시작
  설정은 범위 밖이다. 부분 시작된 FastStream 내부 자원의 정리 완료는 보장하지 않는다.
  정상 종료의 최대 30초 대기와 DB commit 후 offset ACK 계약은 유지한다.
- Kafka 발행 확인은 최대 5초 기다리며 기존 HTTP 전체 수락 제한도 유지한다.
  Publisher 동시 발행 수와 내부 Kafka 메시지 크기에 애플리케이션 자체의 추가 제한을
  두지 않는다. 기존 HTTP 본문 512 KiB와 Kafka·클라이언트 자체 한도는 적용된다.
  최대 유효 HTTP 입력의 실제 직렬화 결과가 전달 가능한지 검증한다.
  로컬 단일 broker의 ACK를 운영 복제 내성으로 표현하지 않는다.
- receipt는 accountId·deviceId·batchId로 식별하고 fingerprint·results·processedAt을
  유지한다. fingerprint는 검증된 batchId·deviceId·records를 기본값 포함·키 정렬·배열
  순서 유지로 정규화해 SHA-256 64자리 해시로 저장한다. 같으면 기존 결과, 다르면 충돌이다.
- receipt source와 Processor의 원본 bytes 인자를 제거한다. 운영·보존 데이터가 없다는
  사용자 전제로 기존 생성 migration에서 컬럼을 직접 제거하며 새 이관 migration은 만들지 않는다.

### 배치 수락

`POST /api/v1/activities/batches`는 Bearer 인증을 요구한다. 계정은 인증 결과에서
결정하고 body에서 받지 않는다. `deviceId`는 해당 계정에 등록된 Device여야 한다.

| 항목 | 계약 |
| --- | --- |
| 최상위 요청 | UUID batchId, UUID deviceId, records 배열 |
| 원본 개수 | 1~200건 |
| 본문 크기 | 비압축 JSON 전체 512 KiB 이하 |
| 개별 원본 | eventId, sequence, recordType, observedAt, timezoneId, utcOffsetMinutes, 선택 focusSessionId, 종류별 context 또는 state/reason |
| Device 지정 | 최상위 deviceId를 모든 원본에 적용하며 개별 원본에는 반복하지 않음 |
| 성공 응답 | 202, batchId와 status: accepted만 반환 |

입력 검증과 Device 귀속 확인이 끝난 배치 전체를 Kafka에 발행하고 브로커 ACK를
확인한 뒤 수락 응답을 반환한다. Handler의 원본 저장·타임라인 갱신·DB commit은
기다리지 않는다. 원본별 처리 결과,
최초 저장 시각, DB 완료 시각은 수락 응답에 포함하지 않는다.

| 수락 실패 조건 | HTTP 상태 |
| --- | --- |
| 인증 실패 | 401 |
| Device 미등록·귀속 불일치 | 404 |
| JSON 본문 크기 초과 | 413 |
| 스키마·빈 배열·건수·필드 검증 실패 | 422 |
| 발행 실패·ACK 제한 시간 초과·미시작·종료 중·용량 부족 | 503 |

오류는 공통 오류 형식을 따른다. 입력 검증 실패 시 일부 원본도 전달하지 않으며,
배치 전체를 하나의 메시지로 발행한다. ACK를 확인하지 못하면 202를 반환하지
않지만 브로커에는 기록됐을 수 있으므로 같은 batchId·내용으로 재시도한다.

### 원본별 처리와 트랜잭션

- 같은 계정·Device·batchId와 같은 내용의 재시도는 기존 결과를 중복 반영하지 않는다.
  같은 batchId의 내용 변경은 내부 거절·진단 대상이며 기존 결과를 덮어쓰지 않는다.
  HTTP 수락 단계에서 동기 DB 대조로 즉시 409를 반환하는 계약은 두지 않는다.
- 이미 저장된 eventId는 다시 처리하거나 덮어쓰지 않는다. 다른 계정·Device의
  원본이나 처리 결과를 재사용·노출하지 않는다.
- 같은 Device sequence의 서로 다른 원본은 먼저 온 기록을 유지하고 후발 원본만
  거절한다. 한 배치 안의 중복도 한 번만 반영하고 승자 선택은 결정적이어야 한다.
- Handler에서 집중 세션 소유권·시간 검증에 실패하면 배치 전체를 롤백하고
  실패 원본 보관은 후속으로 남긴다. 해당 원본만 제외하거나 연결만 제거해 저장하지 않는다.
- 채택된 원본과 타임라인 변경은 하나의 DB 트랜잭션으로 반영한다. DB 장애가
  발생하면 채택 집합의 변경을 모두 롤백한다.
- 같은 Device에서 sequence가 증가하는데 관찰 시각이 감소하면 배치 전체를
  롤백한다. 실패 원본 보관은 후속이다. 시각이나 구간 경계를 임의로 보정하지 않는다.

### 순서와 타임라인 반영

Device 내 순서는 sequence다. 연속된 숫자를 요구하지 않으며, 미사용 낮은
sequence가 늦게 도착해도 관찰 시각 역행이 없다면 저장하고 재구성한다.
여러 Device를 합친 순서와 구간 의미는 관찰 타임라인 PRD에서 정의한다.

append는 마지막 상태에서 증분 계산하고, 과거 변경은 배치 단위로 묶어 영향을
받는 지점부터 계산한다. 기존 상태·경계와 일치하는 안전한 지점에서 중단한다.
문맥 동등성, 불투명 활동, 수집 공백, 60초 병합, 길이 없는 구간, 날짜 경계,
내용 버전과 라벨 적용성은 보존한다.

### 장애 처리·복구 — 후속 요구

partition별 순차·partition 간 최대 두 배치 처리와 HTTP 요청에서 독립된 DB
세션·트랜잭션은 이번 범위다. Publisher에는 별도 동시 발행 수 제한을 두지 않는다.
아래 재시도·실패 보관·Device별 보류·재처리는 후속 요구로 보존하며 이번 완료 조건이 아니다.

일시 장애는 최초 시도 포함 최대 5회 처리한다. 재시도 대기에는 jitter를 적용하고
상한은 1/2/4/8초다. 중복·sequence 충돌은 정상 처리 결과이며, 집중 세션 연결
오류·관찰 시각 역행은 재시도로 해결할 일시 장애로 취급하지 않는다. 실패·보류
원본은 제한된 개발용 진단 경로에 보관한다. Kafka에서 실패·보류·재처리와 offset을 조율하는 후속 방식은 [Kafka 전달 ADR](../adr/0006-deliver-activity-batches-through-kafka.md)에서 결정한다.

실패한 배치와 같은 계정·Device의 후속 배치는 수락 순서대로 보류한다. 다른
Device·계정의 배치는 계속 처리한다. 개발용 재처리 경로로 실패한 선두 배치를
다시 처리하고, 성공하면 후속 보류 배치를 원래 수락 순서대로 해제한다. 실패
원인이 해소되지 않으면 재처리는 다시 실패하고 후속 배치는 보류 상태를 유지한다. 이 실패·복구 동작은 후속 범위다.

### 클라이언트 전송과 조회

- 전송 가능한 상태에서 대기 10초, 최대 200건, 비압축 본문 512 KiB 중 먼저
  도달한 조건으로 전송한다. Device별 전송 중인 배치는 하나로 제한한다.
- 수락 응답이 확인되면 해당 로컬 배치를 제거한다. 적체가 있으면 다음 배치를
  즉시 전송한다. 수락 응답이 확인되지 않으면 원본과 batchId·내용을 보존한다.
- 재시도에는 full jitter를 적용하고 backoff 상한은 1/2/4/8/16/32/60초다.
  서버의 Retry-After를 존중한다.
- 수락 전 명확한 413을 받으면 원본 ID·sequence·내용을 유지해 재분할하고
  새 batchId를 사용할 수 있다. 단건 원본 크기 초과에도 원본을 절삭하지 않는다.
- 화면 열기·재활성화 시 즉시 조회하고, 열린 화면은 초기 5초 간격으로 polling한다.
  화면을 숨기면 중단하고 요청 겹침·오래된 응답 반영을 방지한다. 조회 실패 시
  기존 화면을 유지하고 backoff한다.

## 정책·제약·엣지케이스

`accepted`는 Kafka 브로커의 발행 ACK를 확인했다는 뜻이다. 원본별 처리 성공·DB
commit·consumer offset commit은 뜻하지 않는다. 보존과 장애 내성의 범위는
연결한 Kafka의 복제·저장·retention 설정에 따른다.

| 경계 | 결과 |
| --- | --- |
| HTTP 스키마·필드 검증 실패 | 배치 전체 미전달 |
| Handler의 원본 중복 | 기존 저장 결과 보존, 중복 반영 없음 |
| Handler의 sequence 충돌 | 해당 원본 제외, 나머지 채택 원본 반영 |
| 집중 세션 연결 오류·관찰 시각 역행·DB 처리 장애 | 배치 전체 변경 롤백 |

집중 세션 연결의 소유권·시간 오류는 수락 후 Handler에서 배치 전체 실패로
처리한다. 수집 중단 레코드에 허용되지 않는 연결처럼 요청 스키마에서 거절하는
입력은 수락하지 않고 전체 미전달로 처리한다.
수락 후 발견한 원본별 거절을 수락 응답에 뒤늦게 추가하거나 공개 부분 실패
조회·복구 API를 제공하지 않는다.

원본 채택과 재처리에도 계정 격리·중복 안전성·필요한 DB 동시성 보호를 유지한다.
Kafka의 partition 순서만으로 DB 원자성이나 계정·Device별 실패 격리가
보장된다고 가정하지 않는다.

## 비기능 요구사항

- 개인정보 보호와 기존 종류별 입력 검증·공통 오류 계약을 유지한다.
- HTTP 요청 세션·토큰·요청 자원의 수명을 비동기 처리에 의존시키지 않는다.
- Consumer는 수신한 메시지마다 무제한 처리 task를 생성하지 않고 partition별
  실행을 관리하며, 종료 시 소비 task·DB 세션·트랜잭션을 정리한다.
  Publisher에는 별도 동시 발행 수 제한을 두지 않으므로 API 전체 메모리 상한을 보장하지 않는다.
  처리 task의 예외를 관찰하지 않은 채 남기지 않는다.
- 정상 경로에서 매 배치마다 계정 원본 전체 조회나 구간 전체 삭제·재삽입을 하지 않는다.
  전체 재생과 증분·부분 재생의 관찰 의미가 같아야 한다.
- 응답 지연·처리량의 수치 목표는 정하지 않는다. 정상 계산에 근거 없는 짧은
  hard timeout을 적용하지 않는다.

## 확장 방향

Kafka 연결 정보는 환경별로 구성하며 개발·운영 환경에 같은 발행 수락 계약을
적용한다. 개발 환경의 로컬 Docker 실행 방식으로 운영 배포 방식을 제한하지 않는다.
운영 환경의 복제·retention·장애 대응 정책은 별도로 정의한다.
클라이언트의 부분 실패 통지·복구 계약은 후속 범위로 둔다.

기존 이력의 최초 정렬 전환은 현재 계정 전체를 한 번 재구축한다. 이를 부분
재구성으로 최적화하는 후속 작업이 필요하다. 정렬이 달라지는 지점을 먼저 식별하고,
최초 영향 구간부터 마지막 변경 지점을 지난 안전한 수렴 경계까지 재구성해야 한다.
중간 구간이 기존 결과와 같다는 이유만으로 이후 구간을 재사용해서는 안 된다.
최적화 전까지 최초 전체 재구축을 유지하며, 변경 지점 탐색 비용과 재구성 비용을
구분해 검증한다.

## 인수 조건

- AC-6001: 인증 계정 소유 Device의 유효한 1~200건 배치를 발행하고 브로커 ACK를 확인하면,
  Handler의 DB 처리가 대기 중이어도 batchId와 accepted만 담은 202가 먼저 반환된다.
  ACK를 확인하기 전에는 202를 반환하지 않는다.
- AC-6002: 잘못된 스키마·빈 배열·건수 초과는 422, 512 KiB 초과는 413,
  인증 실패는 401, Device 미등록·귀속 불일치는 404이며 일부 원본도 전달하지 않는다.
- AC-6003: 발행 실패·5초 내 ACK 미확인·미시작·종료 중·전달 자원 부족에는 503으로 응답하고
  수락 성공을 반환하지 않는다.
- AC-6004: 동일 계정·Device·batchId와 같은 내용의 재시도는 결과를 중복 반영하지
  않으며, 다른 내용은 기존 결과를 덮어쓰지 않고 내부 거절·진단 대상으로 처리한다.
- AC-6005: 저장된 eventId의 재전송은 다시 반영하지 않고, Device별 sequence 충돌은
  먼저 온 기록을 보존하며 충돌하지 않은 원본은 반영한다. 계정·Device 경계도 보호한다.
- AC-6006: 배치 내부 중복은 한 번만 반영하고 충돌 승자는 결정적이다.
- AC-6007: sequence가 누락되거나 미사용 낮은 sequence가 늦게 도착해도 연속성을
  기다리지 않고 저장하며, 관찰 시각 역행이 없는 입력의 타임라인을 재구성한다.
- AC-6008: DB 처리 장애 시 해당 채택 집합의 원본과 구간 변경을 모두 롤백한다.
- AC-6009: 동일 Device의 순서는 sequence로 정하고 다른 Device의 sequence를
  전역 순번으로 비교하지 않는다. 서로 다른 Device의 관찰 시각이 같으면
  deviceId·sequence·eventId 오름차순으로 정렬해 전송 순서와 무관한 결과를 얻는다.
- AC-6010: append·과거 삽입·배치 내 여러 과거 변경의 결과가 전체 재생과 같은
  관찰 의미를 가지며, 정상 경로는 증분 또는 영향 범위 재구성을 사용한다.
- AC-6011: 배치 처리 후에도 문맥 동등성·불투명 활동·명시적 공백·60초 병합·길이 없는
  구간·날짜 경계·내용 버전·라벨 적용성이 기존 계약대로 유지된다.
- AC-6012: 유효한 집중 세션 연결은 기존 소유권·시간·수집 상태 규칙대로 반영한다.
  Handler의 집중 세션 소유권·시간 검증에 실패하면 배치 전체의 원본·타임라인
  변경을 롤백한다. 실패 원본 보관 부분은 후속 요구로 유지한다.
- AC-6013: [후속] 일시 Handler 장애는 최초 포함 최대 5회와 1/2/4/8초 jitter 상한으로
  재시도하고 정상 중복·sequence 충돌에는 장애 재시도를 하지 않는다.
- AC-6014: Handler는 HTTP 요청과 독립된 메시지별 세션·트랜잭션을 사용하며,
  정상 실행·종료에서 자원과 세션을 정리하고 미관찰 task 예외를 남기지 않는다.
  Kafka 시작 실패·task 취소는 단일 API worker·Consumer 프로세스 종료로 전파하며
  내부 시작 재시도 없이 외부 supervisor에 재시작을 맡긴다. 라이브러리 부분 시작 자원의
  정리 완료를 보장하는 조건은 아니며 실제 supervisor 설정은 범위 밖이다.
- AC-6015: 클라이언트는 전송 가능한 상태에서 10초·200건·512 KiB 중 먼저 도달한
  조건으로 전송하며 Device별 한 배치만 전송 중으로 둔다. 수락 후 로컬 배치를
  제거하고 적체가 있으면 즉시 다음 배치를 전송한다.
- AC-6016: 응답 미확인 시 로컬 원본과 batchId·내용을 보존해 지정 backoff와
  Retry-After에 따라 재시도한다. 수락 전 명확한 413에는 원본을 보존한 재분할과
  새 batchId를 허용하며 단건 초과 원본을 절삭하지 않는다.
- AC-6017: 화면 열기·재활성화 즉시 조회하고 열린 화면은 초기 5초 간격으로 갱신한다.
  숨김 시 중단하며 겹치는 요청·오래된 응답을 방지하고 오류 시 기존 화면을 유지한다.
- AC-6018: 수락 경로의 API 설명과 실행 설정에서 accepted가 Kafka 발행 ACK를
  뜻하며 DB 처리 완료와 구분됨을 확인할 수 있다. 원본 보존·장애 내성의 범위는
  해당 환경의 Kafka 설정을 기준으로 설명한다.

- AC-6019: 같은 Device에서 sequence가 증가하는데 관찰 시각이 감소하면 배치
  전체의 원본·타임라인 변경을 롤백한다. 실패 원본 보관 부분은 후속 요구로 유지한다.

- AC-6020: [후속] 배치 처리 실패 후 같은 계정·Device의 후속 배치는 보류하고 다른
  Device·계정의 배치는 처리한다. 실패한 선두 배치의 재처리 성공 후 보류 배치를
  수락 순서대로 처리하며 실패·보류 원본의 보관량도 제한한다.

- AC-6021: 내부 메시지 value는 인증 accountId·batchId·deviceId·records이며 key는 같은
  accountId의 UTF-8 문자열이다. header에 계정을 중복하지 않고 Consumer가 일치를 검증한다.
- AC-6022: 초기 partition 2개에서 내부 순차·partition 간 병렬 처리를 지원하며 최대 두
  배치를 실행한다. API·Consumer는 별도 프로세스이며 계정 순서는 Kafka 기록 순서다.
- AC-6023: acks=all·producer idempotence를 사용하고 정상 DB commit 후 해당 offset을
  확정한다. 두 commit 사이 재전달에도 receipt로 중복 반영하지 않는다.
- AC-6024: 유효한 offset에서 재개하며 없을 때에만 earliest를 사용한다. 정상 종료는 새
  실행을 멈추고 진행 중 배치만 최대 30초 기다리며 broker·DB 자원을 정리한다.
  이는 Consumer 종료 대기이며 FastAPI 서버 종료 설정과 구분한다.
- AC-6025: source 없는 초기 스키마와 Processor 입력을 사용한다. fingerprint는 유지하고
  동일 식별자의 같은 내용은 기존 결과, 다른 내용은 충돌로 판정한다. 기존 생성 migration을 수정한다.

## 미결정 사항과 가정

단건 원본 자체가 크기 제한을 초과할 때의 사용자 진단·복구 방법과 응답 지연·처리량의
수치 목표는 미정이다. 크기 초과 원본 보존·비절삭 원칙은 유지한다.

클라이언트는 수락 응답 후 로컬 배치를 제거하며, 수락 뒤 서버 처리 실패를 사용자에게
통지·복구하는 계약은 현재 범위에 없다. Kafka에서 실패·보류 상태를 복구하는
구체적 방식은 후속이다. 정상 처리의 DB commit 후 offset 확정은 합의됐으며
Kafka 전달 ADR을 따른다.
