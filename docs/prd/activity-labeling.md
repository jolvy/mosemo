# 개인화 활동 라벨링 PRD

## Problem Statement

사용자는 관찰 타임라인에서 앱·창 등의 문맥과 시간은 볼 수 있지만, 그 시간이 자신에게 어떤 활동이었는지는 기록하거나 라벨별로 집계할 수 없다. 같은 관찰이라도 사람마다 `coding`, `shopping`처럼 다른 라벨을 붙일 수 있다. 활동이 쌓일 때마다 즉시 판단할 수도 없으므로, AI 제안을 나중에 모아 검토하고 고칠 수 있어야 한다. AI의 미확정 판단이 공식 활동 시간에 섞이면 대시보드를 신뢰하기 어렵다.

## Solution

관찰 활동 구간의 사실 기록과 별도로 사용자별 라벨 목록, AI 라벨 제안, 사용자 확정값을 관리한다. AI는 종료된 라벨 대상 구간에 사용 중인 라벨 하나를 제안하거나 미분류로 남긴다. 사용자는 라벨 타임라인에서 제안을 확인·변경하고, 한 항목이나 여러 항목을 나중에 확정한다. 시간상 이어지고 라벨 및 확정 상태가 같은 구간만 한 행으로 보여주되, 대시보드는 떨어져 있는 구간까지 라벨별로 합산한다. 합계에는 사용자 확정값만 넣고 검토 대기, 확정된 미분류, 불투명 활동은 각각 구분한다. 확정과 정정은 같은 사용자의 다음 제안에 바로 참고한다.

## User Stories

1. 사용자로서 내 활동의 의미를 나타내는 라벨을 보고 싶다. 그래야 관찰된 앱 종류와 내가 한 일을 구분할 수 있다.
2. 사용자로서 기본 라벨 목록을 받고 싶다. 그래야 처음부터 모든 라벨을 만들지 않아도 된다.
3. 사용자로서 사용자 정의 라벨을 만들고 싶다. 그래야 같은 관찰을 내 방식으로 분류할 수 있다.
4. 사용자로서 내 라벨 이름을 바꾸고 싶다. 그래야 과거 기록까지 현재 사용하는 이름으로 볼 수 있다.
5. 사용자로서 사용하지 않는 라벨을 보관하고 싶다. 그래야 과거 기록은 남기면서 새 제안과 선택 목록에서는 빼둘 수 있다.
6. 사용자로서 같은 앱을 사용했어도 활동의 의미에 따라 다른 라벨을 붙이고 싶다. 그래야 앱이 라벨을 결정하지 않는다.
7. 사용자로서 서로 다른 앱·창을 오가더라도 같은 의미의 활동에 같은 라벨을 붙이고 싶다. 그래야 관련 문서를 읽고 코드를 고친 시간을 함께 볼 수 있다.
8. 사용자로서 한 관찰 활동 구간에 대표 라벨 하나를 붙이고 싶다. 그래야 현재 지원하는 분류 단위가 명확하다.
9. 사용자로서 종료된 관찰 활동 구간에 AI가 제안한 라벨을 보고 싶다. 그래야 반복적인 분류 작업을 줄일 수 있다.
10. 사용자로서 판단 근거가 부족한 구간은 미분류 제안으로 보고 싶다. 그래야 근거 없는 확신을 강요받지 않는다.
11. 사용자로서 AI가 제안하지 못하거나 실패한 구간도 검토 대기 상태로 보고 싶다. 그래야 활동이 조용히 사라지지 않는다.
12. 사용자로서 라벨 제안과 확정 라벨을 구분해서 보고 싶다. 그래야 어느 시간이 아직 검토 대상인지 알 수 있다.
13. 사용자로서 AI 제안을 그대로 승인하고 싶다. 그래야 맞는 판단을 빠르게 확정할 수 있다.
14. 사용자로서 다른 라벨을 골라 제안을 바꾸고 싶다. 그래야 AI의 판단이 내 분류를 대신하지 않는다.
15. 사용자로서 제안을 바꾼 뒤 별도로 확정하고 싶다. 그래야 편집 중인 선택이 공식 기록이 되지 않는다.
16. 사용자로서 미분류 상태를 명시적으로 확정하고 싶다. 그래야 확인했지만 분류하지 않은 활동을 미검토 활동과 구분할 수 있다.
17. 사용자로서 활동이 쌓인 뒤 검토 대기 항목을 모아보고 싶다. 그래야 매 구간마다 승인할 필요가 없다.
18. 사용자로서 시간상 이어진 동일 라벨·동일 확정 상태의 구간을 한 행으로 보고 싶다. 그래야 반복되는 짧은 구간을 읽기 쉽다.
19. 사용자로서 한 행으로 묶인 구간 전체를 같은 선택으로 확정하고 싶다. 그래야 묶음의 모든 원본 구간을 각각 누르지 않아도 된다.
20. 사용자로서 서로 다른 여러 항목의 선택을 한 번에 제출하고 싶다. 그래야 모아둔 활동을 한 차례 검토로 처리할 수 있다.
21. 사용자로서 중간에 다른 라벨의 구간이 있으면 앞뒤의 같은 라벨을 별도 행으로 보고 싶다. 그래야 시간순 활동을 숨기지 않는다.
22. 사용자로서 두 구간 사이에 관찰되지 않은 시간이 있으면 같은 라벨이라도 별도 행으로 보고 싶다. 그래야 연속 활동으로 오해하지 않는다.
23. 사용자로서 라벨이 같아도 제안과 확정 상태가 다르면 별도 행으로 보고 싶다. 그래야 검토 대상을 정확히 고를 수 있다.
24. 사용자로서 같은 시각에 끝나고 시작하는 0초 관찰 구간도 타임라인에서 잃지 않고 싶다. 그래야 관찰된 순서가 보존된다.
25. 사용자로서 불투명 활동을 별도 항목으로 보고 싶다. 그래야 개인정보 보호로 가려진 활동을 미분류나 수집 공백으로 오해하지 않는다.
26. 사용자로서 불투명 활동에는 AI 제안이나 수동 라벨 선택이 나타나지 않길 원한다. 그래야 정보가 없는 활동을 임의로 분류하지 않는다.
27. 사용자로서 수집 공백을 활동 시간으로 보지 않길 원한다. 그래야 관찰하지 못한 시간을 실제 활동으로 오해하지 않는다.
28. 사용자로서 오늘의 확정된 라벨별 활동 시간을 보고 싶다. 그래야 `coding`과 `shopping`에 쓴 시간을 비교할 수 있다.
29. 사용자로서 떨어져 있는 같은 라벨의 확정 구간을 대시보드에서 합산해 보고 싶다. 그래야 시간순 행의 개수와 총 시간을 혼동하지 않는다.
30. 사용자로서 미확정 제안이 라벨별 합계에 들어가지 않길 원한다. 그래야 AI 판단을 내가 승인한 활동 시간으로 오해하지 않는다.
31. 사용자로서 검토 대기 활동 시간을 별도로 보고 싶다. 그래야 아직 확인할 분량을 알 수 있다.
32. 사용자로서 확정된 미분류 시간을 별도로 보고 싶다. 그래야 확인한 미분류 활동이 검토 대기에 섞이지 않는다.
33. 사용자로서 불투명 활동 시간을 별도로 보고 싶다. 그래야 분류 대상 밖의 관찰 시간을 알 수 있다.
34. 사용자로서 확정 라벨을 나중에 정정하고 싶다. 그래야 잘못 분류한 기록을 바로잡을 수 있다.
35. 사용자로서 정정 직후 대시보드 합계가 최신 확정값을 반영하길 원한다. 그래야 과거 합계가 남지 않는다.
36. 사용자로서 내 확정·정정 이력이 다음 AI 제안에 바로 반영되길 원한다. 그래야 같은 유형의 활동에서 점점 내 분류 방식에 맞는 제안을 받는다.
37. 사용자로서 한 번의 정정이 모든 유사 구간에 자동 적용되지 않길 원한다. 그래야 활동 의미가 달라진 경우도 직접 판단할 수 있다.
38. 사용자로서 과거에 생성된 검토 대기 제안이 조용히 바뀌지 않길 원한다. 그래야 검토 중인 판단의 기준이 흔들리지 않는다.
39. 사용자로서 다른 사용자의 확정 이력이 내 개인화 사례로 섞이지 않길 원한다. 그래야 내 라벨 체계와 활동 정보가 분리된다.
40. 사용자로서 늦게 도착한 관찰 때문에 관찰 구간이 재구성되어도 잘못된 확정 라벨이 다른 활동에 조용히 붙지 않길 원한다. 그래야 기록과 집계를 신뢰할 수 있다.
41. API 소비자로서 인증된 계정의 라벨·제안·확정·집계만 조회하고 변경하고 싶다. 그래야 다른 계정의 활동이 노출되거나 수정되지 않는다.
42. 사용자로서 아직 열린 관찰 활동 구간을 확정 대상이나 확정 활동 시간으로 보지 않길 원한다. 그래야 종료가 확인되지 않은 시간을 앞질러 분류하지 않는다.
43. 사용자로서 새 분석으로 검토 대기 제안이 바뀌어야 한다면 그 변경을 확인하고 싶다. 그래야 내가 보던 제안이 설명 없이 대체되지 않는다.

## Implementation Decisions

- 기존 관찰 타임라인은 사실 기록으로 유지한다. 라벨 타임라인은 그 위에 제안·확정 상태를 결합한 사용자용 보기이며, `활동 흐름`을 새 도메인 단위로 도입하지 않는다.
- 라벨은 계정별 목록으로 관리한다. 기본 라벨은 `코딩`, `학습`, `소통`, `쇼핑`, `여가` 다섯 개로 시작하고 사용자 정의 라벨도 지원한다. 이름 변경은 과거 표시에도 반영한다. 보관 라벨은 과거 확정 기록에 남지만 새 활동의 제안·선택 후보에서 제외한다.
- 현재 분류 단위는 관찰 활동 구간 하나다. 한 구간에는 대표 라벨이 최대 하나이며 구간 내부의 시간 분할은 하지 않는다. 상세 문맥이 있는 구간만 라벨 대상이다. 불투명 활동과 수집 공백은 대상에서 제외한다.
- 제안은 관찰 활동 구간이 종료된 뒤 생성한다. 종료 전에는 AI 판단이나 확정을 요구하지 않는다. 제안 생성 실패는 자동 확정이나 기록 누락으로 이어지지 않으며 재시도 또는 사용자 검토가 가능한 상태로 남긴다.
- AI는 해당 사용자의 활성 라벨만 후보로 받고, 개인정보 필터를 통과한 관찰 문맥과 같은 사용자의 최신 확정 사례를 참고한다. 초기 개인화는 공통 AI 제안에 사용자별 유사 사례 검색·순위 조정을 더한다. 근거가 부족하면 미분류로 남긴다. 사용자별 모델 미세 조정과 다른 사용자의 사례 재사용은 하지 않는다.
- 라벨 제안, 편집 중 선택, 확정값을 구별한다. 편집만으로 집계나 학습 근거가 바뀌지 않는다. 그룹 행을 확정하면 그 행에 포함된 모든 관찰 활동 구간에 선택한 라벨 또는 미분류를 확정한다. 여러 항목은 각자의 선택을 담아 한 번에 제출할 수 있다.
- 확정값은 나중에 다시 바꿀 수 있다. 최신 확정값만 집계와 다음 제안의 사례로 사용한다. 새 확정 이력은 다음 제안부터 참고하며, 이미 생성된 미확정 제안은 묵시적으로 재작성하지 않는다. 한 번의 정정을 자동 반복 규칙으로 만들지 않는다.
- 보관된 라벨을 가리키는 기존 미확정 제안은 기록상 그대로 보여주되, 확정 전에 활성 라벨 또는 미분류를 다시 선택하게 한다. 새 분석으로 제안을 바꾼다면 대체 사실을 검토 화면에 드러낸다.
- 시간상 연속이고 라벨과 확정 상태가 같은 구간만 라벨 타임라인에서 묶는다. 다른 라벨, 다른 확정 상태, 불투명 활동, 수집 공백, 미관찰 시간은 묶음의 경계다. 길이 0인 관찰 구간도 순서와 경계를 보존한다.
- 대시보드의 날짜 경계는 계정 시간대로 계산한다. 날짜를 가로지르는 확정 구간은 해당 날짜와 겹치는 시간만 합산한다. 떨어진 확정 구간은 라벨별로 합산한다. 종료된 미확정 구간은 라벨별 잠정합계로 표시하지 않고 검토 대기 시간으로 표시한다. 열린 관찰 활동 구간은 종료 전까지 확정·집계 대상에서 제외한다. 확정된 미분류와 불투명 활동 시간은 각각 별도 값이며 수집 공백은 모든 활동 시간에서 제외한다.
- 기존 관찰 구간의 공개 식별자는 projection 재구축·병합·분할 때 바뀔 수 있으므로 확정값의 유일한 영구 근거로 사용하지 않는다. 늦은 관찰이나 재구축으로 구간의 소속·시간 경계가 달라지면 영향 받은 라벨 상태를 현재 관찰 사실과 대조한다. 다른 활동에 라벨을 조용히 이전하지 않으며, 안전하게 이어 붙일 수 없는 경우 다시 검토 대상으로 드러낸다.
- 서버는 인증된 계정에 대해 라벨 목록 관리, 라벨 타임라인·검토 대기 조회, 묶음 및 여러 항목의 확정·정정, 날짜별 집계를 제공한다. 공개 요청·응답은 Pydantic 계약과 기존 camelCase·공통 오류 규칙을 따르고 OpenAPI를 갱신한다. macOS 앱은 이 계약으로 제안 표시, 변경, 일괄 확정, 집계를 제공한다.
- 사용자 확정과 정정은 한 요청 안에서 일관되게 처리한다. 중복 제출이나 오래된 검토 화면이 최신 확정을 조용히 덮어쓰지 않게 하고, 적용되지 않은 항목을 클라이언트가 알아볼 수 있게 한다.

## Testing Decisions

- 좋은 테스트는 모델의 내부 순위 계산이나 SQL 호출 순서보다 사용자에게 보이는 제안·확정 상태, 계정 격리, 타임라인 행, 날짜별 합계와 재시도 결과를 검증한다. AI 응답은 결정적으로 제어해 같은 입력의 결과를 반복 검증한다.
- 주 서버 테스트 경계는 인증된 실제 HTTP 요청에서 FastAPI와 실제 PostgreSQL까지 관통하는 E2E 테스트다. 관찰 구간 생성부터 제안·확정·정정·집계까지 저장된 상태와 공개 응답을 한 경계에서 검증한다. AI 제안기는 결정적 대역으로 제어한다. 기존 관찰 타임라인의 PostgreSQL 통합 fixture와 활동 API의 HTTP 계약 테스트가 선례다.
- 같은 경계에서 인증, 입력 검증, camelCase JSON, 오류 응답, 배치 확정의 충돌과 재시도 결과를 검증한다. 계층별 호출 순서를 확인하기 위한 별도 테스트 경계는 추가하지 않는다.
- E2E 사례에는 동일 문맥·다른 의미의 수동 라벨, 다른 앱·같은 라벨, 연속·비연속·중간 0초 구간, 제안과 확정의 분리, 그룹 및 여러 항목 확정, 확정 미분류, 불투명 활동·수집 공백 제외, 날짜 경계, 계정 격리, 보관·이름 변경, 정정 후 합계 및 다음 제안, 늦은 관찰에 따른 projection 재구성을 포함한다.
- macOS 앱은 고정된 API 응답으로 제안·확정 구분, 행 묶음, 선택 변경 후 확정, 여러 항목 검토, 대시보드의 별도 시간 표시를 확인한다. 기존 앱 상태·API 경계 테스트를 선례로 삼고, 실제 모델 서비스의 확률적 문구나 화면 내부 구현에 테스트를 묶지 않는다.

## Out of Scope

- 관찰 활동 구간 내부를 시간별로 나누어 서로 다른 라벨을 붙이는 기능.
- `활동 흐름`을 만들거나 그에 기반해 집중·컨텍스트 스위칭을 판단하는 기능. 타이머 기반 집중 세션은 별도 논의 대상이다.
- 불투명 활동의 AI 또는 수동 라벨링과 수집 공백을 활동으로 추정하는 기능.
- 미확정 제안을 라벨별 잠정합계에 포함하거나 사용자 승인 없이 자동 확정하는 기능.
- 사용자별 모델 미세 조정, 계정 간 개인화 사례 공유, 수정 한 번으로 만들어지는 강제 자동 적용 규칙.

## Further Notes

- 현재 서버에는 관찰 활동 구간의 projection과 날짜별 관찰 타임라인 API가 있으나 라벨 저장·제안·확정·집계 API는 없다. 현재 macOS 앱에도 이 라벨 검토·대시보드 화면은 없다.
- 기본 라벨은 계정별 데이터로 만들며, `미분류`는 기본 라벨이 아닌 별도 확정 상태다. 기본 라벨 이름은 초기 제안값이므로 사용자가 변경하거나 보관할 수 있다.
- 구체적인 공개 경로와 저장 테이블 형태, AI 실행 방식은 구현 설계에서 정한다. 관찰 사실과 사용자 확정의 분리, 확정값만 집계, 사용자별 개인화, 기존 관찰 구간 재구성과의 안전한 관계는 반드시 유지한다.
