# macOS 활동 수집 설계

> 상태: 설계 확정
> 범위: macOS 클라이언트의 관찰, 서버 수집 API, 서버 기준 타임라인
> 비범위: AI 해석, 사용자가 확정하는 의미, 통계·집중도, 물리 DB 최적화와 삭제 정책의 세부값

## 1. 목표와 책임 경계

목표는 사용자가 실제로 포커싱한 앱 또는 웹 활동을 신뢰성 있게 기록하고, 서버가 그 기록을 해석해 하나의 활동 타임라인으로 보여 주는 것이다.

```
macOS 클라이언트                  서버                         화면
관찰·필터·로컬 보관·전송  →  원본 보존·순서 검증·경계 판단  →  서버 타임라인 조회
```

| 주체 | 책임 |
| --- | --- |
| 클라이언트 | 포커싱된 대상만 관찰하고, 개인정보 필터링 후 전체 스냅샷을 순서대로 보낸다. |
| 서버 | 관찰의 순서와 차이를 판단하여 활동 구간과 공백을 만든다. |
| 화면 | 서버가 확정·투영한 타임라인만 표시한다. 클라이언트 전송 대기열을 활동으로 표시하지 않는다. |

클라이언트는 도메인 이벤트나 활동 경계를 결정하지 않는다. 매 관찰 시점의 사실만 보낸다. 같은지, 새 활동인지, 이전 흐름을 어디서 끝낼지는 서버가 결정한다.

### 핵심 용어

| 용어 | 의미 |
| --- | --- |
| 관찰 | 클라이언트가 한 시점에 포커싱된 대상을 읽은 사실 |
| 전체 스냅샷 | 이전 값과의 차이만 보내지 않고, 그 시점에 알 수 있는 전체 관찰값을 보내는 방식 |
| 활동 레코드 | 서버가 영구 보관하는, 개인정보 필터링을 거친 하나의 관찰 또는 수집 상태 변경 |
| 활동 구간 | 서버가 연속된 관찰을 비교해 만든 표시·분석 단위 |
| 수집 공백 | 실제로 관찰하지 못했거나 처리할 수 없었던 구간 |
| 불투명 활동 | 관찰은 했지만 식별 정보를 저장하지 않기로 한 정상 활동 |

## 2. 데이터 구조

### 2.1 전송 단위

클라이언트는 한 수집 스트림의 레코드를 FIFO로 묶어 보낸다.

```json
{
  "batch_id": "uuid",
  "device_registration_id": "uuid",
  "collection_stream_id": "uuid",
  "records": [
    {
      "record_type": "activity_observation",
      "event_id": "uuid",
      "sequence": 412,
      "observed_at": "2026-09-07T10:15:30Z",
      "timezone_id": "Asia/Seoul",
      "utc_offset_minutes": 540,
      "clock_epoch_id": "uuid",
      "monotonic_ns": 8920033000000,
      "context": {}
    }
  ]
}
```

| 필드 | 책임과 의미 |
| --- | --- |
| `batch_id` | 전송 요청의 재시도 식별자. 응답을 잃으면 같은 ID와 같은 본문으로 재전송한다. |
| `device_registration_id` | 서버에 등록된 기기를 가리키는 서버 발급 식별자. |
| `collection_stream_id` | 단조 증가 순서가 유효한 수집 계보. |
| `event_id` | 레코드 자체의 중복 제거 식별자. |
| `sequence` | 스트림 안에서의 순서. 재시도와 주기 관찰도 각각 새 번호를 갖는다. |
| `observed_at` | 클라이언트 벽시계 기준의 UTC 관찰 시각. |
| `timezone_id`, `utc_offset_minutes` | 관찰 당시의 표시 시간대 문맥. |
| `clock_epoch_id`, `monotonic_ns` | 벽시계 조정과 재부팅을 구별하기 위한 시간 근거. 서로 다른 epoch의 monotonic 값은 빼서 계산하지 않는다. |

수집 스트림은 일반적인 앱 재시작, OS 재부팅, 네트워크 실패로 바꾸지 않는다. 로컬 대기열과 순서 상태가 소실·재생성되었거나, 앱 재설치 등으로 기존 순서를 이어 갈 수 없을 때만 새 스트림을 시작한다. 새 스트림은 이전 흐름과의 명시적 경계다.

### 2.2 활동 관찰 레코드

`ActivityObservation`은 항상 전체 스냅샷이다. 변경된 필드 목록이나 클라이언트가 판정한 “동일 활동” 표시는 없다.

```json
{
  "record_type": "activity_observation",
  "event_id": "uuid",
  "sequence": 412,
  "observed_at": "2026-09-07T10:15:30Z",
  "timezone_id": "Asia/Seoul",
  "utc_offset_minutes": 540,
  "clock_epoch_id": "uuid",
  "monotonic_ns": 8920033000000,
  "context": {
    "kind": "detailed",
    "app": {},
    "window": {},
    "web": {}
  }
}
```

#### 상세 활동 문맥

```json
{
  "kind": "detailed",
  "app": {
    "bundle_id": { "status": "captured", "value": "com.apple.Safari" },
    "name": { "status": "captured", "value": "Safari" }
  },
  "window": {
    "status": "captured",
    "title": {
      "status": "captured",
      "value": "프로젝트 설계 문서"
    }
  },
  "web": {
    "kind": "browser",
    "tab_title": {
      "status": "captured",
      "value": "Mosemo"
    },
    "url": {
      "status": "captured",
      "value": "https://example.com/work"
    }
  }
}
```

앱, 창, 웹의 각 필드는 독립적으로 상태를 표현한다. 한 필드를 읽지 못했다고 다른 필드까지 없는 것으로 취급하지 않는다.

| 영역 | 구조와 의미 |
| --- | --- |
| `app` | `bundle_id`와 표시 이름을 각각 수집한다. bundle ID가 있으면 우선 사용하고, 없으면 이름으로 표시한다. 둘 다 없으면 서버는 원본만 보관하고 화면 카드에는 표시하지 않는다. |
| `window` | `captured`, `absent`, `unavailable` 중 하나다. 제목은 실제 빈 문자열도 보존하며, 읽지 못함은 `unavailable`과 사유로 구별한다. 창 제목이 없어도 앱 활동은 유효하다. |
| `web` | `not_applicable` 또는 `browser`다. 브라우저일 때 탭 제목과 URL은 각각 독립 상태다. 브라우저의 구체적인 식별은 `app.bundle_id`로 한다. URL만 정상이어도 유효한 웹 활동이다. |
| 텍스트 | 창·탭 제목은 정한 제한을 넘으면 앞부분과 `truncated: true`, 원래 바이트 길이를 보관한다. URL은 일부를 잘라 보관하지 않는다. |

탭 제목과 URL의 상태는 `captured`, `absent`, `unavailable`, `redacted` 중 하나다. `redacted`는 수집 실패가 아니라 클라이언트 정책에 따라 값을 저장하지 않았다는 뜻이며, `reason`을 함께 기록한다.

URL은 브라우저가 관찰한 문자열을 그대로 저장한다. 서버가 URL을 정규화하거나 쿼리·프래그먼트를 제거하지 않는다. URL을 파싱할 수 없다는 이유만으로 관찰을 거절하지 않는다.

#### 불투명 활동 문맥

```json
{
  "kind": "opaque"
}
```

불투명 활동은 개인정보 필터가 적용된 정상 관찰이다. 대상 앱, 창 제목, 도메인, 해시, 필터 규칙 이름 등 식별 가능한 부가 정보는 넣지 않는다. 서버에서는 연속된 불투명 활동을 하나로 합칠 수 있지만, 불투명 활동을 일반 상세 활동과 병합하거나 앱 전환으로 해석하지 않는다.

### 2.3 수집 상태 변경 레코드

잠금, 절전, 수집 중지·재개, 접근 권한 상실처럼 관찰 자체를 할 수 없는 사실은 활동 관찰과 별도 레코드로 보낸다.

```json
{
  "record_type": "collection_state_changed",
  "event_id": "uuid",
  "sequence": 413,
  "observed_at": "2026-09-07T10:20:00Z",
  "timezone_id": "Asia/Seoul",
  "utc_offset_minutes": 540,
  "clock_epoch_id": "uuid",
  "monotonic_ns": 9190033000000,
  "state": "suspended",
  "reason": "screen_locked"
}
```

`state`는 적어도 `active`와 `suspended`를 구별한다. `reason`은 잠금·절전·사용자 중지·권한 상실처럼 수집 가능성에 관한 이유이며, 사용자의 활동 내용을 담지 않는다.

### 2.4 수신 결과

서버는 배치 전체를 처리한 뒤 다음 결과를 반환한다.

```json
{
  "batch_id": "uuid",
  "status": "accepted",
  "accepted_through_sequence": 413,
  "received_at": "2026-09-07T10:20:03Z"
}
```

동일한 `batch_id`와 동일 본문은 이전 결과를 재현한다. 이미 저장된 `event_id`도 본문이 같으면 중복으로 처리하고, 같지 않으면 충돌로 배치 전체를 거절한다.

## 3. 클라이언트 처리 책임

### 3.1 무엇을 관찰할지

클라이언트는 현재 포커싱된 앱과 그 포커스 창만 수집한다. 화면에 떠 있는 모든 창이나 백그라운드 앱을 나열해 수집하지 않는다.

다음 시점에는 새 전체 스냅샷을 만든다.

- 수집 시작 또는 중단 후 재개
- 포커싱된 앱 변경
- 포커스 창, 창 제목, 브라우저 탭, URL 변경
- 수집 가능성의 변경 이후 다시 관찰 가능해진 시점
- 변화가 없더라도 활성 수집 중 마지막 관찰 후 30초가 지난 시점

빠르게 연속되는 화면 변화는 짧게 안정화한 뒤 스냅샷 하나로 보낸다. 이것은 관찰 노이즈를 줄이기 위한 클라이언트 처리이며, 활동이 이어지는지의 판단은 서버가 한다.

창이 없거나 제목을 읽지 못해도 앱 정보가 있으면 앱 활동을 보낸다. 앱·창·웹 어느 정보도 얻지 못했을 때는 상세 활동을 억지로 만들지 않는다. 개인정보 규칙에 걸린 경우에는 불투명 활동을 보낸다.

### 3.2 개인정보 필터와 로컬 보관

식별 정보는 암호화된 로컬 대기열에 넣기 전에 클라이언트에서 필터링한다.

| 상황 | 클라이언트가 보내는 값 |
| --- | --- |
| 개인정보를 저장하면 안 되는 활동 | `{ "kind": "opaque" }` |
| `data:` 또는 `javascript:` URL | URL `redacted`, 사유 `embedded_content_scheme` |
| 허용 길이를 넘는 URL | URL `redacted`, 사유 `length_exceeded` |
| 창 제목을 읽지 못함 | 창 `unavailable`과 수집 실패 사유 |
| 창 자체가 없음 | 창 `absent` |

창·탭 제목은 제한을 넘을 때 앞부분을 보관하고 잘렸다는 사실과 원래 바이트 길이를 함께 기록한다. URL은 값을 잘라 저장하지 않고, 저장할 수 없으면 `redacted`와 사유를 보낸다. URL 필터링, 이벤트 ID·순번 부여, 암호화 대기열 기록은 하나의 원자적 처리로 끝낸다. 실패한 레코드를 순번만 부여한 채 잃어버리지 않는다.

### 3.3 전송·재시도·복구

- 하나의 스트림에서는 순서대로 배치하고, 동시에 하나의 배치만 전송한다.
- 네트워크 오류나 응답 유실이면 같은 `batch_id`와 바이트상 동일한 본문을 재전송한다.
- 서버가 수락 또는 동일 레코드 중복을 확인한 뒤에만 로컬 대기열에서 제거한다.
- 순번 불일치나 ID 충돌 같은 무결성 오류는 배치 전체를 거절하고 현재 스트림을 유지한다. 로컬 대기열과 순서 상태를 영구적으로 복구할 수 없을 때만 현재 스트림을 명시적으로 끝내고 새 스트림으로 시작한다.

클라이언트의 로컬 대기열은 전송 신뢰성을 위한 장치다. 아직 서버에 반영되지 않은 관찰을 타임라인 활동으로 화면에 선표시하지 않는다. 클라이언트는 동기화 상태만 보여 줄 수 있고, 활동은 서버 동기화와 투영이 끝난 뒤 조회하여 표시한다.

## 4. 서버 처리와 표시 정책

### 4.1 수신과 영구 보관

서버는 인증, 배치 식별자, 레코드 식별자, 순번, 스트림 상태를 검증한다. 검증을 통과한 **개인정보 필터 후 원본 활동 레코드**는 주기 관찰·반복·정보량이 적은 관찰까지 모두 영구 보관한다.

한 배치에서는 다음을 하나의 트랜잭션으로 처리한다.

1. 레코드 원본 보관
2. 스트림의 마지막 수락 순번 갱신
3. 활동 구간·공백 투영 갱신
4. 수신 결과 확정

하나라도 실패하면 배치 전체가 수락되지 않는다. 오프라인 동안 로컬 대기열에 쌓였다가 나중에 온 정상 관찰은 수집 공백이 아니다.

외부 봉투는 유효하지만 활동 문맥을 해석할 수 없는 레코드는 `unusable` 상태의 원본으로 보관한다. 화면에는 표시하지 않고, 앞뒤 활동을 이어 붙이지 않으며 수집 공백 경계로 취급한다. 인증 실패, JSON 파싱 실패, 순번 단절·충돌, ID와 본문의 충돌처럼 프로토콜 자체가 깨진 경우는 배치 전체를 거절한다.

### 4.2 활동 구간과 공백 판단

서버는 순서가 보장된 전체 스냅샷을 비교해 `ActivitySpan`을 만든다.

| 다음 레코드 | 서버 판단 |
| --- | --- |
| 표시·비교 가능한 문맥이 이전과 동일 | 기존 구간 연장 |
| 앱, 창, 탭 또는 URL이 변경됨 | 이전 구간 종료, 새 구간 시작 |
| 연속된 불투명 활동 | 불투명 활동 구간으로 병합 가능 |
| 불투명 활동과 상세 활동 사이 | 서로 병합하지 않음 |
| `suspended` 상태 변경 | 해당 시각에서 활동 종료 |
| 재개 뒤 첫 관찰 | 새 활동 구간 시작 |
| 실제 관찰의 시간적 단절 | 수집 공백 생성 |
| 새 스트림, 시간 epoch 변경, 해석 불가 레코드 | 앞뒤 활동을 연결하지 않음 |

첫 버전에서는 URL의 쿼리와 프래그먼트 차이도 변경으로 본다. 의미적으로 같은 페이지인지, 여러 활동을 하나의 더 큰 흐름으로 묶는 일은 후속 모델의 책임이다.

벽시계는 보정될 수 있으므로 단순한 시각 차이만으로 활동 지속 시간을 확정하지 않는다. 같은 시간 epoch 안의 단조 시간과 수집 상태, 순번을 함께 사용한다.

### 4.3 화면 표시

화면은 원본 레코드가 아니라 서버가 만든 활동 구간을 표시한다.

| 서버 문맥 | 표시 |
| --- | --- |
| 앱 정보가 있음, 창 정보 없음 또는 미수집 | 앱 활동 |
| URL만 정상인 브라우저 문맥 | 웹 활동 |
| 불투명 문맥 | 알 수 없는 활동 |
| 표시할 앱·웹 식별 정보가 전혀 없음 | 카드 미표시 |
| 수집 공백 | 공백으로 표시 |

카드를 표시하지 않는 원본도 서버에는 보관한다. 그 레코드는 이전 활동을 끝내거나 다음 활동과 합치지 않도록 하는 경계 근거가 된다. 화면에는 서버가 수락·투영을 마친 결과만 반영한다.

## 5. 보존·개인정보 정책

- 서버는 수락한 개인정보 필터 후 원본 활동 레코드를 영구 저장한다.
- 저장하지 말아야 할 식별 정보는 클라이언트에서 대기열 기록 전 제거한다.
- 불투명 활동은 수집 실패가 아니라 정상적인 프라이버시 상태다.
- 수집 공백은 실제로 관찰할 수 없었거나 기록을 해석·연결할 수 없었던 사실을 뜻한다. 불투명 활동과 혼동하지 않는다.
- 원본 활동, 서버의 후속 추론, 사용자가 확인한 의미는 같은 데이터로 섞지 않는다.

## 6. 후속 모델과 비범위

현재 설계는 관찰과 타임라인의 신뢰성 있는 기반을 확정한다. 다음은 이 구조 위에서 별도 모델로 다룬다.

- AI가 활동 의미를 추론하는 모델
- 사용자가 활동의 의미를 수정·확정하는 모델
- 목표, 집중도, 생산성 통계
- 보존 기간, 삭제, 내보내기 정책의 구체 값
- 배치 크기와 각 필드의 정확한 길이 제한

이 후속 기능은 활동 원본을 바꾸지 않고, 원본·서버 추론·사용자 확정 의미를 분리한 채 추가한다.
