# Pull Request

## 템플릿 선택
- 기능 개발, 리팩터링, 문서·테스트·설정 변경에는 [개발 템플릿](references/development.md)을 사용한다.
- 기존 동작의 결함을 수정하는 PR에는 [버그 수정 템플릿](references/bug-fix.md)을 사용한다.
- 사용자 지정이 있으면 우선한다. 여러 목적이 섞여 있으면 PR의 주된 목적에 맞춰 하나를 선택한다. 선택한 템플릿만 읽는다.

## 작성 절차
1. 현재 저장소의 `AGENTS.md`를 확인한다. GitHub 접근·인증, 커밋, 검증 규칙은 저장소 지침을 따른다.
2. 대상 브랜치와 기준 브랜치, 작업 트리 상태를 확인한다. PR에 포함될 전체 diff와 커밋을 읽고 관련 이슈·기존 PR은 필요할 때 조회한다. 미커밋 변경을 이미 PR에 포함된 변경으로 설명하지 않는다.
3. 선택한 템플릿의 제목과 순서를 유지해 본문을 채운다. 작성 안내 주석은 제거한다. 해당 없는 항목은 `해당 없음`, 확인하지 못한 내용은 `미확인`과 이유를 적는다. 내용을 추측해 채우지 않는다.
4. 제목은 변경 목적과 결과가 드러나도록 짧게 작성한다. 본문은 대화 이력 없이 이해할 수 있도록 최종 변경을 설명한다. 검토에 필요한 경우 구체적인 이전·이후 동작을 포함한다.
5. 관련 이슈는 실제로 확인한 번호나 링크를 사용한다. 해결되어 PR 병합 시 자동 종료할 이슈에는 `Closes #번호`, 참고·부분 해결에는 `Refs #번호`를 쓴다. 다른 저장소의 이슈는 저장소까지 명시한다. 관련 이슈가 없으면 `없음`으로 적고 새 이슈를 임의로 만들지 않는다.
6. 검증에는 실제 실행한 명령과 결과를 기록한다. 미실행·실패·진행 중인 검증은 이유와 함께 구분하고, 기존 결과는 현재 변경에 유효한 경우에만 사용한다. 버그 수정은 기존 재현 조건에서 해결됐는지와 회귀 검증을 설명한다.
7. 사용자가 본문 초안만 요청했으면 초안을 제공한다. PR 생성·갱신을 요청했으면 승인된 범위에서 수행한다. 기존 PR 갱신 시 현재 전체 변경에 맞춰 제목과 본문을 정리하고 관련 없는 사용자 작성 정보는 보존한다. 여러 줄 본문은 임시 파일에 작성해 `gh`의 `--body-file`로 전달한다.

PR 작성 요청만으로 커밋·푸시·머지를 수행하지 않는다. 해당 작업에 대한 기존 사용자 승인이 있으면 그 범위에서 진행한다.
