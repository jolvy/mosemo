# 구현

## 시작 전 확인
사용자의 직접 요청·대화에서 합의한 범위와 기대 결과를 기준으로 독립적으로 구현할 수 있다. 선행 Skill 실행, PRD 작성이나 Plan Issue 생성을 요구하지 않는다. `AGENTS.md`와 현재 코드·테스트를 확인하고 용어집·PRD·ADR은 관련 자료가 있을 때 참조한다.

관련 Plan Issue가 있으면 그 본문을 계획의 유일한 원본으로 삼고 최신 범위·체크리스트·완료 기준과 승인 기록을 대조한다. 유효한 기존 승인은 재사용한다. Issue를 읽을 수 없으면 옛 문서나 기억을 최신 Plan으로 대신하지 않고 영향과 확인할 범위를 밝힌다. 기존 승인 모델과 충돌하거나 요청만으로 결정할 수 없는 정책·모델 변경은 해당 부분의 제안과 필요한 승인부터 확인한다. Issue가 없다는 사실만으로 구현을 중단하지 않는다.

## 구현 원칙
- 현재 저장소의 계약과 승인된 범위를 우선한다. 상태를 읽고 판단·변경·저장하는 경로를 따라 책임의 소유자를 확인한다.
- 객체의 책임과 협력을 중심으로 설계한다. 계산·변환·판단은 가능한 한 명시적인 입력과 반환값을 갖는 순수함수로 구현하고, I/O와 외부 부수 효과는 애플리케이션 경계에서 조율한다. 객체의 불변식과 상태 전이는 해당 객체가 소유하며, 순수함수로 분리하기 위해 책임을 객체 밖으로 옮기지 않는다.
- 여러 객체에 걸친 판단은 협력하는 도메인 연산에 둔다. 애플리케이션 서비스는 로딩·트랜잭션·잠금·외부 호출·순서를 조율한다.
- 도메인 규칙 없는 대입에 메서드를 만들거나 모든 원시값을 감싸지 않는다. 저장 형태만으로 도메인 책임을 정하지 않는다.
- 함수·클래스 크기, 필드·매개변수 수, 들여쓰기·else 사용은 가독성과 응집도의 검토 신호다. 고정 수치를 맞추기 위한 분리·추상화는 하지 않는다.
- 코드 예시는 책임과 계약을 설명하는 자료다. 현재 구조와 다른 패턴을 예시만 보고 도입하지 않는다.
- 업무 용어의 공백이나 의미 충돌은 [유비쿼터스 언어](../ubiquitous-language/SKILL.md) 절차로 피드백한다. 코드·DB 구조에 맞춰 업무 정의를 바꾸지 않으며, 정책·모델 변경이 필요하면 영향받는 요구사항·명세·설계 절차로 반환한다. 용어집 갱신만으로 변경 승인을 대신하지 않는다.

## 절차
1. 현재 구현 기능, 제외 범위 및 확장할 변화 축을 구별한다.
2. 기존 도메인 코드가 책임·불변식을 보호하는지 확인한다. ORM·DB 저장 모델은 별도로 구현하며 단순 1:1 대응을 강제하지 않는다.
3. 작업 단위별로 테스트를 추가·수정하고 최소한의 코드, 필요 시 **신규** Alembic 마이그레이션을 작성한다. 과거 적용된 마이그레이션은 수정하지 않는다.
4. JSON 계약·오류 응답·시간 및 멱등성·트랜잭션·권한 요구를 지킨다. API 변경 시 OpenAPI 스냅샷을 갱신한다.
5. 구현이 승인된 객체 협력 또는 저장 구조에서 본질적으로 벗어났다면 engineering-planning으로 돌아가 해당 모델링 절차에 따라 **시각화와 재승인**을 수행한다.
6. 관련 테스트와 `.codex/skills/verification/scripts/validate.sh`를 실행한다. 실패는 원인 기반으로 수정하되 **동일 원인 최대 3회**까지만 재시도한다. 매번 같은 수정을 반복하거나 검증을 비활성화하지 않는다.
7. 테스트·검증을 통과한 구현을 `code-reviewer`, `domain-reviewer`, `security-auditor` 세 subagent에게 검토받는다. 각 subagent에 요청 범위, 변경 사항, 관련 요구사항·문서와 검증 결과를 제공하고, 저장소의 해당 agent 정의에 따라 읽기 전용으로 검토하도록 한다.
8. 리뷰 피드백을 검토하고 유효한 지적을 수정한다. 반영하지 않는 지적에는 근거를 기록한다. 수정 후 관련 테스트·검증을 다시 실행하고, 해당 지적을 한 subagent에게 수정 사항과 영향을 재검토받는다. 새 지적도 같은 방식으로 처리하며, 동일 원인의 수정·재검토는 최대 3회로 제한한다. 해결하지 못한 지적이나 필요한 정책 결정은 남은 문제로 명시하고 완료로 보고하지 않는다.
9. 변경 파일, 완료한 인수 조건, 검증 증거, 세 subagent의 리뷰 결과와 피드백 처리 내역, 남은 위험을 보고한다. 요청 없이는 커밋하지 않는다.

## 중단
핵심 정책이 미확정이거나 승인된 모델과 구현이 충돌하면 영향받는 작업을 보류하고 필요한 결정을 확인한다. 독립적인 작업은 계속할 수 있다. 세 차례 수정에도 동일 오류가 지속되면 원인·추천 대응·대안을 제시하고 해당 수정을 멈춘다.

## 구현·시연 인계
- Plan이 있으면 현재 AC·T번호에 작업을 연결하고 실제 검증 증거·상태를 같은 Issue 본문에 반영한다. Plan이 없으면 사용자 요청의 기대 결과와 검증 증거를 최종 응답에 연결한다. 추적을 위해 별도 PRD나 Issue를 만들지 않으며, 증거 없는 항목은 완료 처리하지 않는다.
- `uv run --locked python .codex/skills/verification/scripts/validate_architecture.py`로 의존성 경계를 검사한다. 검사하는 의존성 규칙은 verification Skill의 실행 도구 설명을 따른다. 위반을 숨기기 위한 제외 목록 추가는 하지 않는다.
- 기능 단위 결과를 시연하거나 재현 절차를 제공한다. 관련 Plan이 있으면 engineering-planning의 [계획 관리 규칙](../engineering-planning/references/plan-issue.md)에 따라 피드백을 반영한다. Plan이 없으면 요청 범위와 기대 결과·테스트에 연결하고, 관련 문서·승인은 실제 영향을 받는 경우에만 갱신한다.
