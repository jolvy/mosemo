# 엔지니어링 계획

## 시작
사용자 요청·대화에서 합의한 범위와 기대 결과 또는 승인된 PRD를 기준으로 독립적으로 시작한다. specification 실행이나 PRD 파일을 요구하지 않는다. 현재 코드·테스트·마이그레이션을 확인하고 용어집·ADR·관련 Plan Issue는 존재하는 경우 참조한다. 모델링이 끝나지 않았어도 시작할 수 있다. 핵심 정책 미결정은 해당 결정만 확인하며, 별도 명세 작성은 요청 범위에 필요할 때 수행한다.

## 필요한 설계 선택
이번 변경에 필요한 단계와 이유를 짧게 알리고 해당 문서만 읽는다. 모든 참조를 미리 읽거나 모든 단계를 순서대로 수행하지 않는다.

| 판단 기준 | 사용할 절차 |
| --- | --- |
| 객체의 상태·불변식·행동·책임 또는 협력이 바뀐다 | [도메인 모델링](references/domain-modeling.md) |
| 저장할 사실·테이블·제약·인덱스·조회 구조·트랜잭션 경계를 설계해야 한다 | [영속성 모델링](references/persistence-modeling.md) |
| 지속적인 영향을 주는 기술 선택에 대안과 트레이드오프를 남겨야 한다 | 독립 [architecture-decision Skill](../architecture-decision/SKILL.md) |
| 구현 전 검증할 행동·경계·실패 사례를 정리해야 한다 | [테스트 시나리오 계획](references/propose-tests.md) |
| 필요한 설계 판단을 마쳤거나 기존 설계로 충분하다 | 최종 계획을 승인받고 GitHub Issue 등록·갱신 및 하위 티켓 분할안을 조율하는 [Plan Issue 작성](references/plan-issue.md) |

## 조율
1. 현재 범위에서 필요한 설계와 이미 유효한 결정·승인을 구분한다. 단계 선택 자체를 매번 승인받지는 않는다.
2. 의존 관계에 맞춰 설계를 진행한다. 새 객체 행동만 필요하면 도메인 모델링 후 계획으로, 도메인 의미를 유지하는 저장 구조 변경이면 영속성 모델링부터, 기술 선택이 전제라면 ADR부터 시작할 수 있다.
3. 각 절차의 승인 조건을 지키고 결과를 받은 뒤 다음 단계를 판단한다. 기존 승인과 현재 대상·범위가 일치하면 재사용하고, 설계 변경이 다른 결정에 영향을 주면 해당 부분만 다시 검토한다.
4. 새 정책 질문은 사용자와 해결하고 관련 명세가 있으면 갱신한다. 도메인 책임이 달라지면 도메인 모델링을 검토한다. 업무 용어의 공백·의미 차이는 [유비쿼터스 언어](../ubiquitous-language/SKILL.md) 절차로 피드백하며 클래스·테이블 구조에 맞춰 업무 정의를 바꾸지 않는다. 용어집 갱신으로 정책·모델 승인을 대신하지 않는다. 기존 설계로 충분한 단계는 생략하고 이유를 최종 계획에 짧게 기록한다.
5. 테스트 계획을 구체화할 때 테스트 시나리오 계획 참조를 사용한다. 이미 충분한 계획이 있거나 작은 변경이면 필요한 부분만 보완한다.
6. 설계 결과와 테스트 시나리오를 작업 순서·마이그레이션·위험으로 종합하고 검토 가능한 계획안을 제시한다. 객체 간 협력이 계획 이해에 필요하면 승인된 최신 Mermaid 협력 지도를 Issue 본문에 포함한다. 필요한 설계 판단을 마쳤고 게시 여부가 정해지지 않았다면 “이 계획을 GitHub Issue로 등록할까요?”라고 묻는다. 기존 Plan Issue가 있으면 해당 Issue 갱신 여부를 묻는다. 이미 등록·갱신을 요청받았거나 게시하지 않기로 했다면 같은 질문을 반복하지 않는다. 사용자가 게시를 원하면 Plan Issue 작성 절차에 따라 본문을 제안·승인받고 등록·갱신한다.

7. 최종 계획을 사용자에게 확인받고 승인되면 하위 티켓 분할안 제안으로 이어간다. 계획 승인과 분할안 승인은 구분한다. 분할안의 구체적인 내용·생성 절차는 [Plan Issue 작성](references/plan-issue.md)을 따른다. 이미 승인된 계획으로 시작했다면 계획 승인을 반복하지 않고 분할안을 제안한다. 계획·설계 제안만 요청했거나 GitHub 게시를 원하지 않는 경우에는 티켓 생성을 강제하지 않는다.

## 종료
계획 또는 설계 결과, 적용 범위, 설계 승인 상태와 남은 미결정을 보고한다. Issue 게시를 요청받았다면 URL을 보고하고, 게시할 수 없으면 등록 미완료로 밝힌다. 제안만 요청받은 작업은 Issue 없이 완료할 수 있다. 도메인·영속성 모델링만 요청받았다면 그 범위에서 종료한다. 계획 수립을 이유로 구현을 시작하지 않는다.
