# 영속성 모델링 — 사용자 승인 필수

## 입력
사용자와 합의한 범위·기대 결과 또는 승인된 PRD, 현재 도메인 설계,기존 SQLAlchemy 모델·Alembic 마이그레이션과 저장·조회 패턴을 확인한다. 관련 ADR과 모델 승인은 존재하는 경우 참조한다. 선행 Skill 실행이나 PRD 파일은 요구하지 않으며, 이번에 도메인 설계를 변경했다면 해당 변경의 승인을 확인한다.

## 의미 보존 검토
현재 도메인 설계의 의미를 저장·조회·변경 후에도 보존하는지 아래 항목 중 관련된 것을 검토한다. 저장 기술의 제약을 업무 규칙으로 바꾸지 않는다. 도메인 의미가 불명확하거나 바뀌어야 한다면 engineering-planning에 반환하여 먼저 해당 결정을 확인한다.

### 동일성의 저장 표현
- 도메인의 동일성 기준을 PK·업무 키·외부 식별자·유일성 제약에 대응시킨다. 행 식별자와 업무 대상의 동일성, 요청·사건의 멱등 키를 구분하고 각 키의 범위와 변경 가능성을 정한다. UUID 자체를 금지하거나 자연 키를 항상 우선하지 않는다.
- 동일 대상의 중복 저장, 서로 다른 식별 범위나 외부 시스템에서 사용한 같은 식별자, 삭제 후 재생성에서 필요한 제약과 충돌 처리를 확인한다. 재시도가 새 대상을 만들지 않아야 하는 경우에는 원자적인 저장·조회 방식을 검토한다.
- 파생·재구축 가능한 저장 표현이 있다면 그 식별자가 업무 대상의 동일성을 유지하는지 확인한다. 저장 표현의 식별자를 영구 도메인 식별자로 사용할 수 있다고 자동으로 가정하지 않는다. 병합·분리·재구축 시 참조가 유지되거나 무효화되는 조건은 승인된 의미에 맞춰 정한다.

### 사실·해석·불확실성의 저장 표현
- 업무상 원본 정보·해석 또는 판단·파생 데이터의 구분이 필요한 경우 각각의 저장·갱신 책임을 정한다. 어떤 정보를 덮어쓰거나 보존할지는 승인된 업무 규칙을 따르고, 필요한 구분이 저장·조회 과정에서 사라지지 않도록 한다. 모든 도메인에 원본·해석·읽기 모델의 세 구조를 요구하지 않는다.
- NULL과 기본값이 각 필드에서 무엇을 뜻하는지 정한다. 모름·해당 없음·미결정 등이 업무상 구별되어야 할 때만 명시적 값이나 상태로 보존한다. NULL을 항상 모름으로 정의하거나 모든 필드에 상태 컬럼을 추가하지 않는다.
- 시간의 의미가 업무 결과에 영향을 준다면 발생·입력·유효·변경 시점 등 필요한 시점을 구분한다. 과거와 현재 정보의 조회, 삭제·보존·정정에 필요한 이력만 설계한다. 모든 데이터에 이벤트 이력이나 이중 시간 모델을 강제하지 않는다.

### 관계의 저장 표현
- 승인된 관계의 역할·허용 개수·필수 여부·생명주기를 FK·Unique·Check·연결 테이블과 갱신 규칙으로 표현한다. DB 제약으로 보장하는 부분과 객체의 협력·트랜잭션에서 보장하는 부분을 구분한다.
- 관계 자체의 상태·기간·이력이 필요한 경우 저장 위치와 식별 방식을 비교한다. 연결 테이블을 만든다는 이유만으로 새 도메인 Entity를 요구하지 않는다.
- 관계 생성·변경·종료와 참여 객체 삭제의 영향을 확인한다. cascade·NULL 처리·보존 정책과 동시 갱신이 업무 의미를 훼손하지 않는지 검토하고, 필요한 원자성과 동시성 제어를 정한다.

### 업무 규칙과 저장 결과의 연결
- 의미 손실 위험이 있는 핵심 규칙은 `업무 의미 → 저장 표현 → 강제 수단 → 재조회 결과 → 필요한 검증`을 짧은 표나 설명으로 연결한다. 강제 수단은 DB 제약과 도메인 검증·트랜잭션 등의 역할을 구분한다. 모든 규칙에 별도 표를 만들지는 않는다.
- 예: `사용자가 미분류로 확정했다 → 미확정과 구별 가능한 확정 여부·선택값 표현 → 허용 조합 검증과 원자적 갱신 → 재조회 후 검토 대기에서 제외되고 확정 미분류 시간에 반영 → 저장 왕복 및 집계 검증`. 이는 의미 보존 예시이며 특정 컬럼·테이블 구조를 요구하지 않는다.

### 저장 경계의 반례 검증
- 관련 정상·경계 사례를 저장한 뒤 다시 조회했을 때 동일성, 불확실한 상태, 관계와 도메인 값의 의미가 유지되는지 확인할 시나리오를 정한다. 저장 변환이나 기본값 때문에 구분이 사라지는 경우를 찾는다.
- 중복·동시 요청·부분 실패·롤백·지연 또는 역순 데이터·정정·삭제·파생 데이터 재구축 중 변경에 관련된 사례를 선택해 기대 저장 상태와 조회 결과를 설명한다. 모든 경우를 필수 목록으로 수행하지 않는다.
- 선택한 반례는 `깨뜨릴 저장 가정 → 기대 저장·재조회 결과 → 남은 미결정(없으면 없음)`으로 짧게 설명한다. [도메인 모델링](domain-modeling.md)의 미분류 반례를 이어 검토한다면, 확정 미분류를 저장·재조회해도 미확정으로 복원되지 않아야 한다. 자동화할 사례의 상세는 [테스트 시나리오 계획](propose-tests.md)에 연결하고 중복 작성하지 않는다.
- 기존 데이터가 있다면 새 제약·변환·마이그레이션 후에도 같은 의미로 읽히는지 확인할 시나리오를 포함한다. 검증하지 못한 DB 동작은 가정과 필요한 테스트로 남기며, 설계 검토를 실제 DB 테스트 통과로 보고하지 않는다.

## 수행 절차
1. 저장해야 할 사실, 변경 주체, 식별자, 생명주기와 조회·갱신 경로를 파악한다.
2. 도메인 Entity와 ORM Entity를 1:1로 가정하지 않는다. 읽기 모델, 정규화/비정규화, 트랜잭션 경계의 필요성을 비교한다.
3. 위 의미 보존 검토를 적용해 테이블·PK/FK/Unique/Check, NULL 정책, 인덱스·쿼리, 삭제·보존, 동시성·멱등성, 마이그레이션/역호환을 검토한다.
4. **채팅에서 Mermaid erDiagram**으로 제안하는 논리 스키마를 보여준다. 관계와 주요 키·제약, 읽기 모델은 표나 짧은 설명으로 보완한다.
5. 예상 접근 패턴과 데이터 정합성 위험, 설계 대안·트레이드오프를 설명한다. 핵심 규칙의 업무 의미·저장 표현·강제 수단·재조회 결과·필요한 검증을 연결하고 관련 반례의 결과와 미결정을 요약한다.
6. 사용자에게 **추천안과 대안**을 제시하고 명시적 승인을 요청한다. 수정 시 시각화를 갱신하고 재승인받는다.
7. 승인된 저장·조회 구조, 제약과 트랜잭션 경계, 남은 미결정을 engineering-planning에 반환한다. 다음 단계나 중요한 기술 결정의 필요성은 조율 단계에서 판단한다.

## 산출물과 중단
- 도식·테이블 설명은 **대화에만 표시**하며 영구 DB 모델 문서나 ERD 파일을 작성하지 않는다.
- 실제 구조의 Source of Truth는 이후 구현될 ORM 코드와 Alembic 마이그레이션이다.
- 사용자 승인 전에는 계획 확정·마이그레이션 구현으로 진행하지 않는다.
- 도메인 책임 자체를 바꾸어야 한다면 engineering-planning에 영향을 반환하여 도메인 모델링과 필요한 승인부터 갱신한다.

## 승인 인계
승인 대상·버전, 주요 결정, 근거, 유효 범위, 승인 주체·시점과 상태를 기존 Plan Issue 본문에 기록한다. 아직 Plan이 없으면 생성 시 반영한다. 새 세션은 기록과 현재 범위가 일치하는 유효한 승인을 재사용한다. 책임·제약·저장 구조가 달라지면 영향받는 승인만 갱신한다. 그림과 대화 원본은 복제하지 않는다.
