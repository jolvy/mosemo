# 테스트 시나리오 계획

사용자와 합의한 기대 결과 또는 제품 명세와 설계 결과를 구현 작업으로 분해할 때, 무엇을 자동화 테스트로 검증할지 정한다. PRD·Plan 파일은 선행 조건이 아니다. 사용자에게 영향을 주는 실패 위험을 줄이는 최소한의 충분한 검증을 제안한다. 이 절차에서는 테스트 코드를 구현하지 않는다.

## 근거와 기존 검증 확인
- 사용자 요청의 기대 결과와 현재 범위를 확인하고, PRD·기존 Plan이 있으면 해당 인수 조건과 대조한다. 충돌하는 요구사항은 임의로 합치지 않는다.
- 관련 공개 동작과 기존 테스트를 필요한 만큼 확인한다. 기존에 충분히 검증하는 동작, 추가할 검증, 확인하지 못한 부분을 구분한다. 현재 코드의 동작을 곧바로 요구사항으로 간주하지 않는다.
- 각 제안은 인수 조건에 근거한 필수 사례인지, 위험에 근거한 보완 제안인지 표시한다. 보완 제안을 제품 범위에 조용히 추가하지 않는다.

## 시나리오 선정
- 관찰 가능한 성공 결과와 중요한 불변식을 기준으로, 해당 변경에 관련된 입력 경계·권한·계정 격리·상태 전이·실패와 복구·중복·동시성·외부 연동을 검토한다.
- 서로 다른 실패 원인과 기대 결과를 대표하는 사례를 고른다. 조합을 모두 열거하거나 같은 동작을 여러 계층에서 중복 검증하지 않는다.
- 외부에서 확인 가능한 동작과 계약을 검증한다. 사적인 메서드나 호출 횟수에 묶지 않고, 테스트 파일·함수 이름·fixture·mock 구성은 구현 단계에 맡긴다.
- 변경된 행동 경계와 실패 가능 지점을 먼저 찾고, 사용자 영향·재발 가능성·기존 검증 공백을 근거로 우선순위를 정한다. 확인된 결함과 위험 가설을 구분한다.
- 정상·실패·통합 경계 사례 중 실제 변경에 관련된 것을 선정한다. 종류별 개수를 강제로 채우거나 무관한 사례를 추가하지 않는다.
- 시간·난수·외부 서비스·공유 데이터에 의존하는 사례는 결과를 결정적으로 만들고 실행 간 격리를 확보할 방법을 계획한다. fixture·mock의 구체적 구현은 구현 단계에 맡기되, 대역이 가리는 실제 연동 위험은 밝힌다.
- 실행 시간과 환경 비용을 고려해 같은 위험을 검증하는 가장 가까운 적절한 경계를 선택한다. CI 시간 증가나 병렬 실행의 공유 자원 충돌이 예상되면 근거와 대응을 적고, 측정하지 않은 비용을 실측값처럼 쓰지 않는다.
- 자동화가 어려워 중요한 요구사항을 검증할 수 없다면 검증 가능성 문제를 별도로 드러낸다. 시나리오 수를 미리 정하지 않는다.

## 미결정과 계획 반영
기대 결과를 바꾸는 누락·모호함·문서 충돌은 영향과 추천안을 제시하고 필요한 결정을 받는다. 불확실한 기대 결과를 확정된 테스트로 쓰지 않으며, 영향받지 않는 사례는 먼저 정리할 수 있다. 이미 결정된 정책과 테스트 범위에 별도 승인을 반복 요구하지 않는다.

## 테스트 케이스 작성 형식
항상 아래 형식을 사용한다. 요약 표는 사례 선택과 비교에 사용하고, 상세는 케이스별 고정 항목으로 작성한다. 긴 조건·결과를 표 셀에 몰아넣거나 같은 설명을 두 곳에 반복하지 않는다. 한 사례만 있어도 같은 형식을 유지한다.

우선순위는 `필수`(인수 조건·중대한 불변식), `중요`(주요 경계·실패·재발 위험), `보완`(추가 가치)으로 구분한다. 케이스 ID는 Plan 안에서 고유하게 부여하고 같은 ID를 다른 사례에 재사용하지 않는다.

```markdown
### 테스트 케이스 요약

| ID | 사례 | 근거 | 우선순위 | 대응 |
| --- | --- | --- | --- | --- |
| TC-1 | <관찰 가능한 행동을 표현하는 제목> | <PRD 경로·AC번호 또는 위험 가설> | <필수/중요/보완> | <기존으로 충분/기존 보강/신규/미결정> |

### TC-1 — <사례 제목>

- **근거와 위험:** <요구사항 근거 또는 위험 가설, 예방할 실패와 사용자 영향>
- **우선순위 이유:** <이 사례를 먼저 또는 나중에 검증하는 이유>
- **사전 조건 (Given):** <초기 상태·계정·데이터·필요한 환경>
- **행동 (When):** <입력과 실행 순서; 동시성 사례라면 경쟁 조건>
- **기대 결과 (Then):** <외부에서 확인 가능한 응답·저장 상태·불변식; 실패 후 남지 않아야 할 상태도 명시>
- **검증 경계:** <단위/컴포넌트/통합 등 해당 행동을 확인할 경계와 선정 이유>
- **기존 검증과 대응:** <관련 테스트의 경로·사례와 충분성; 신규/보강이 필요한 차이>
- **결정성·한계·비용:** <시간·외부 연동·격리·대역 가정과 CI 영향; 해당 없으면 해당 없음, 확인하지 못했으면 미확인과 이유>
```

기대 결과가 미결정이면 이를 명시하고 해결할 정책 질문을 적는다. 기존 검증을 찾지 못했으면 없다고 단정하지 말고 조사 범위와 미확인 상태를 적는다. 계획 단계의 케이스에는 실행 전인데 통과했다고 쓰지 않는다.

## 구현 단계에 넘길 품질 조건
- 회귀 사례는 잘못된 동작에서 실패하고 수정 후 통과하는지 확인하도록 계획한다. 기존 결함을 재현하지 못했거나 신규 기능이라면 증명할 수 있는 범위와 한계를 밝힌다.
- assertion은 요구사항의 결과와 불변식을 검증하고, 구현 내부의 우연한 형태에 의존하지 않도록 한다.
- 테스트가 결정적이고 다른 실행과 격리되는지, 회귀 방지에 충분하면서 범위가 과하지 않은지 확인한다.
- 실제 CI 실행 비용이나 환경·대역 가정의 영향은 구현 후 검증 결과로 확인한다. 이 단계에서는 계획과 확인된 근거만 제시한다.
- 별도 요청 없이 테스트 프레임워크를 광범위하게 교체하거나 테스트 기반 구조를 재설계하지 않는다.

결과는 [Plan Issue 작성](plan-issue.md)의 테스트 계획과 완료 기준에 반영한다. 별도 테스트 계획 문서를 만들지 않는다. 명세가 바뀌면 engineering-planning에서 관련 결정을 갱신하며, 최종 계획의 검토·승인 절차 안에서 테스트 범위도 확인한다.
