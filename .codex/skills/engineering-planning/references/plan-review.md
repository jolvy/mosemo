# Plan 리뷰

## 호출 시점
- 사용자와 필요한 정책·설계를 정리하고 Plan Issue 본문 초안을 완성한 뒤, 사용자에게 최종 승인·게시를 요청하기 전에 `plan-reviewer` subagent를 호출한다. 탐색 대화의 매 응답이나 설계 선택마다 호출하지 않는다.
- 게시하지 않는 최종 계획안에도 같은 검토를 적용하되 Issue 생성을 요구하지 않는다. 도메인·영속성 모델링만 요청받았다면 Plan 초안이나 리뷰를 강제하지 않는다.
- 이미 게시된 Issue는 범위·설계·작업 의존성·완료 기준이 실질적으로 바뀌는 수정안을 대상으로 검토한다. 같은 본문을 게시 직후 다시 검토하거나 문구 수정만으로 전체 리뷰를 반복하지 않는다.
- 하위 티켓 분할안은 사용자에게 분할 승인을 요청하기 전에 범위 누락·중복·의존성·단독 착수와 완료 가능성에 한정해 검토한다. 근거 있는 충돌이 없으면 승인된 상위 설계를 다시 심사하지 않는다.

## 전달할 근거
검토할 본문 전체와 버전 식별자(임시 파일의 내용 해시 등), 합의한 범위·제외 범위와 실제 승인 근거, 관련 문서·코드 탐색 시작점, 구조 검사 결과를 전달한다. 수정안이면 비교할 이전 본문과 변경 이유를, 재검토면 지적별 처리 내역과 수정된 본문을 제공한다. PRD·ADR은 존재하는 경우에만 참조하며 별도 문서 작성을 선행 조건으로 삼지 않는다.

GitHub Issue 본문이 게시된 Plan의 원본이라는 정책을 유지한다. 초안·내보낸 본문은 임시 파일로 전달하고 저장소에 Plan 복제본을 만들지 않는다. 아직 게시되지 않은 초안을 게시된 사실이나 승인된 계획으로 표현하지 않는다.

## 검토 기준
리뷰어는 [agent 정의](../../../agents/plan-reviewer.toml)에 따라 읽기 전용으로 검토한다. 핵심 질문은 “다른 구현자가 이 계획에서 무엇을 추측해야 하며, 그 추측이 어떤 실패로 이어지는가?”다.

- 합의한 요구사항과 제외 범위가 작업·테스트·완료 기준에 일관되게 연결되는지 확인한다.
- 현재 코드·테스트·마이그레이션을 필요한 만큼 읽어 계획의 전제를 확인한다. 현재 구현과 의도한 변경을 구분한다.
- 해당 변경의 가정을 깨뜨릴 구체적인 반례를 골라 책임·저장·트랜잭션·실패·복구 경로를 따라간다. 관련 없는 항목을 채우거나 모든 조합을 열거하지 않는다.
- 작업 순서와 선행 조건, 중간 배포 상태가 실행 가능한지, 추가 구조가 구체적인 실패 예방이나 변경 비용 감소에 기여하는지 확인한다.
- 지적에는 `문제 위치 → 발생 조건 → 결과 → 근거 → 최소 보완안 → 확인 방법`을 포함한다. 확인된 누락·모순, 조사할 가정, 사용자 정책 결정, 선택적 개선을 구분한다.

## 반영과 종료
1. 작성자가 지적의 타당성을 판단해 유효한 지적을 반영하고, 반영하지 않은 지적에는 근거를 남긴다. 리뷰어가 파일·Issue를 수정하거나 정책·모델을 승인하지 않는다.
2. 이미 합의한 내용의 구체화는 작성자가 반영한다. 새로운 정책이나 승인된 모델의 실질적인 변경이 필요하면 영향과 추천안을 사용자에게 제시하고 해당 부분만 결정·재승인받는다. 리뷰 결과로 기존 승인을 무효화하거나 모든 승인을 반복하지 않는다.
3. 수정된 지적과 영향 범위를 같은 리뷰어에게 재검토받는다. 동일 원인의 수정·재검토는 최대 3회로 제한한다. 미해결 지적·정책 질문은 남은 문제로 명시하고 해당 범위를 확정하지 않는다. 선택적 개선은 자동으로 승인 차단 사유가 되지 않는다.
4. 구조 검사를 최종 본문에 다시 실행하고, 리뷰 반영 결과와 남은 위험을 포함한 최종안을 사용자에게 제시한다. 리뷰 통과는 사용자 승인이나 게시 권한을 대신하지 않는다. 기존 승인이 현재 본문에도 유효하고 등록·갱신 권한도 이미 받았다면 같은 승인을 반복 요청하지 않는다.

검토 완료는 계획의 검토 결과다. 구현·테스트 통과나 배포 완료로 보고하지 않는다. 리뷰 보고서를 별도 영구 Plan 문서로 만들거나 자동으로 GitHub 댓글에 게시하지 않는다.
