# 도메인 모델링 — 사용자 승인 필수

## 입력
사용자와 합의한 범위·기대 결과 또는 승인된 PRD와 실제 도메인 코드를 확인한다. 용어집·ADR은 존재하는 경우 참조하며, 선행 Skill 실행이나 PRD 파일을 요구하지 않는다. DB 테이블과 ORM 클래스에서 책임을 역추론해 고정하지 않는다.

## 모델 판단
합의한 요구사항의 목적·관점·범위에 맞춰 아래 항목 중 관련된 것을 검토한다. 모델은 그 목적을 위한 선택이며 현실 전체의 정답이라고 가정하지 않는다. PRD나 기존 결정에 답이 있으면 재질문하지 않는다. 개념 분류보다 객체의 행동·책임·협력을 중심에 둔다.

### 동일성
- 동일성을 판단하기 전에 후보 개념 하나가 무엇을 대표하고 어디까지를 포함하는지 한 문장으로 적는다. 원본 사실·파생 구간·표시용 묶음처럼 서로 다른 단위를 혼동하지 않는다. 예를 들어 관찰 활동 구간 하나와 라벨 타임라인의 표시용 묶음 하나는 같은 단위가 아니다.
- 이 업무에서 무엇을 시간 경과와 변경 후에도 같은 대상으로 추적하는지 정한다. 같은 이름·값·물리적 대상·시스템 ID·저장 기록은 서로 다른 동일성 기준일 수 있다. 이름이 같다는 이유로 다른 맥락의 개념을 합치지 않는다.
- 생성·재생성·정정·병합·분리 중 어떤 변화가 동일성을 유지하거나 새 대상을 만드는지 관련 시나리오로 확인한다. 표시명 변경, 다른 시스템의 식별자 및 중복 요청을 대상의 동일성과 혼동하지 않는다. 식별자 발급만으로 동일성이나 중복 판정이 해결됐다고 보지 않는다.
- 값인지, 동일성과 생명주기를 가진 객체인지, 다른 객체와의 관계인지 책임과 규칙을 근거로 판단한다. 물리적으로 독립된 존재일 필요는 없으며 모든 중요한 개념에 별도 Entity를 만들지 않는다. 저장 키 선택은 영속성 모델링에서 구체화한다.

### 사실·해석·불확실성
- 해당 도메인에서 확보한 정보와 추론·해석한 결과를 구별할 필요가 있는지 확인하고, 필요한 경우 각각의 근거와 결정·확정 권한을 명시한다. 특정 관찰·분류·승인 단계가 항상 존재한다고 가정하지 않으며, 확정된 정책 없이 추론을 사실로 취급하지 않는다.
- 정보의 부재·미확인·해당 없음·미결정·추정·충돌 등이 업무 결과를 다르게 만든다면 필요한 구분만 명시한다. 불완전한 정보에서 허용되는 행동과 확정·정정 권한, 새 정보가 들어왔을 때의 전이를 정한다. 모든 값에 공통 상태 체계를 강제하지 않는다.
- 정보나 판단의 변경·정정이 필요한 경우, 무엇을 보존하고 무엇을 갱신할지 업무 규칙에 따라 정한다. 과거 기록·현재 상태·후속 판단에 미치는 영향을 확인하고, 미확정 정책은 추정으로 확정하지 않는다. 사건을 구분했다는 이유만으로 메시지 발행이나 이벤트 저장을 도입하지 않는다.

### 관계의 의미와 책임
- 관계가 나타내는 업무 의미, 참여자의 역할, 생성·변경·종료 조건과 허용 개수·필수 여부를 확인한다. 관계를 단순한 연결이나 FK로만 해석하지 않는다.
- 관계의 상태·기간·역할 등 정보가 있다면 그 규칙을 누가 판단하고 변경할지 정한다. 독립적인 동일성·생명주기·행동이 필요한 경우에만 관계 객체나 사건으로 표현할지 검토한다. 속성이 있다는 이유만으로 Entity나 Event로 승격하지 않는다.
- 참여 객체의 로컬 불변식과 관계 전체의 규칙을 구분한다. 여러 객체의 상태에 의존하는 판단은 필요한 정보를 가진 객체의 협력으로 설계하고, 관계에 대한 결정과 변경 책임이 호출자 여러 곳에 흩어지지 않도록 한다.

### 반례 검증
- 유스케이스의 정상 예시와 모델의 가정을 깨뜨릴 수 있는 관련 반례를 비교한다. 중복·재생성·정정·시간 경과·불완전한 정보·관점 충돌·병합·분리 중 이번 변경에 해당하는 사례만 선택한다.
- 각 사례에서 같은 대상인지, 어떤 정보와 판단이 유효한지, 누가 결과를 결정하고 상태를 바꾸는지 설명한다. 외부 호출 실패·재시도·역순 입력 등이 도메인 결과를 바꾼다면 함께 검토한다.
- 선택한 반례는 `깨뜨릴 가정 → 기대 도메인 결과 → 남은 미결정(없으면 없음)`으로 짧게 설명한다. 예: `라벨 값이 없으면 모두 미확정이다 → 사용자가 미분류로 확정한 활동은 검토 대기에서 제외된다 → 없음`. 불변식이나 책임이 유지되지 않으면 모델을 보완하고, 기대 결과가 정해지지 않았다면 정책 질문으로 남긴다.
- 자동화할 사례의 상세는 [테스트 시나리오 계획](propose-tests.md)에 연결하고 여기서 중복 작성하지 않는다. 사례 검토를 실행된 자동화 테스트나 구현 검증으로 표현하지 않는다.

## 수행 절차
1. 유스케이스의 목표, 업무 사실, 규칙, 불변식과 처리 결과를 식별하고 후보 개념의 대표 단위와 경계를 명시한다.
2. 위 모델 판단을 적용해 참여 객체의 **책임·자율성·메시지·협력 상대**를 정한다. Entity/VO/Aggregate/Domain Service 분류는 필요할 때만 한다.
3. 정보 전문가, Tell Don't Ask, 응집도, 결합도, 불변식의 소유자, 외부 인프라 누출 여부를 검토한다.
4. **채팅 응답에 Mermaid flowchart 객체 협력 지도**를 그린다. 노드에는 역할을, 간선에는 요청 메시지를 표시한다. 복잡한 시나리오에는 Mermaid sequenceDiagram을 덧붙인다.
5. 그림 아래에 책임/협력 근거, 대안, 자율성 위험, 관련 반례의 결과와 아직 알 수 없는 정책을 요약한다.
6. 사용자에게 **추천 모델과 수정 가능 선택지**를 제시하고 명시적인 OK/승인을 요청한다.
7. 수정 요청 시 시각화를 갱신하고 다시 승인받는다. 승인된 책임·협력·제약과 남은 미결정을 engineering-planning에 반환한다. 영속성 모델링 등 다음 단계의 필요성은 조율 단계에서 판단한다.

## 산출물과 경계
- **영구 파일을 생성하지 않는다.** ERD, 클래스 도표, 객체지도 Markdown도 만들지 않는다.
- Domain Entity는 DB Entity와 별개이다. 파일이 필요하다는 이유로 설계 그림을 문서화하지 않는다.
- 승인 대상·버전, 주요 결정, 근거, 유효 범위, 승인 주체·시점과 상태는 기존 Plan Issue 본문에 남긴다. Plan 생성 전 승인은 생성 시 반영한다. 새 세션에서는 해당 기록과 현재 범위를 대조하여 유효한 승인을 재사용한다. 근거가 없거나 범위가 달라졌다면 확인한다. 그림과 대화 원본은 저장하지 않는다.
- 모델을 실질적으로 변경할 필요가 생기면 관련 그림을 다시 보여주고 재승인을 받는다.

## 종료 조건
시각화와 책임·자율성 검토가 제시되고 **명시적인 사용자 승인**을 받기 전에는 다음 단계로 넘어가지 않는다.
