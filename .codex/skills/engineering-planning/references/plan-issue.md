# Plan Issue 작성

## 적용 범위
GitHub Plan Issue 등록·갱신을 요청받거나, 설계·계획안 제시 후 게시 여부를 물어 사용자가 동의한 경우에 적용한다. 게시에 동의하지 않은 작업에는 Issue 생성을 요구하지 않는다.

## 원본 정책
- **GitHub Issue 본문이 Plan의 유일한 Source of Truth**다. `docs/plans/`에 Plan 파일을 새로 생성하거나 Issue와 동기화하는 복제본을 두지 않는다.
- PRD, ADR, 유비쿼터스 언어는 기존 Git 문서로 유지한다. 모델링 그림은 대화에서만 시각화하고 승인받는다. 승인 대상·버전, 주요 결정, 근거, 유효 범위, 승인 주체·시점 및 상태는 기존 Plan Issue 본문의 승인 기록에 남긴다.
- 계획의 범위·순서·인수 조건·진행 상태·위험이 변경되면 해당 Issue를 수정한다. 댓글은 토론과 근거로 활용하지만 최종 최신 계획은 본문에 반영한다.
- 하나의 기능 Plan은 상위 Issue 한 개로 관리한다. 분할이 필요하면 하위 작업 Issue를 만들고 상위 Plan Issue에 링크와 상태를 연결한다. 동일 내용을 복제하지 않는다.

## PRD·ADR 참조 표기
- GitHub에 게시된 문서는 실제로 열람 가능한 파일 링크를 사용한다. 승인된 버전을 식별할 수 있으면 해당 commit 링크를 사용한다. 로컬 변경과 게시된 내용이 같다고 추정하지 않는다.
- 아직 commit·push하지 않았거나 해당 버전이 로컬에만 있는 문서는 저장소 상대 경로와 `로컬 문서, 미게시` 상태를 일반 텍스트 또는 인라인 코드로 적는다. GitHub에서 열리는 링크처럼 표시하거나 존재하지 않는 URL을 만들지 않는다.
- 문서 게시를 Issue 발행의 선행 조건으로 강제하지 않는다. 이후 해당 문서 버전이 게시되면 같은 Issue의 참조를 실제 링크로 갱신한다. 이 규칙 자체가 문서 commit·push 권한을 부여하지는 않는다.

표기 예시:

```text
PRD: docs/prd/example.md — 로컬 문서, 미게시
ADR: docs/adr/0006-example.md — 로컬 문서, 미게시
```

## 선행 조건
1. 사용자와 합의한 범위·기대 결과 또는 승인된 PRD와 필요한 설계 검토 결과, 코드·마이그레이션·테스트를 확인한다. PRD·ADR은 존재하는 경우 참조하고, 없으면 합의 근거를 Issue에 기록한다. Issue 작성을 위해 별도 PRD를 만들지는 않는다.
2. 수행한 모델링과 중요한 기술 결정의 승인을 확인한다. 생략한 모델링은 해당 없음과 이유를 적는다. 기존 Plan Issue의 승인 기록과 현재 대상·범위를 대조하여 유효한 승인은 재사용하고, 달라진 부분만 재승인받는다. 확인할 수 없는 승인을 만들어내지 않는다.
3. GitHub 저장소와 기존 Issue를 확인해 중복 생성·잘못된 저장소 등록을 방지한다.

## 수행 절차
1. 요구사항 및 제외 범위, 도메인 정책, 승인된 모델과 영향을 받을 코드·DB·API를 분석한다.
2. 현재 구현 대상과 미래 확장 방향을 분리하고 트랜잭션·동시성·인덱스·마이그레이션·운영 위험을 검토한다.
3. 아래 **GitHub Plan Issue 템플릿**으로 사용자에게 제안안을 제시한다. 제목은 `[Plan] <기능·변경 이름>`으로 작성한다.
4. **사용자 승인 후** 해당 저장소의 기존 Issue가 있는지 다시 확인하여 생성하거나 기존 Plan Issue 본문을 갱신한다. 연결 권한이 없다면 게시하지 못한 이유와 복사 가능한 본문을 보고한다. 게시한 것처럼 말하지 않는다.
5. 작업 분해는 Issue 본문의 체크리스트로 시작한다. 여러 담당자·독립 배포·독립 추적이 필요할 때만 하위 Issue를 생성한다. 하위 Issue 생성도 사용자 승인과 권한이 필요하다.
6. 이 Plan에 속한 구현·검증 작업에서는 Issue 번호/URL을 기준 식별자로 사용한다. PR에는 `Refs #<번호>`를 연결하며 실제 완료가 검증되기 전 자동 종료 문구를 남발하지 않는다.
7. 중요한 요구사항 변경은 영향 범위와 추천 수정안을 사용자에게 승인받은 후 Issue 본문을 갱신한다.

## 중단 및 완료 조건
- 승인되지 않은 모델이나 핵심 정책을 계획에 확정하지 않는다. 중요한 구조 변경은 engineering-planning에서 영향과 필요한 모델링·ADR을 다시 판단한다.
- GitHub Issue를 읽거나 쓸 수 없으면 **Plan 등록 미완료**로 보고한다. 임시 `docs/plans/` 파일로 우회하지 않는다.
- 완료 보고에는 Issue URL, 적용 범위, 승인 상태, 티켓 연결, 검증·미해결 위험을 포함한다.

## 추적과 변경 반영 규칙
- Requirement/PRD의 인수 조건에 `AC-1` 같은 안정적인 ID를 부여한다. 변경·삭제한 ID를 다른 의미로 재사용하지 않는다. 여러 PRD는 경로와 함께 식별하며 하나의 Plan 안에서는 ID가 충돌하지 않게 한다.
- Plan의 추적 표는 현재 범위의 인수 조건을 모두 포함한다. 현재 범위 PRD를 저장소 루트 기준 로컬 링크로 연결하면 검사기가 AC 누락을 대조한다. 일반 텍스트로 적은 로컬 경로는 같은 체크아웃의 파일을 직접 읽어 수동 대조한다. 외부 링크와 기존 ID 없는 PRD도 수동 대조하고, 각 행에 존재하는 T번호·검증 증거·통과/실패/미검증을 기록한다. 계획 단계는 미검증으로 시작한다.
- 증거는 실제 실행한 검사·결과와 대상 revision 또는 작업 트리 diff 식별자를 포함한다. 이전 코드의 통과 결과를 변경 후 증거로 재사용하지 않는다. 미실행은 이유를 적고 미검증으로 남긴다.
- 승인 기록은 인간 승인의 요약이며 기계적 승인 인증이 아니다. 그림과 대화 원본은 복제하지 않는다. 아직 Plan이 없다면 대화의 실제 승인 근거를 Plan 생성 시 기록한다.
- 시연 후 피드백은 `문구/표현`, `동작·정책`, `객체 책임·저장 구조`, `공개 계약/운영`으로 분류한다. 문구 변경은 관련 문서·작업·검증만 갱신한다. 동작·정책 변경은 Requirement/PRD·AC와 사용자 승인을, 책임·저장 구조 변경은 해당 Modeling 재승인을 갱신한다. 계약/운영 변경은 관련 AC·OpenAPI·마이그레이션·배포 검증 및 중요한 ADR의 영향을 검토한다.
- 새 범위가 기존 승인에 포함되는지 확인한 뒤 필요한 부분만 재승인받는다. 재승인이 필요한 기록은 `재승인 필요`로 바꾸고 해당 구현을 확정하지 않는다.
- Issue 게시·갱신 전 본문을 임시 파일로 내보내 `uv run --locked python .codex/skills/verification/scripts/validate_docs.py --plan /tmp/plan.md`로 검사한다. 임시 파일은 검사용이며 저장소에 Plan 복제본을 만들지 않는다. 외부 링크의 실존·승인 진위·PRD와의 의미적 일치는 별도 검토한다.
