# 제품 명세 작성

## 시작과 읽을 자료
사용자 요청·대화에서 확인한 요구사항으로 독립적으로 PRD를 작성·검토·수정할 수 있다. requirement-discovery 실행이나 별도 요구사항 파일은 선행 조건이 아니다. `AGENTS.md`와 코드의 현행 계약을 확인하고, 용어집·요구사항 파일·관련 PRD·ADR은 존재하는 경우 참조한다. 핵심 기대 동작이 부족하면 해당 결정만 확인한다.

## 절차
1. 요구사항의 출처·확정 여부·상충 정책을 확인한다. 의미를 추측해서 확정하지 않는다.
2. 아래 내장 PRD 템플릿의 순서로 문제, 목표/비목표, 행위자, 현재 범위, 기능 요구, 정책/경계, NFR, 확장 방향, 인수 조건과 미결정을 작성한다.
3. 파일명은 `docs/prd/<기능-슬러그>.md`(소문자 kebab-case). 기존 파일이 있으면 중복 파일을 생성하지 않고 변경안을 제시한다.
4. 인수 조건은 관찰 가능한 Given/When/Then 또는 동등한 명세로 작성한다. 성능 수치는 근거 없이 발명하지 않는다.
5. 구현 기술과 데이터 스키마를 PRD의 확정된 요구로 오인하지 않는다. 필요한 설계 판단은 engineering-planning에서 조율한다.
6. 현재 구현 범위와 추가 제공자 같은 미래 변형 축을 분리하고 미구현 기능은 제외 항목에 둔다.
7. 문서 검사 및 기존 요구사항과의 일관성 검토를 수행한다. PRD·인수 조건의 정상·경계 사례가 용어집의 의미와 일치하는지 확인한다. 새로운 의미나 충돌은 [유비쿼터스 언어](../ubiquitous-language/SKILL.md) 절차로 검토하고, 제품 동작이 바뀌면 영향받는 요구사항도 갱신한다. PRD 작성 중 용어의 의미를 조용히 바꾸지 않는다.

## 승인 게이트
주요 PRD 내용과 인수 조건을 사용자에게 제시한다. 명세를 확정할 때는 명시적 검토·승인을 받는다. 초안 작성·검토만 요청받았다면 승인 상태와 미결정을 보고하고 종료할 수 있다. 미승인 PRD를 확정으로 선언하지 않으며 engineering-planning으로 자동 진행하지 않는다.

## 완료 기준
요청한 작성·검토·수정 결과, 문서 경로, 검증 결과와 미해결 위험을 보고한다. 초안은 미승인 상태로 종료할 수 있으며, 명세 확정을 요청받았다면 사용자 승인을 확인한 뒤 확정으로 보고한다.

## 내장 문서 템플릿

```markdown
# <기능명> PRD

## 문제와 배경

## 목표와 비목표

## 사용자와 사용자 시나리오

## 현재 구현 범위

## 기능 요구사항

## 정책·제약·엣지케이스

## 비기능 요구사항

## 확장 방향
<!-- 확장할 변화의 축. 미구현 기능은 별도 -->

## 인수 조건
- AC-1 <관찰 가능한 조건과 결과>
<!-- 사용자 관점에서 검증할 수 있도록 작성 -->

## 미결정 사항과 가정

## 관련 요구사항과 ADR
```

## 변경과 추적
인수 조건은 안정적인 AC-번호로 식별한다. 관련 Plan Issue가 있으면 작업·검증 증거와 연결하며, PRD 작성을 위해 Issue를 새로 만들지는 않는다. 시연 피드백으로 정책·동작이 바뀌면 영향받는 조건과 범위를 갱신하고 필요한 사용자 승인만 다시 받는다. 문구 보완은 기존 승인 범위 안에서 반영한다.
