# 요구사항 탐색

## 시작 조건과 입력
- 새로운 기능, 정책 변경, 기존 기능의 모호한 요구를 분석할 때 독립적으로 실행한다. 선행 Skill이나 문서 작성을 요구하지 않으며, 요청받은 탐색 범위에서 종료할 수 있다.
- `AGENTS.md`와 현재 코드·테스트를 확인하고, 연관 PRD·ADR은 존재하는 경우 읽는다. `docs/ubiquitous-language.md`는 있으면 읽으며, 파일 부재를 탐색 중단 사유로 삼지 않는다.
- 이미 결정된 내용을 반복 질문하지 않는다. 코드가 현행 동작을 보여도 그것을 곧바로 업무 정책으로 확정하지 않는다.

## 수행 절차
1. 사용자 목적, 행위자, 현재 범위와 제외 범위를 정리한다.
2. 정상·예외·경계 시나리오, 권한, 실패, 재시도, 중복, 순서, 동시성, 보안·개인정보, 관측성·성능을 관련성에 따라 점검한다.
3. 업무 사실·확정된 정책·가정·미결정 사항을 분리하고 기존 용어집과 충돌하는 표현을 찾는다. 새로운 업무 개념이나 정의의 공백·충돌이 있으면 [유비쿼터스 언어](../ubiquitous-language/SKILL.md) 절차로 이번 범위의 용어를 합의하고 `docs/ubiquitous-language.md`를 작성·갱신한다. 기존 사용자 결정은 재사용하고 미합의 의미는 요구사항의 미결정으로 남긴다.
4. 미래 기능 목록을 임의로 늘리지 말고, 사용자가 원하는 **변화의 축**과 허용 변경 범위를 정리한다. 현재 지원 대상과 미래에 쉽게 추가할 대상은 구분한다.
5. 답변에 꼭 필요한 정책 결정만 질문한다. **모든 질문에 추천 선택지, 이유, 반대 선택의 비용**을 붙인다. 질문에 답했다는 이유만으로 모델 승인으로 간주하지 않는다.
6. 기능이 충분히 구체화되면 이 Skill의 **내장 문서 템플릿**를 사용해 `docs/requirements/<기능-슬러그>.md` 초안을 만든다. 기존 문서가 있으면 중복 생성 대신 수정 제안을 먼저 제시한다.
7. 문서 검증을 수행하고 확인하지 못한 내용과 인수 조건을 보고한다.

## 사용자 승인과 중단
- 정책 또는 제품 범위의 중요한 결정은 사용자에게 추천안과 함께 검토를 요청한다.
- 탐색·초안 작성만 요청받았다면 미결정과 확정 여부를 보고하고 종료한다. specification으로 인계하는 경우에는 요구사항 초안의 확정을 확인한다. 사소한 문장 수정을 위해 매번 재승인을 요구하지 않는다.
- 미해결 사항이 핵심 동작을 바꾸면 그 지점에서 멈추고 질문한다.

## 완료 기준
현재 범위, 제외 항목, 검증 가능한 인수 조건, 확장 방향, 미결정 사항이 구분되어 있고 문서 검사 결과를 제시했다.

## 내장 문서 템플릿

새 문서는 다음 형식으로 작성한다. 괄호형 자리표시자와 HTML 주석은 실제 산출물에서 제거하고, 확정되지 않은 항목은 미결정으로 명시한다. 기존 문서에는 형식을 강제로 소급하지 않는다.

```markdown
---
status: draft
---
# <요구사항 제목>

## 목적과 사용자
<!-- 누구의 어떤 문제를 해결하는가 -->

## 현재 구현 범위
<!-- 반드시 지금 제공하는 행동 -->

## 기능 요구사항
<!-- 식별 가능한 조건·행동·결과 -->

## 정책과 불변식
<!-- 확정된 규칙. 가정은 아래로 분리 -->

## 예외와 경계 조건
<!-- 권한·중복·역순·동시성·실패·보안 등 해당 항목만 -->

## 비기능 요구사항
<!-- 수치가 미확정이면 목표를 꾸며내지 말 것 -->

## 확장 방향
<!-- 미래에 무엇을 쉽게 추가/교체해야 하는가. 구현 범위와 구분 -->

## 제외 범위

## 인수 조건
- AC-1 <관찰 가능한 조건과 결과>
<!-- 검증 가능한 Given/When/Then 또는 동등한 형식 -->

## 확인된 사실·가정·미결정
<!-- 정책 질문마다 추천 선택지와 근거 -->

## 관련 PRD·ADR·티켓
```

## 변경과 추적
인수 조건은 안정적인 AC-번호로 식별한다. 관련 Plan Issue가 있으면 작업·검증 증거와 연결하며, 탐색을 위해 Issue를 새로 만들지는 않는다. 시연 피드백으로 정책·동작이 바뀌면 영향받는 조건과 범위를 갱신하고 필요한 사용자 승인만 다시 받는다. 문구 보완은 기존 승인 범위 안에서 반영한다.
