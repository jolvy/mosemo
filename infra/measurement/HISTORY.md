# 성능 측정 이력

활동 분석 기능을 목표 규모(하루 활성 사용자 1천 명, 1천 DAU)에서 버틸 수 있는지 확인하려고 2026-11-13부터 2026-11-16까지 여덟 번 측정했다. 측정마다 목표, 배경, 테스트 방법, 판정 기준, 결과, 이후 결정, 사용한 도구를 적는다. 숫자는 각 측정 보고서에 적힌 값을 그대로 옮겼다. 시각에 `Z`가 붙으면 UTC다. 그 밖의 시각은 KST다.

## 2026-11-13 측정 준비 로컬 드라이런(5단계 T0)

**목표** AWS 측정 전에 측정 절차 전체(시드 생성 → 덤프 → 복원 → 검증 → 측정 → 요약)가 끝까지 도는지, 측정 Pod 메모리 상한이 충분한지 로컬에서 확인하고 실제 측정용 시드 덤프를 만든다.

**배경** AWS 랩 측정은 Pod 수명(12시간) 안에 끝내야 하고 중간에 고치기 어렵다. 측정기(하네스)가 새 분석 경로의 참조 구현과 같은 값을 내는지도 먼저 확인해야 했다.

**테스트**
- 환경: Mac 로컬 일회용 postgres:18.3 컨테이너. 복원은 메모리 768Mi로 제한한 별도 컨테이너에서 돌렸다.
- 드라이런 1(PG 18.6, 10명 × 3일), 드라이런 2(18.3, 덤프 → 복원 경로), 드라이런 3(10명 × 2일 + 90일 계정 1개, 768Mi 복원, 모드별 최대 RSS 기록). 장기 계정을 측정에서 빼는 드라이런 4를 더 했다.
- 실제 시드: 1천 명 × 2일 + 90일 계정 1개를 만들어 `pg_dump -Fc -Z 6`으로 덤프했다.

**판정 기준** 합격 기준을 따로 두지 않은 준비 단계다. 오류 0, 하네스와 참조 구현의 결과 불일치 0, 측정 Pod 메모리 상한(tools 768Mi, pg 512Mi) 안을 확인 항목으로 봤다. 로컬 응답 시간은 판정 근거로 쓰지 않았다.

**결과**
- 드라이런 3: 오류 0, 검증 429건(날짜 110, 세션 319) 불일치 0. 768Mi 클라이언트 복원 46초, cgroup peak 58MiB.
- 최대 RSS: 하네스 `verify` 190MB, `m7` 168MB, 그 밖 62MB 이하. 동시 실행 최악도 약 160MB라 상한 안이었다.
- 실제 시드: 적재 2,227초(37분), DB 12.63GB, 덤프 1,186,556,574 B(1.19GB), 덤프 165초.
- 계정 삭제(M10): 구간 FK 두 열에 인덱스가 없어 90일 계정 레코드 500행 삭제에 1,198ms가 걸렸다. 후보 인덱스가 있으면 레코드 전체 삭제가 18.75초였다.
- 고친 절차 결함 9개 중 큰 것: 백그라운드 CPU 표본 프로세스가 고아로 남던 문제, 시드 WAL이 디스크를 더 쓰던 문제(`max_wal_size` 8GB → 2GB).

**이후 결정** 측정 Pod는 `mosemo` 네임스페이스에 requests/limits를 명시해 둔다. M10은 롤백 표본(M10a)과 후보 인덱스(M10b)로 나눠 재고, 구간 FK 인덱스는 7B 마이그레이션 후보로 넘겼다. 장기 계정은 검증·부하 대상에서 뺀다.

**사용한 도구** 5단계 T0 하네스·도착률 생성기·절차 스크립트·측정 Pod 매니페스트(원본은 저장소 밖 보관). 일부는 이후 `infra/measurement/`의 도구로 이어졌다.

## 2026-11-14 AWS 1차 측정(db.t4g.micro)

**목표** 새 활동 분석 경로가 1천 DAU 데이터에서 응답 시간 목표를 지키는지 AWS에서 처음 잰다.

**배경** 가장 작은 DB 사양으로 먼저 쟀다.

**테스트**
- 환경: AWS 시드니(ap-southeast-2) EKS 랩, RDS PostgreSQL db.t4g.micro(CPU 2개·메모리 1GiB, 크레딧제), 노드 t3.small.
- 데이터: 1번 측정에서 만든 시드(계정 1,001개, 약 11GB).
- 시나리오·부하·측정 방식은 3번 측정과 같다. 측정 Pod는 2026-11-13 UTC에 돌았다.

**판정 기준** 3번 측정과 같은 사전 등록 기준 P1~P5.

**결과**
- "자정 직후 · 높음 · 1회차" 응답 p50 / p95 / p99: 133 / 8,195 / 11,384ms. 층별 p95(대기 · DB · 계산) 7,094 · 1,335 · 636ms.
- 자정 배치는 1천 날짜 중 100개만 처리했다(P5 불합격). 재처리 속도 시간당 2,285날짜.
- DB CPU 최대 78%(크레딧 0까지), 여유 메모리 최소 41MiB. 메모리 1GiB로 자주 쓰는 데이터도 담지 못해 읽기마다 디스크로 갔다(초당 읽기 최대 2,299회, 디스크 대기열 최대 27).
- 메모리 위급으로 DB가 자동 재시작됐고(17:56Z), 이후 측정이 실패해 측정기가 무한 대기했다. 재시작 시각은 DB 자동 백업 시간대(17:47~18:17Z) 안이었다(원인 후보로만 기록).

**이후 결정** DB를 db.m7g.large(메모리 8GiB, 크레딧 없음)로 바꿔 같은 측정을 다시 했다(3번).

**사용한 도구** 5단계 측정 하네스·절차 스크립트·측정 Pod(원본은 저장소 밖 보관).

## 2026-11-14 AWS 2차 측정(db.m7g.large)

**목표** 1차와 같은 측정을 DB 사양만 올려 다시 재고, 사전 등록한 합격 기준으로 판정한다.

**배경** 1차는 DB 메모리 부족으로 측정이 끝나지 못했다. 새 분석 경로는 아직 API로 배포되지 않아 두 부분으로 나눠 쟀다.

**테스트**
- 환경: 시드니 한 가용 영역, RDS db.m7g.large(CPU 2개·메모리 8GiB), 노드 EC2 t3.small(app·측정·Kafka 각 1). API 서버는 uvicorn 워커 1개(CPU 1개 상한).
- 데이터: 계정 1,001개(1천 명 × 2일 + 90일 계정 1개), 약 11GB.
- 측정 방식: 측정기가 새 경로 참조 구현으로 DB에 직접 질의·계산한 p95와, 기존 타임라인 API(`GET /api/v1/activities/timeline`)를 같은 부하로 호출한 p95를 더해 판정값으로 썼다. 요청은 포아송 도착.
- 시나리오: 기존 API(S0), 오늘 화면(S1), 지난 날짜 재계산(S2, 캐시 비움 S2c), 세션 화면(S3), 자정 직후(S4), 재처리 중(S5), 쓰기 섞임(W), 계정 삭제(M10).
- 부하: 보통 L1 초당 4건 × 10분(오늘 화면은 30분), 높음 L2 초당 10건 × 10분, 계단 L3 10 → 20 → 40 rps 각 3분. 회차 2회, 두 회차 p95가 20% 넘게 다르면 3회차.
- 측정 시각 2026-11-14 05:22~14:17Z. 서버·DB 지표는 CloudWatch 1분 값.

**판정 기준** 측정 전에 고정했다. P1 판정값 p95 ≤ 300ms, p99 ≤ 500ms(S1·S3·S4·S5 × 보통·높음). P2 같은 기준(S2·S2c × 보통). P3 요청 오류 0, DB 시간 초과 0. P4 오늘 화면 처리 가능량 ≥ 1.9 rps. P5 1천 날짜를 자정 배치 1회 120초 안에 처리. 모든 회차가 각각 합격해야 합격.

**결과** 불합격(P1·P2 불합격, P3·P4·P5 합격).
- 새 경로 p95는 재처리 중을 빼면 높음에서도 80ms 이하였다.
- 기존 API p95는 보통 199·184ms, 높음 381·803·397ms(3회차까지)였다. API 서버가 요청을 한 번에 하나씩 처리하는 프로세스 1개라 줄이 길어졌다(요청 1건당 CPU 약 55ms, 노드 CPU에서 거꾸로 계산한 추정).
- P4 처리 가능량 12.4·12.5 rps. P5 4번 모두 1천 날짜 처리, 38.5~42.4초.
- 같은 측정 "자정 직후 · 높음 · 1회차"의 p95가 1차 8,195ms에서 7.2ms로 줄었다.
- 재처리 중이 느린 것(높음 p95 2,096~4,397ms)은 재처리 배치와 측정기가 같은 Pod·CPU 1개를 나눠 쓴 측정 구조 탓이다.
- DB CPU 최대 12%(측정 중), 여유 메모리 4.6GiB 이상. 크레딧 잔액 246 이상.
- 계정 삭제: 지금 구조에서 사용 기록 500행 삭제 81.3초. 구간 FK 인덱스를 만든 뒤 90일 계정 전체 삭제 37.5분.

**이후 결정** 원인은 DB·서버 사양이 아니라 API 단일 워커이므로 수평 확장으로 해결할 문제로 판단했다. API·업로드 한계를 따로 재고(4번), 서버 수를 늘린 기준 사양 측정(5번)으로 넘어갔다. 구간 FK 인덱스는 다음 DB 변경 후보, 계정 삭제 방식은 다음 설계 과제(8번)로 넘겼다.

**사용한 도구** 5단계 측정 하네스·절차 스크립트·측정 Pod·시간순 재배치 SQL(원본은 저장소 밖 보관).

## 2026-11-14 API·업로드 한계 측정(k6 계단 부하)

**목표** 실제 API 서버 1개와 업로드 처리기(consumer) 1개가 어디까지 버티는지 찾는다.

**배경** 2차 측정은 기존 API가 판정값을 밀어 올렸다. 서버를 몇 개로 늘려야 하는지 정하려면 1개의 한계가 필요했다.

**테스트**
- 도구 k6(일정한 간격 도착)로 단계별 부하를 걸었다. 각 단계 3분, 앞 30초 제외.
- 조회: 오늘 화면 API에 초당 4 → 6 → 8 → 10 → 15 → 20건.
- 업로드: Mac 앱처럼 약 10초씩 묶은 사용 기록(묶음당 평균 1.9건)을 초당 54묶음(1천 명 하루 평균), 109묶음으로 보냈다. 반영 지연은 접수 응답부터 DB 저장까지.
- 환경: 2차와 같다. 업로드 처리기 1개가 API 서버와 같은 app 노드(t3.small)에 있었다.

**판정 기준** 합격 기준 밖의 참고 측정이다. 오류·지연이 한도를 넘거나 밀린 묶음이 계속 늘면 단계를 멈췄다.

**결과**
- 조회: 초당 10건 p95 169ms, 15건 584ms, 20건에서 p95 4,652ms로 자동 중단. API 서버 1개의 조회 한계는 초당 10~15건, p99 500ms까지 지키려면 초당 6건.
- 업로드 초당 54묶음: API 응답 p95 35ms, 반영 지연 p50 / p95 / p99 15.5 / 24.2 / 25.2초, 밀린 묶음 439 → 0(60초 뒤).
- 업로드 초당 109묶음: 반영 지연 101 / 133 / 136초, 밀린 묶음 11,262 → 9,330으로 계속 밀려 중단.
- 처리기 1개(일꾼 2개 = 파티션 2개)의 한계는 초당 약 40~55묶음이었다. DB CPU는 10~11%, app 노드 CPU는 60~88%였다.

**이후 결정** 기준 사양을 API 4개, 처리기 4개, Kafka 파티션 8개로 정했다(API 1개가 업로드 초당 54묶음까지 여유 → 136 ÷ 54 ≈ 2.5에 여유를 둠). 다음 측정에서는 Pod별 CPU를 기록한다.

**사용한 도구** 5단계 k6 한계 측정 스크립트(조회·쓰기 계단)와 입력 준비 스크립트(원본은 저장소 밖 보관).

## 2026-11-15 기준 사양 측정(1천 DAU 피크 137.6 rps)

**목표** 코드를 바꾸지 않고 1천 명 피크 부하를 버티는 기준 사양을 정한다. 다음 개발 단계(7단계) 뒤 같은 사양·같은 부하로 다시 재서 비교한다.

**배경** 2차 측정과 한계 측정에서 병목이 API 단일 워커와 처리기 1개로 드러났다.

**테스트**
- 부하: 1천 명 피크 시간 초당 137.6건 = 조회 1.9건 + 업로드 135.7묶음(고정 부하 파일). 업로드가 98.6%라 사실상 쓰기 경로 측정이다.
- k6가 두 종류 요청을 일정한 간격으로 동시에 보냈다. 15분 × 2회, 앞 1분 웜업 제외, 끝난 뒤 1분 기다려 남은 업로드 반영을 확인했다.
- 환경: 노드 m7i.large × 6(app 4 · Kafka 1 · 측정 1), API 4개·처리기 4개(노드마다 1개씩), 파티션 8개, DB db.m7g.large. 데이터는 2~4번 측정이 남긴 그대로(계정 1,001개).
- 측정 구간 2026-11-14 15:36:27Z ~ 16:21:13Z(KST 2026-11-15). 처리기 CPU는 30초 간격 cgroup 사용량 차분, DB 통계는 30초 간격 `pg_stat_database`.

**판정 기준** 측정 전 고정, 회차마다 모두 만족. C1 조회 p95 ≤ 300ms, p99 ≤ 500ms. C2 전체 오류율 ≤ 0.1%. C3 업로드 반영 지연 p95 ≤ 10초. C4 밀린 묶음 증가 추세 없음. C5 부하 도구가 못 보낸 요청 0. C6 실제 보낸 양 목표의 ±2%.

**결과** 합격(2회 모두 6개 기준 통과).
- C1 조회 p95 / p99: 122 / 171ms, 132 / 183ms.
- C2 오류율 0%(조회 1,597건, 업로드 113,988·113,989건).
- C3 반영 지연 p95 0.069·0.073초. 끝나고 1분 뒤 반영 안 된 묶음 0.

## 2026-11-15~16 측정 A(7단계 뒤 재측정)

**목표** 7단계(다시 계산 표시 처리) 뒤 코드가 기준 사양에서 1천 명 피크 부하를 계속 버티는지 확인하고, 기준 측정과 자원 사용을 비교한다.

**배경** 7단계는 업로드 경로에 다시 계산 표시 처리기 질의를 더했다. 기준 측정 때 질의별 통계가 없어 DB CPU 47%의 원인을 가를 수 없었다.

**테스트**
- 사양·부하·판정은 5번과 같다(같은 부하 파일). 측정 2026-11-15 14:44~15:50Z(KST 11-15 23:44 ~ 11-16 00:50).
- 데이터: 5단계 시드를 이 저장소 마이그레이션 head로 변환한 덤프를 새로 복원(570초)하고, 시간순 재배치·VACUUM(366초) 뒤 측정했다. 업로드 처리기 외 batch는 돌리지 않았다.
- 회차마다 직전에 `pg_stat_statements`를 초기화하고 직후에 회수해 질의별 통계를 처음 기록했다.
- 자원 지표는 각 회차 k6 시작 + 60초부터 + 900초까지의 평균·최대로, 기준 측정과 같은 계산기로 다시 계산했다.

**판정 기준** 5번과 같은 C1~C6. 기준 측정과의 차이는 "7단계 + 데이터 상태 차이"의 합으로만 읽고 원인을 7단계로 단정하지 않는다(사전 등록 규칙).

**결과** 합격(2회 모두 C1~C6 통과).
- C1 조회 p95 / p99: 166.0 / 226.2ms, 150.1 / 193.2ms.
- C3 반영 지연 p95 0.096·0.087초, 유예 뒤 미반영 0. 오류 0.
- DB CPU 평균 30.1·29.9%(기준 47.2·47.5%, −37%).
- 업로드 묶음당 `blks_hit` 328·317(기준 4,021·4,081, 약 1/13).
- 처리기 CPU 평균 0.417 → 0.561코어(+35%), app 노드 CPU +9포인트.
- 7단계 표시 처리기 질의 4개가 업로드 경로 DB 실행 시간의 16.1%·15.8%, 버퍼의 10.4%·10.2%를 썼다. 묶음당 0.13ms·27블록.

**이후 결정** 7단계 뒤 코드는 기준 사양에서 합격으로 본다. 묶음당 블록 감소는 7단계보다 데이터 상태 차이 쪽일 가능성이 커 #290 로컬 조사로 확인하기로 했다. 다음 비교부터는 측정 A를 기준으로 삼고 같은 덤프를 다시 복원해 데이터 상태를 맞춘다. 복원 중 pg 컨테이너 메모리 최대 506.6MB(제한 512Mi)라 상한을 늘릴지는 다음 측정 전 후보로 남겼다.

## 2026-11-16 업로드 DB 읽기 비용 조사(#290, 로컬 재현)

**목표** 업로드 묶음 하나가 DB에서 예상보다 많이 읽는 원인과 개선 후보를 찾는다. 롤백 수가 커밋 수와 같은 이유도 확인한다.

**배경** 기준 측정에서 DB CPU가 47%로 측정 전 추정의 약 1.5배였고, 묶음당 버퍼 블록이 약 4,000개였다. 측정 A에서는 약 320블록이었다.

**테스트**
- 로컬 PostgreSQL에서 재현했다. 작은 시드에서 값이 재현되지 않아, 측정 A에 쓴 시드 덤프(계정 1,001개, 기록 1,140만 건, 10GB)와 기준 측정의 k6 스크립트·부하 파일을 로컬에 올렸다.
- 실제 경로 재현: k6 → API 4 → Kafka 파티션 8 → consumer 4, 5분, 초당 137.6건.
- 그 밖 확인: consumer 처리 함수 직접 호출(시드 계정 156개 × 2일, 묶음 1만 8천 개까지 누적), 늦게 온 관찰, 질의 계획 강제(맞춤·재사용), 90일치 계정과 2일치 계정 비교, 연결 확인(`pool_pre_ping`) 끄기.
- `pg_stat_statements`의 `shared_blks_hit`·`calls`와 `EXPLAIN (ANALYZE, BUFFERS)`로 질의별 블록을 봤다. 코드 수정·인덱스 추가·AWS 랩 기동은 하지 않았다.

**판정 기준** 원인 조사라 합격 기준은 없다. 묶음당 블록의 대부분을 차지하는 질의와 기록 길이에 따른 증가 여부를 찾는 것이 산출물이다.

**결과**
- 지금 코드의 업로드 묶음 하나는 버퍼 블록 약 280~330개를 읽는다. 실제 경로 재현 281블록, 랩 시드 덤프 290, 직접 호출 227(누적해도 일정), 계획 강제 280 / 256.
- 기록 길이에 따라 늘지 않는다(90일치 계정 307, 2일치 계정 302).
- 기준 측정의 약 4,000블록은 재현되지 않았다. 코드, 데이터 규모, 부하 모양, 실행 경로, 질의 계획은 원인이 아니었다. 남은 후보는 기준 측정 때의 DB 상태지만 남아 있지 않아 재현할 수 없다.
- 롤백 수 ≈ 커밋 수는 실패가 아니다. 연결 풀이 연결을 꺼낼 때마다 `BEGIN` → 확인 → `ROLLBACK`을 보낸다. 끄면 묶음당 롤백이 1.00 → 0.00이 되고 커밋·블록 수는 같다.
- 가장 큰 질의는 활동 기록 저장(호출당 약 32블록)이다. 7단계 표시 UPSERT는 호출당 약 13.5블록이었다.

**이후 결정** 지금 코드에 묶음당 수천 블록을 읽는 질의가 없어 개선 후보는 없다. 7단계 표시 쓰기도 지금 줄일 대상으로 보지 않는다.

**사용한 도구** 기준 측정과 같은 k6 스크립트·부하 파일: `k6-mixed-read-upload.js`, `k6-common.js`, `workload-137.6rps.json`(`infra/measurement/`). 그 밖의 재현 스크립트는 원본은 저장소 밖 보관.

## 2026-11-15~16 7B 데이터 삭제 방식 측정(로컬)

**목표** 야간 이관의 DB 삭제와 계정 삭제를 어떤 방식으로 할지 정하려고, 후보별 시간과 동시 부하 영향을 잰다.

**배경** 1~3번 측정에서 구간 FK에 인덱스가 없어 계정 삭제가 매우 느렸다(인덱스를 넣어도 90일 계정 37.5분). 7B 설계 전에 삭제 방식을 비교해야 했다.

**테스트**
- 환경: 일회용 PG 18.6 컨테이너(Docker 8GB·8 CPU)에 5단계 시드를 복원하고 head 마이그레이션 + 인덱스 후보 4개를 넣었다. DB 10GB, 레코드 1,140만 행. `shared_buffers=1GB`, `max_wal_size=1GB`.
- 동시 부하: pgbench 고정 비율로 조회 초당 10건, 쓰기 초당 45건. 지연은 삭제 SQL이 도는 구간에 시작한 트랜잭션만 셌다.
- 야간 이관 삭제(1천 계정 × 하루): 계정 하나 = 트랜잭션 하나(②), 레코드 2,000행씩 커밋(③), 각각 뒤에 명시 VACUUM.
- 90일 계정 삭제: 계정 행 CASCADE(①), 명시 순서 한 트랜잭션(②, 라벨·장치 인덱스 유무), 레코드 현지 날짜별 커밋(③).
- 추가 실험: 하루 1/90 삭제 뒤 VACUUM의 인덱스 처리(450만 행 표, 18일 반복), 시간순 재배치 뒤 계정 삭제가 읽는 페이지 수로 운영 시간 추정.

**판정 기준** 측정 전 등록. P1 야간 이관 DB 삭제 ≤ 30분. P2 90일 계정 DB 삭제 ≤ 5분. P4 실행 중 조회 p95 ≤ 300ms. P5 실행 중 쓰기 p95, 1초 넘는 잠금 대기 0건. P6 WAL ≤ 지운 데이터 크기의 2배. P7 부풀음 +20% 안. P8 죽은 행. 결과는 로컬 예측값이다.

**결과**
- 야간 이관: ② 127.0초(최장 트랜잭션 750ms), ③ 150.1초(최장 198ms). 둘 다 P1 통과. WAL 비율 1.87 / 1.34로 P6 통과.
- 삭제보다 뒤따른 VACUUM이 부하에 더 영향을 줬다. 쓰기 p95 15 → 212~293ms(최대 292.7ms), 조회 p95 최대 104.1ms. 1초 넘는 잠금 대기 0건.
- 90일 계정: ① CASCADE는 RESTRICT FK 위반으로 실패했다(복원 DB의 RI 트리거 순서). ② 10.6초, ③ 17.9초로 P2 통과(데이터 쏠림으로 왜곡된 값).
- 라벨 6행 삭제가 인덱스 없이 1,123ms, 라벨 FK 인덱스를 넣으면 12ms였다.
- P7·P8은 로컬로 판정할 수 없었다. P8의 "10%(autovacuum 기본값)"는 오류였다(실제 `autovacuum_vacuum_scale_factor` 기본값 0.2).
- 기본 VACUUM은 하루치(1.1%) 죽은 행에서 인덱스 처리를 건너뛰고 이틀치(2.2%)에서 처리했다. VACUUM 없이 18일 반복하면 표 +17%, 인덱스 +16%로 커졌다.
- 운영 90일 계정 삭제 추정: 비관(3,600 IOPS) 459초(7.7분), 낙관(12,000 IOPS) 138초(2.3분)로 "빠듯"이었다.

**이후 결정** 레코드·구간·확정·제안 4개 표에 `autovacuum_vacuum_scale_factor = 0.01`을 두고, P8은 "죽은 행 비율이 상시 10% 아래"로 바꿨다. 계정 삭제는 명시 순서 + 레코드 현지 날짜별 분할 커밋으로 하고, 운영 규모 비교는 랩 측정으로 넘겼다. 7B 마이그레이션 인덱스는 6개(구간 `first_event_id`·`last_event_id`, 확정·제안 `first_event_id`, 확정 `label_id`, 제안 `suggested_label_id`)로 정했다. 야간 이관 삭제는 계정·날짜마다 확정·제안·구간 한 트랜잭션 + 레코드 2,000행씩 커밋으로 정했다.

**사용한 도구** pgbench, auto_explain, 일회용 PostgreSQL 컨테이너. 삭제·VACUUM·페이지 흩어짐 실험 스크립트는 원본은 저장소 밖 보관.
