# 고정 부하 137.6 rps(조회 + 업로드) — 기준 사양 측정·7단계 뒤 비교용

생성: `k6_inputs_and_reports.py workload --total 137.6 --reflect-p95 10`(C3 줄의 「추천·확정 필요」 문구만 확정 표기로 손봄)(이 파일과 같은 이름의 `.json`을 k6 mixed가 읽는다). 사전 등록 형식이며, 측정 뒤 이 값을 바꾸지 않는다.
목적: 현재 코드 그대로 이 부하를 아래 기준 안에서 버티는 **기준 사양**을 정한다. 7단계 개발 뒤 같은 사양·같은 파일·같은 인자로 다시 재 비교한다. 최적화·프로파일링은 하지 않는다.

## 2. 실행

- 총 **137.6 rps × 15분**, **2회**. 앞 60초는 웜업으로 빼고 판정한다. 각 회차 뒤 60초 기다렸다가 반영 여부를 본다.
- consumer replicas는 실행 인자(1 또는 2, 토픽 파티션이 2개라 2를 넘으면 의미 없음)로 정하고 결과에 적는다. 원래 replicas를 기록하고 끝나면 되돌린다.
- k6 v2.3.0 constant-arrival-rate는 도착 간격이 일정해 포아송보다 몰림이 덜하다.

## 3. 판정 기준(회차마다 모두 만족, 2회 모두 통과해야 통과)

| # | 기준 | 값 | 재는 법 |
| --- | --- | --- | --- |
| C1 | 조회 지연 | p95 ≤ 300ms, p99 ≤ 500ms | k6 `http_req_duration{scenario:read, phase:main}`(사용자 결정 예산과 같음) |
| C2 | 전체 오류율 | ≤ 0.1% | 두 시나리오 합 `http_req_failed{phase:main}`(조회 200·업로드 202 아니면 오류) |
| C3 | 업로드 반영 지연 | **p95 ≤ 10초(사용자 확정 2026-11-14)** | 묶음별 전송 시각(k6 응답 끝 − 요청 시간) → `activity_batch_receipts.processed_at`. 유예 뒤까지 반영 안 된 묶음은 무한대로 센다 |
| C4 | 미처리 기울기 | 0(OLS 기울기의 95% 신뢰구간 하한 ≤ 0) | 실행 중 30초마다 "지금까지 보냈을 묶음 − 반영된 묶음" 표본, 웜업 뒤 표본의 시간 회귀. 양수로 확실하면 "처리 못 따라감" |
| C5 | 부하 발생기 | k6 `dropped_iterations` 0 | 시나리오별 |
| C6 | 도착률 | 목표의 ±2% | 웜업 뒤 시나리오별 시작한 요청 수 ÷ 시간 |

C3 근거: 오늘 화면은 보이는 동안 60초마다 새로고침한다(사용자 결정). 업로드가 다음 새로고침에 거의 늘 보이려면 반영 지연이 새로고침 간격보다 충분히 짧아야 한다. 클라이언트는 이미 10초 창으로 묶어 최대 약 10초 늦게 보낸다. 서버 쪽 반영 p95를 10초로 두면 "관찰 → 화면" 지연이 최악에도 묶음 10초 + 반영 10초 + 새로고침 60초 안이다. 로컬 검증의 반영 p95는 수십 ms였다.
