# 측정 B — 새 분석 API와 일간 통계 batch를 켠 운영 구성

이 파일과 `measurement-b.json`이 측정 B의 고정 기준이다. 측정 전에 정하고 측정 뒤 바꾸지 않는다. `run-load-measurement.sh`는 `measurement-b.json`의 sha256이 상수와 다르면 측정 B를 시작하지 않는다.

## 1. 답할 질문

- Q1(G1): 구간이 많은 날의 조회 계산이 같은 API Pod의 다른 요청을 얼마나 늦추는가. 계산을 스레드로 분리할지 정하는 근거다.
- Q2: 그 시간이 원천 읽기·스냅샷 변환·계산 중 어디에 있는가(조회 로그 `source_read_ms`·`snapshot_build_ms`·`compute_ms`).
- Q3: 일간 통계 batch와 새 API 조회를 켠 운영 구성에서도 기준 사양(API 4·consumer 4·m7i.large·db.m7g.large)이 판정을 통과하는가.

## 2. 회차

6회차, 순서 R1 R2 R3 R1 R2 R3. 회차마다 k6 900초(앞 180초는 데우기로 판정에서 뺀다), 회차 뒤 유예 60초. 같은 종류 2회 모두 통과해야 통과다.

| 시나리오 | k6 이름 | R1 | R2 | R3 | 내용 |
| --- | --- | --- | --- | --- | --- |
| 타임라인 조회 | `read` | 1.896 rps | 같음 | 같음 | 측정 A와 같음(2026-11-12 90%, 지난 날짜 10%) |
| 업로드 | `write` | 135.704 rps | 같음 | 같음 | 측정 A와 같음 |
| 일간 통계 조회 | `stats` | — | 1.896 rps | 같음 | `GET /api/v1/analytics/daily-stats?date=`. 서버 실제 오늘(Asia/Seoul) 90%, 시드 날짜(2026-11-11·11-12) 10% |
| 세션 분석 조회 | `sessions` | — | 0.139 rps | 같음 | `GET /api/v1/analytics/focus-sessions/{id}`. 시드의 완료 세션 중 무작위 |
| 구간 많은 날 조회 | `heavy` | — | — | 0.833 rps | 구간 1만 계정의 오늘 일간 통계 |
| 구간 수별 탐침 | `probe` | — | — | 1천·5천 계정 각 0.05 rps | 각 계정의 오늘 일간 통계 |

R2·R3의 총 도착률은 137.6 rps보다 크다.

## 3. 시작 상태

- 측정 A와 같이 `seed-7a.dump`를 빈 스키마에 복원하고 재배치·VACUUM한다.
- 구간 많은 계정 3개를 만든다. 오늘(Asia/Seoul) 활동 구간이 정확히 1천·5천·1만 개이고 오늘 이전 기록은 없다.
- 시드 계정 전원(구간 많은 계정·90일 계정 제외)의 2026-11-12에 batch가 바로 처리할 수 있는 일간 통계 표시를 넣는다. 자정 직후 어제 날짜가 한꺼번에 batch 대상이 되는 상황이다.
- 이 상태를 원본 DB `mosemo_b_base`로 복사하고, 회차마다 작업 DB를 지우고 원본에서 다시 만든다(`STRATEGY FILE_COPY`). 모든 회차가 같은 데이터·차가운 캐시에서 시작한다.

## 4. batch

측정 도구가 일간 통계 job(`analytics-daily-stats`)만 k6 시작과 함께 한 번, 이후 300초마다 돌린다(운영 `serve`와 같은 주기). 라벨 제안 job은 외부 호출(Gemini)과 합성 창 제목 전송을 피하려고 돌리지 않는다. 정의 표시 job은 운영에서도 일정이 없다.

## 5. 판정(회차마다)

| # | 기준 | 값 | 적용 시나리오 |
| --- | --- | --- | --- |
| C1 | 조회 지연 | p95 ≤ 300ms, p99 ≤ 500ms | `read`·`stats`·`sessions` 각각 |
| C2 | 전체 오류율 | ≤ 0.1% | 모든 시나리오 합 |
| C3 | 업로드 반영 지연 | p95 ≤ 10초 | `write` |
| C4 | 미처리 기울기 | OLS 기울기 95% 신뢰구간 하한 ≤ 0 | `write` |
| C5 | 부하 발생기 | `dropped_iterations` 0 | 모든 시나리오 |
| C6 | 도착률 | 목표의 ±2%(목표 = k6 실제 값 `round(rps × 100) / 100`) | `read`·`write`·`stats`·`sessions` |

`heavy`·`probe`는 그 지연이 계산 자체라 판정하지 않고 보고만 한다.

G1 결론(`summary-b.json`의 `g1`): R3 두 회 모두 통과 → `no_split_now`(지금은 분리하지 않음). R3가 하나라도 실패하고 R2 두 회 모두 통과 → `split_needed`(분리 필요). 그 밖(R2 실패, 건너뛴 회차) → `undecidable`.

## 6. 보고(판정 아님)

- API 로그 `analytics read` 줄의 `segment_count`별(`small` = 1천 미만, `1000`, `5000`, `10000`) `source_read_ms`·`snapshot_build_ms`·`compute_ms` p50·p95와 건수.
- 걸리는 요청 비율 환산: 무거운 사용자 1%·5%·10%·20%에서 `rps × compute_ms p95(1만) ÷ API Pod 4`(rps = 1천 × 비율 ÷ 60).
- 회차별 batch 실행(`saved`), 회차 시작 표시 수, 원본 복사·되돌리기 시간, 회차 사이 남은 업로드 묶음 수, `pg_stat_statements`, DB·consumer·API CPU(랩 지표).

## 7. 가정

`measurement-b.json`의 `assumptions`와 같다.

- 새 API 조회 횟수는 앱 화면 구성이 정해지지 않아 오늘 화면에 통계가 함께 보인다고 가정했다.
- 무거운 사용자 5%는 근거 데이터가 없는 가정이다. 다른 비율은 6절 환산표로 다시 판단한다.
- k6 업로드는 회차 초반에 시드 계정의 2026-11-12 표시를 다시 쓴다. 운영과 같은 동작이라 막지 않는다.
- 평범한 계정의 오늘은 회차 중 업로드로 쌓인 구간뿐이라 실제 저녁보다 가볍다.
- 고정 부하의 업로드는 10초 창 묶음 가정을 그대로 쓴다. 실제 클라이언트는 1분마다 보낸다.

## 8. 전제와 시간 조건

- 랩 RDS 저장 공간이 원본 DB와 작업 DB를 함께 담을 만큼(50GB 이상) 늘어나 있어야 한다. 측정 A 복원 뒤 DB는 약 11GB다.
- DB 사용자에게 DB를 만들 권한이 있고 작업 DB의 소유자여야 한다(랩 `mosemo`는 RDS 마스터 사용자). prep이 확인하고 아니면 멈춘다.
- 계정 시간대가 모두 Asia/Seoul이다. 원본을 만든 날짜와 회차 시작 날짜가 같아야 하고, 남은 회차가 다음 Asia/Seoul 자정 전에 끝나야 한다. 예상 종료 = 지금 + 남은 회차 수 × (900 + 60 + 600)초. 아니면 멈춘다.
